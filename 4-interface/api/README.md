# `/api/v1` — contract conventions

Binding shape: `openapi.yaml` (this folder). Interim source of truth until the Rust DTOs carry
`utoipa` annotations; from then on CI regenerates the doc from Rust and diffs it against this file.
UI types are generated by `pnpm gen:types` (`openapi-typescript`) + `scripts/gen-sse.mjs` (from
the `x-sse-events` map) into `ui/src/lib/api/types.gen.ts` — never hand-edited.

- **Origin:** same-origin only (served by `111d`). No CORS headers, ever. Dev uses Vite `server.proxy`.
- **Auth:** loopback peers bypass auth. Others need the `s111` session cookie from
  `POST /auth/pair`; missing/invalid → `401 unauthenticated` on every `/api/v1/*` route except
  `/auth/*`. Loopback-only operations → `403 loopback_only`. Mutating routes require
  `Content-Type: application/json`; if `Origin` is present its host must equal `Host`.
- **Errors:** RFC 9457 `application/problem+json` `{type,title,status,detail?,code,errors?}`.
  `code` is the machine key (enum in the yaml). `111d` normalizes upstream plain-text 400/415/422
  from `111-agent` into this envelope (`bad_request`), connection failures into
  `503 agent_unavailable`, model-down into `503 model_unavailable`, `needs hub` into `409 needs_hub`.
- **Versioning:** additive-only under `/api/v1`; a breaking change bumps the prefix. UI and daemon
  ship in one binary, so there is no long compatibility window.
- **SSE (`GET /events`):** `event:` names from `x-sse-events.events`; `id:` is one global monotonic
  sequence per daemon lifetime, assigned at egress; ring buffer 256; `Last-Event-ID` replays from
  the ring, otherwise the first frame is `event: reset` and the client refetches `/status`,
  `/services`, `/proposals`; `: keep-alive` comment every 15 s; `status` is also re-sent every 30 s
  as a heartbeat. `agent` frames are the upstream `111-agent` events verbatim (dedupe on `seq`;
  upstream replays its last 50 on connect). `status` frames are shared by every subscriber, so
  their `auth` block is a placeholder — clients keep the `auth` from their own `GET /status`.
  `services`/`devices` frames are published on a **state** change (plus `since`); `detail`
  refreshes on the next snapshot, not on every probe tick. Layer 5 adds `message` (a new message, a
  state change or a new request, **coalesced per message per tick** so a 16-fragment transfer cannot
  flood the ring), `contact`, `fabric` (a full `FabricStatus` snapshot), `nearby` and `panels` (full
  snapshots). After `reset` the Layer 5 views also refetch `/fabric`, `/messages/threads`, `/contacts`,
  `/nearby` and `/panels`. Layer 6 adds `network_message` and `bridge` (below); after `reset` its views also refetch
  `/networks`, `/bridge/edges` and `/transport`. Layer 7 adds `relay` (a full `RelayStatus` on change) and `registry` (`{rows}`, a full
  snapshot); after `reset` its views also refetch `/relay` and `/registry` (the store re-reads a slice only once something loaded it).
- **Layer 5 additions (Messaging & Data; `os/5-messaging/README.md` §15, D20) — additive under `/api/v1`:**
  - *Routes:* `GET /messages/threads`, `GET /messages/threads/{peer}`, `POST /messages`, `POST /messages/{id}/retry`,
    `GET|POST /contacts`, `GET|PATCH|DELETE /contacts/{id}`, `GET /contacts/me/card`, `GET /fabric`,
    `POST /fabric/hub/enroll`, `POST /fabric/hub/offer`, `PATCH /fabric/settings`, `GET /nearby`, `GET /panels`,
    `POST /panels/{id}/session`, `POST /devices/{id}/identify`. Lists use the `{schema, <plural>}` envelope; single
    resources are returned bare.
  - *Ids and order:* a peer is always its `NodeId` (64 lowercase hex) in paths and bodies; `node1…` is accepted only as
    `POST /contacts {node_id}`. Message ids are `msg-…`, minted by `111d` for the local row — not the wire `msg_id`
    (§4), which only `Message.msg_id` (Advanced) exposes. A thread is ordered by `local_seq`; `Message.at` (local wall
    clock) and `sent_at_claim` (the sender's unverified claim) are display only and never order anything.
  - *States:* `Message.state` is `queued|sent|relayed|delivered` (§9) with `reason_code` + `reason` while it needs an
    explanation: `waiting_for_key`, `hub_not_yours`, `restore_pending`, `store_full` (queued), `mailbox_full` (sent).
    `POST /messages` always answers 202 and never promises delivery. The agent does not call it: it proposes
    (`kind: message`) and the human accepts in the UI. Peer-authored strings (`Message.text`, `NearbyNode.*` names) are
    untrusted: text-only rendering.
  - *Writes that are loopback-only* (403 `loopback_only` otherwise): `PATCH /fabric/settings`, `POST /fabric/hub/offer`.
    The rest follow the usual rule (loopback or a paired session).
  - *Problem codes:* `port_busy` (409 on `identify` when the port has another owner), `panel_ticket_expired` (403, sent
    by a **panel listener** on its own port, not by `/api/v1`: a spent or expired ticket without a cookie),
    `upstream_error` (502: a panel shim whose upstream is down, a hub that is unreachable or refuses, meshmud that did not
    answer an identify). Conflicts that have no dedicated code (not retryable, already enrolled, key conflict on a card)
    are 409 `bad_request`.
  - *Hosted panels (§13):* `ServiceRecord.panel` is `Panel | null`; `embed_url` is never set when it is non-null. The UI
    builds the panel origin from `location.hostname` and `panel.port`; the `POST /panels/{id}/session` ticket URL is
    single use, 30 s, bound to the minting session. Panel listeners answer their own errors as `problem+json` too.
  - *Enum growth (all additive; unknown values render as `unknown`):* `ServiceId` + `fabric`, `meshtastic`;
    `DeviceRecord.actions` has `identify` (now live for Meshtastic-capable boards); `reason_code` sets grow as above;
    `Problem.code` + `port_busy`, `panel_ticket_expired`.
  - *No key material:* `Card` and `HubOffer` carry the public announce and a one-time enrollment code only.
- **Layer 6 additions (Transport & Bridge; `os/6-transport/README.md` §10, D27) — additive under `/api/v1`:**
  - *Routes:* `GET /networks`; `GET|POST /networks/{net}/conversations` (POST opens a foreign DM, `{kind: dm, native_id}`);
    `GET /networks/{net}/conversations/{conv}` (`?limit&since_seq`); `POST /networks/{net}/conversations/{conv}/messages`
    (`{text, size_mode?}` → 202 `{id, plan}`); `POST /messages/fanout/preview`, `POST /messages/fanout` (→ `{group_id, items}`);
    `GET|POST /bridge/edges`, `GET|PATCH|DELETE /bridge/edges/{id}`; `GET|PATCH /bridge/settings`; `GET /bridge/components`,
    `POST /bridge/components/{id}/enable|disable|remove-files`; `GET /transport`, `PATCH /transport/posture`,
    `POST /transport/join`. `{net}` is a network id (`meshtastic`, `lxmf`, `app:deltachat`, `app:simplex`; the colon is
    percent-encoded), `{conv}` an `fc-…` id. Lists use the `{schema, <plural>}` envelope; single resources are bare.
  - *Ids and order:* `fc-…` conversations, `fm-…` foreign messages (one per stored row; a split send is one row per part),
    `be-…` edges, `sg-…` send groups, all minted by `111d`; bodies and proposals name a conversation by `fc-` id, never by
    native id or name. `msg-…` stays 111-only. Foreign rows are ordered by `ForeignMessage.seq` (the store-wide receipt
    sequence); `at` and `claim_ts` are display only. A foreign conversation is never a 111 thread and a foreign address
    never a contact. Foreign strings (`title`, `sender.name`, `text`, `Network.account`, interface names) are untrusted:
    text-only rendering.
  - *States:* `ForeignMessage.state` is the closed enum `queued|sent|relayed|delivered|failed` (§4); Layer 5's
    `MessageState` stays at four and is not used for foreign rows. Monotone; `failed` only for a refusal before air and
    terminal unless a later `delivered` arrives; `dir: in` rows are `delivered`. `reason_code` (vocabulary
    `ForeignReasonCode`) grows by: `region_unset, no_channel, too_large, not_authorized, pki_failed, got_nak, adapter_down,
    no_route, timeout, max_retransmit, no_response, duty_cycle, rate_limited, key_unknown, peer_unannounced, uplink_off,
    ham_unconfirmed, consent_paused, cancelled, oversize`; the field stays a plain string so growth is additive, and unknown
    values render as `unknown`. `Network.state` is `live|not_set|error|disabled`; `Component.state` is
    `declared|cached|installed|running|disabled`.
  - *Writes and the 401 rule:* the agent's bearer is refused with `401 unauthenticated` on **every non-GET** (one global gate
    in `require_session`, no allowlist; this includes `POST /services/{id}/restart` and `POST /devices/{id}/identify`, which
    never called the per-route refusal). The bearer reads every GET, so a route that returns a credential is a POST
    (`/transport/join`, which also answers `no-store`). The agent acts only through proposals (`kind: bridge_message`,
    `bridge_edge`, `device`); a human decides them on a paired or loopback session.
  - *Consent round-trip (`409 consent_required`):* edge enable and resume, component enable, HAM confirmation and the
    uplinked-channel send switch are never a bare write. The first call (without the hash) answers `409` with code
    `consent_required` and the extension member `consent` = `{action, subject, warning_text, hash, addons}`; the client shows
    `warning_text` verbatim and repeats the call with the hash (`accept_warning`; `accept_notice_hash` on component enable;
    `accept_warning` on `POST /proposals/{id}/decision`). The hash is the lowercase hex SHA-256 of the exact UTF-8 bytes of
    `warning_text`. The text is read live: a fact that changed (uplink, licensed mode, channel key) produces a new text and
    hash, so a stale echo is refused again, and a `consent_paused` edge resumes only with the new hash.
  - *Fan-out:* validation is atomic. A target refused for `oversize` (refuse mode) or a consent gate answers `409` (code
    `oversize`, or `consent_required` when a gate is involved) with the extension member `targets` =
    `[{target, code, detail, consent}]` for every refused target, and nothing is queued. Adapter state (region unset, board
    away, queue full, no path) is never a call error: the row queues with its `reason_code`. `size_mode` is `refuse`
    (default) or `split`, per target. `SendPlan` is the per-target preview (`bytes`, `cap`, `parts`, `airtime_estimate`,
    `refusal`, `warnings`); airtime is always an estimate.
  - *SSE:* `network_message` `{network, conv, id?, change: new|state|conversation, seq}` carries no text (refetch the
    conversation). It is coalesced per message per tick for DMs and own rows and **per conversation per tick** (the
    conversation plus its highest `seq`, no `id`) for unpinned channel traffic, so a flood cannot fill the 256-entry ring.
    `bridge` `{networks?, edges?}` carries full snapshots of whichever part changed. A foreign DM raises the unread count
    only, never the header badge.
  - *Problem codes:* `consent_required` (409), `oversize` (409), `component_unavailable` (409: the optional component is not
    enabled, its payload is missing from the cache or fails its pin, or `[requires]` is unmet; nothing is installed),
    `unsupported_action` (a `device` proposal action outside the four applied and two one-shot actions). `not_supervised`
    already exists (Layer 4/5) and is what `service.restart` on an unsupervised child answers.
  - *Enum growth (all additive; unknown values render as `unknown`):* `Proposal.kind` + `bridge_message`, `bridge_edge`,
    `device`; `NearbySource.kind` + `reticulum`; `Problem.code` as above; new schemas `ForeignMessageState`, `ForeignAuth`
    (`none|channel-key|pki|signed|attested-111`), `ForeignConvKind`, `NetworkState`, `ComponentState`. `ServiceId` does not
    grow; `DeviceRecord` is unchanged.
  - *Proposal bodies:* `bridge_message` = `to: <fc-id>` lines, a blank line, the text verbatim; `bridge_edge` = a `from: <fc-id>`
    line and a `to: <fc-id>` line, then the reason. **The text part of a `bridge_message` or `bridge_edge` body is foreign
    text and is rendered as a preformatted text block, never as Markdown** (the agent view otherwise renders proposal bodies
    as Markdown with external links). `device` = one JSON object `{"why": string, "actions": [Action]}`; an Action is
    `{"action": name, …args}` from `rns.interface.upsert {device_id, type, params}`, `rns.interface.remove {name}`,
    `rns.posture.set {share_instance, enable_transport}`, `radio.region.set {region}`, plus the one-shots
    `identify {device_id}` and `service.restart {service_id}`; the rest of the vocabulary (`meshtastic.set`, `ble.pair`,
    `ble.forget`, `firmware.flash`) is refused `unsupported_action`.
  - *Optional components (§2.1):* `GET /networks` and `GET /bridge/components` list a disabled component with its cached and
    installed size and licence notice; enabling needs the recorded acknowledgement and installs from the install-time cache
    (nothing downloads at runtime). A disabled component has no process, listener or timer.

       `scripts/gen-sse.mjs` (`ALIASES`, `ENUMS`).
    4. The UI store's SSE `switch (frame.event)` in `ui/src/lib/api/store.ts` (no `default`: an unknown event is ignored, so the

- **Layer 7 additions (Relay & Presence; `os/7-relay/README.md` §13, D30–D32) — additive under `/api/v1`:**
  - *Routes:* `GET /relay` (`RelayStatus`), `PATCH /relay/settings` (a partial merge; the same keys, secrets as write-only strings),
    `POST /relay/pair/offer` (`{role, via}` → `{bundle, code, link_spki}`; dismissed with `DELETE /fabric/hub/offer`), `POST /relay/pair`
    (`{bundle, role, via, lan?, accept_warning?}` → 202 `PairedHub`), `DELETE /relay/paired/{node_id}` (204, idempotent),
    `POST /relay/carrier/check`, `POST /relay/carrier/flush` (202 `{schema, started}`), `GET /registry` (`{schema, rows}`),
    `POST /registry/browse` (202, a DNS-SD browse of at most 5 s), `POST /nearby/hops` (202; a program spawn, so a POST), `GET /update/origins`
    (`{schema, origins}` in the order they are tried). Lists use the `{schema, <plural>}` envelope; single resources are bare.
  - *Who may call:* `GET`s follow the usual rule and the agent's bearer reads them. The agent's bearer is refused (`401`) on every write
    here (the global gate, no allowlist); the agent acts only through proposals (`kind: relay`). **Loopback-only** (403 `loopback_only`
    otherwise): `POST /relay/pair/offer`, `POST /relay/pair`, `DELETE /relay/paired/{node_id}`, like their Layer 5 siblings; the CLI
    `111 fabric pair` covers the phone case.
  - *`/origin/v1/*` is not in `openapi.yaml`:* `GET /origin/v1/channel-111-stable.toml`, `…toml.minisig` and `blob/{sha256}` are the hub's
    update-origin files (§9.1): read-only, unauthenticated, GET only (405 otherwise), 404 when not serving, mounted beside `/health`
    (see "Not gated"). Their scope is not `/api/v1`.
  - *No secret on any route:* the carrier token and topic secret are write-only. `RelayStatus.carrier.token` and `.topic_secret` are
    `{set: boolean}`; the values are never echoed, logged or sent on SSE. Ages (`checked_ago_s`, `last_flush_ago_s`, `heard_ago_s`,
    `ago_s`) are seconds from a monotonic clock; no Layer 7 shape carries a wall-clock timestamp. Every name, label, endpoint, url and
    evidence string is untrusted: text-only rendering.
  - *Consent round-trip (`409 consent_required`):* the Layer 6 round-trip, unchanged. The Layer 7 gates are `carrier_enable` (a carrier
    turned on, its server changed, or a metered cap set or raised while it is on, with `metered` in `addons`; subject `<kind>:<server>`),
    `gateway_bit` (the public gateway role bit), `origin_serve` (serving update files to the LAN) — all on `PATCH /relay/settings` — and
    `pair_plain` (pairing over an unencrypted non-private link, `POST /relay/pair`, subject the far hub's NodeId). The first call (without
    `accept_warning`) answers `409` with `consent` = `{action, subject, warning_text, hash, addons}`; the client shows `warning_text`
    verbatim and repeats the call with `accept_warning` = the hash (on `POST /proposals/{id}/decision` too). A changed text has a new
    hash, so a stale echo is refused again.
  - *Pairing:* the scan side picks `role` and `via` from its own side and they must complement the bundle's (`peer`↔`peer`,
    `leaf`↔`gateway`, same `via`), else `409 pair_role_mismatch` and nothing is recorded; a `carrier` pair is `peer` only, a `leaf` or
    `gateway` pair `tcp` only. `lan` (default `false`) is the owner's mark that the link is a LAN or an adopted tunnel and runs plain.
    `PairedHub.tls` is `rpk` | `plain` (accepted after `pair_plain`) | `none` (a `lan` or `carrier` pair), with `lan` beside it.
  - *Heartbeat:* every write of `presence.heartbeat` answers `409 no_such_transport`, except `rns`, which answers `409 settings_locked`
    naming `PATCH /api/v1/bridge/settings`; nothing is written. The proposal action `presence.interval` is refused `unsupported_action`
    in v1.
  - *Problem codes:* `no_such_transport`, `licensed_board`, `metered_cap` (409: no request is made past a metered link's daily cap),
    `lan_off` (409: a registry browse or origin serving needs LAN sharing), `pair_role_mismatch` (409). "Needs a hub" stays `needs_hub`.
    `component_unavailable` and `rate_limited` serve `POST /nearby/hops`; `settings_locked` already existed.
  - *SSE:* `relay` = `SseRelay` (a full `RelayStatus`) and `registry` = `SseRegistry` (`{rows}`), both full snapshots on change; no
    timer refreshes either.
  - *Enum growth (all additive; unknown values render as `unknown`):* `Proposal.kind` + `relay` (body: one JSON object
    `{"why": string, "actions": [Action]}` from `gateway.enable {carrier, mode}`, `hub.pair {}`, `presence.interval {transport, minutes}`,
    `carrier.flush {}`; rendered as a card from the parsed JSON, never as Markdown); `NearbySource.kind` + `111` and `NearbyNode` +
    `heard_ago_s`, `heard_seq`, `evidence` (`[{transport, text}]`, `transport` ∈ `tcp-lan`, `hub`, `carrier`), `roles`,
    `position_precision_bits`; `ConsentRequired.action` + the four above; `Problem.code` + the five above; `Message.reason_code` +
    `forwarding` (state `relayed`: "Your hub holds it and passes it to their hub.", `MessageState` stays at four); the `gateway` service
    row's `reason_code` set is `gateway_none`, `carrier_ok`, `carrier_pending`, `gateway_off` (`wan_ok`, `wan_unknown`, `wan_offline`
    retire) and its `detail` is `GatewayDetail`; `HubOffer` + `gateway {carrier, mode}` (the member learns its hub is a gateway once,
    at enrolment). New schemas: `RelayStatus`, `RelaySettingsPatch`, `PairedHub`, `RegistryRow`, `UpdateOrigin` and their parts.
  - *Pin list (each enum or tool-count bump touches these; the change is not done until all are green):*
    1. `Proposal.kind` 8 → 9 (`relay`): `KINDS` in `1-bootstrap/crates/node111/src/daemon/dashboard/api_v1/proposals.rs` (`[&str; 9]`; an

- **Not gated:** `/`, static assets, `/health` (body is booleans), `/origin/v1/*` (Layer 7, §9.1: the hub's verified update files, GET only,
  404 unless the hub serves them; outside `openapi.yaml`) and `/api/v1/auth/*`. Everything
  else — including the Layer 1 seam `/api/status` and the `/v1` legacy page — needs loopback or a
  session.
- **Chat stream (`POST /chat`, `stream:true`):** the response body is `text/event-stream` with
  `event:` names from `x-sse-events.chat`; the stream ends after `done` or `error`. No `id:` lines.
  Pre-stream failures are `problem+json`, never SSE. Clients use `fetch` + a streaming parser
  (`EventSource` cannot POST). `stream:false` returns `ChatReply` JSON.
- **Identity:** no key material on any route, ever (Layer 2 rule). `node.label`/`bech32` are
  display forms computed from the public id.
- **Timestamps:** RFC 3339 UTC. **IDs:** `conv-…` minted by the client (`[A-Za-z0-9_-]{1,128}`);
  `prop-…`/`task-…` minted by `111-agent`; `msg-…` minted by `111d` (Layer 5); `fc-…`/`fm-…`/`be-…`/`sg-…` minted by `111d` (Layer 6). Layer 7 mints no new id family: a paired hub is its `NodeId`.
