# Layer 5 gap 1: who drives the LoRa radio, and what runs on a Cat-1 relay

Scout run 2026-10-14. Sources are fetched upstream files; line numbers are from the files as fetched today. "(computed)" = my arithmetic from fetched constants. "(unverified)" = not confirmed from a fetched source.

## 1. Summary

- **One board, one owner.** If rnsd holds the port (RNodeInterface), 111 has no LoRa path of its own. If 111d holds it, rnsd can still ride through it. So 111d should own any board that carries 111 frames.
- **Option A works in upstream code.** rnsd's `TCPClientInterface` with `kiss_framing = True` and `fixed_mtu = 500` is the documented way to attach to "external devices and programs like soundmodems" (interfaces.rst 390-405). It writes the same bytes as RNodeInterface: `FEND 0x00 escape(packet) FEND` (RNodeInterface.py 722-725; TCPInterface.py 322-323). The RNode firmware adds the 1-byte header and splits packets over 254 B itself, in either mode (.ino 716-745), so on-air frames stay interoperable with Reticulum RNode peers.
- **A has two traps.** rnsd assumes 10 Mbit/s on a TCP link, so announce caps never bite unless 111d renders `bitrate =` from SF/BW/CR. And the firmware prepends a header byte to every frame, so a 111 frame sent through a normal RNode is unreadable to a MeshCore or Meshtastic repeater.
- **Adopted repeaters can carry opaque 111 payloads, in their own format.** A stock MeshCore repeater floods any `GRP_DATA` packet without the channel key (Mesh.cpp 225-249, 344-356), and MeshCore keeps a registry for third-party data types (`number_allocations.md`). Cat-1 then needs no firmware of ours. The host needs a raw modem (MeshCore KISS modem, or RNode `CMD_PROMISC`) and builds the MeshCore frame itself.
- **Option B (rnsd owns the port) has no clean carrier.** lxmd has only an inbound hook, MeshChat takes no arbitrary field, rncp moves files, rnx runs remote commands; the rest needs `import RNS`/`LXMF`, which is banned. It fails D17 #12 as a fabric path and stays the deferred `rns-bridge`.
- **D17 #1 needs one sentence changed, not reversed:** "RNode default makes the board an rnsd interface" becomes "RNode is the default firmware; 111d owns the port; rnsd attaches by loopback on request".

**RX under A.** 111d hands every frame to both 111f and the rnsd socket; each drops what it cannot parse. No classifier is needed. Cost is CPU and noise; rnsd's tolerance of garbage is unverified.

**What rnsd loses under A (RNodeInterface.py, interfaces.rst).**
- Per-interface RSSI/SNR, channel load, noise floor, battery, and `rnstatus` radio detail.
- `airtime_limit_short/long` and `flow_control` (RNodeInterface-only, interfaces.rst 640-660). The firmware still enforces `CMD_ST_ALOCK/LT_ALOCK` if 111d sets them (.ino 932-975, 1673-1696). Under the no-policy rule 111d sets only what law requires (D17 #10) and publishes it to the fabric as physics.
- Automatic bitrate (RNodeInterface.py 700). The generic `bitrate` key is honoured (Reticulum.py 929-931, 1230), as is `announce_cap` (default 2%, Interface.py 117, 415-416), so 111d renders both.
- Radio-parameter discovery announcements (documented for RNodeInterface and KISSInterface only, interfaces.rst 1059).
- MTU is not lost: fixed 500 equals `Reticulum.MTU` (Reticulum.py 93). RNodeInterface HW_MTU is 508; KISSInterface 564 with a 1200 bit/s guess; PipeInterface 1064 with a 1 Mbit/s guess and HDLC, not KISS (KISSInterface.py 62, 102; PipeInterface.py 56, 76).
- Do not point rnsd's KISSInterface straight at an RNode: it sends TXDELAY/P/SLOT/TXTAIL as 0x01-0x04, which RNode firmware reads as frequency/bandwidth/txpower/SF (applied in HOST mode, stored only in TNC mode; .ino 830, 879, 891).

**Does A count as "Reticulum as-is"?** Yes under LICENSING.md 20-35: separate unmodified process, we only write an INI stanza of a documented interface type. Caution: write the RNode driver from the GPL-3.0 firmware source and board behaviour, never from RNodeInterface.py (Reticulum License). I read it for analysis only.

**Option B carriers (LXMessage.py 62-95, Packet.py 106, Link.py 73; arithmetic computed).** LXMF opportunistic single packet 287 B content (383 - 112 + 16), about 230 B after our 56 B seal; over a Link, one packet 319 B (431 - 112), after a handshake; larger via Resource. MeshChat send takes content/image/audio/file only; lxmd has `on_inbound` and propagation, no send; rncp is a file per Link; rnx is remote execution (reject). Reticulum's Token encryption would wrap our seal: two encryptions, two identities (LXMF address plus NodeId), rnsd on the critical path.

## 4. Recommendation

1. **A + E:** RNode everywhere, 111d multiplexes, Cat-1 is 111-native firmware. Keeps D17 #1 whole; reinvents the repeater and owns its firmware burden.
2. **C + D1 (pick):** the board 111 owns is a raw modem emitting MeshCore `GRP_DATA` frames; Cat-1 is the stock MeshCore repeater; Reticulum users get a second RNode board (C) or opt into A on one board.
3. **B:** rnsd owns the port, 111 over LXMF. Rejected as fabric (fails D17 #12, no clean carrier).
4. **D3:** Meshtastic as bearer. Same relay-blind logic, 233 B, parked by D18 #3.

**Pick: 2.** It is the only path with no custom relay firmware, the relay is MIT and already deployed, and lens 2's fragment size F = 160 B was already set by MeshCore's 163 B group data. Cat-1 no longer needs to parse our shim, because MeshCore does dedupe and hop limits; lens 4 item 10 is needed only on fallback to E.

Rules to record: each board has `owner = 111d | rnsd` in `state/interfaces.toml`; a 111d-owned board runs profile `raw` (MeshCore frames) or, on opt-in, `shared` (A). In `shared` the frames are RNode-framed, so adopted repeaters cannot relay them; they travel hub to hub through the fabric's own store-and-forward.

**Raw modem.** MeshCore KISS modem (MIT, documented, 255 B raw frames, p-persistent CSMA, `SetRadio`, `GetAirtime`, `RxMeta`, `TxDone`, one pending TX) has PlatformIO envs for Heltec V3, Heltec V4 and RAK4631 (platformio.ini 374, 435, 266) but **no kiss-modem release tag among the latest 60 releases**, so we would build and pin images. RNode promisc has upstream releases (GPL-3.0) but an undocumented command. Pick the KISS modem if the owner accepts CI-built pinned images; otherwise RNode promisc.

**Fallback.** If a two-board bench shows MeshCore flood or scoped-flood policy unacceptable, build E on RadioLib.

### (f) Can one board be host modem and keep repeating?
- **Meshtastic:** yes. CLIENT forwards (CLIENT_MUTE does not); the API client attaches while the node keeps its role (config.proto roles). Subject to D18 #3.
- **MeshCore companion:** only with client-repeat, and only on 433.000, 869.495 or 918.000 MHz by default (compile-time `ALLOWED_REPEAT_FREQ_RANGE`; companion MyMesh.cpp 485, 995-1020, 1385-1405). Upstream's blog says clients normally do not forward (search snippet; page not read).
- **MeshCore KISS modem:** no forwarding code (kiss_modem/main.cpp). **RNode:** none.

## 5. Open questions for the owner

1. **Must D17 #1 be revisited?** Not for RNode as the firmware default. Choose: (a) keep RNode as the only blank-board default and use A / A'; or (b) add MeshCore KISS modem as the default for boards 111 owns, RNode for Reticulum boards (my pick).
2. May 111 traffic use neighbours' MeshCore repeaters and airtime (flood up to 64 hops), or only repeaters we own?
3. Register a MeshCore `GRP_DATA` data-type range by PR to `number_allocations.md` (0xFF00-0xFFFF while developing)?
4. Accept CI-built, pinned MeshCore images (D17 #9), or prefer upstream-released RNode images?
5. GPL-3.0 firmware (RNode, Meshtastic) in the signed manifest carries a source-offer duty: acceptable for the licence review?
6. Unverified items (Meshtastic sync word, MeshCore repeater airtime budget, public-mesh region policy, rnsd tolerance of garbage frames): approve a two-board bench before the fabric is locked?
