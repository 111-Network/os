# Layer 8 research 07 - gap G2: software updates beyond the 111 release (component payloads, Termux debs, APKs, mirroring duties)

Gap-fill scout for `06-critic.md` §4 G2. Written 2026-11-02 on a box whose proxy allows `raw.githubusercontent.com`, PyPI and crates.io and denies
f-droid.org, packages.termux.dev, salsa.debian.org, sources.debian.org and developer docs. Licences below were read from upstream files unless marked.
Layer 7's hub origin (`7-relay/README.md` §9, `D30 F6`) is the base this report extends; the Layer 9 hand-offs are in §3.6.

## 1. Summary

- **Today nothing but the 111 release has an offline route.** Component payloads are "never shipped as bytes in a release", downloaded from the pinned
  upstream URL at `111 install` (or `sudo 111 install --components ID`), and "a USB drop into the same directory is the offline alternative"
  (`1-bootstrap/README.md:227-246`, `6-transport/README.md:113-117`). The installer's fetcher takes one URL per pin (`install/packages.rs:253-262`,
  `cache_binary` `:498-535`); pip closures run `pip download --require-hashes -r lock -d cache/packages/<id>` against pip's default index (`:480`).
  No origin list exists for either.
- **The pins are already origin-independent.** A component's declaration (URL, sha256, size, or a hash-locked lock) is embedded in the signed `111`
  binary (`daemon/components/manifest.rs:2-4`, `embedded()` `:88`); the fetcher checks size and sha256 before a byte lands. So Layer 7's rule "a hub serves
  only bytes it verified, `blob/<sha256>`" (`7-relay/README.md:867`) extends to components with **no new trust anchor**: the hash is the address and the proof.
- **Who needs which payload decides the value.** Delta Chat core (21.0 to 26.8 MB per target) and Madmail (73.5 to 77.3 MB, glibc 2.38) run on the bridging
  hub and refuse on a phone (`deltachat.toml:6-8`, `madmail.toml:6-9`): their ~104 MB mostly moves hub to hub. The LXMF closure (5.83 MB of wheels) is the
  one payload any member node with `rnsd` needs. Termux debs and APKs are consumed by a provisioning host with `adb`, not by the phone (§3.3).
- **A hub mirror of third-party binaries makes the hub operator the party that conveys them.** GPL-3.0 §6(d), GPL-2.0 §3, MPL-2.0 §3.2 and the
  Reticulum License's notice clause each attach duties to the one who hands over a copy. D26 (5) ("the user installs; 111 and its author are not the
  distributor") says nothing about a third person's disk being the source (§3.4 item 21). The same duty already exists, unrecorded, for the 111 release that the
  F6 origin serves (§3.4 item 22).
- **Candidates: none needs to be resident, and the best fits are files.** A flat pinned-blob directory costs no tool. Of the tools, `termux-apt-repo`
  (Apache-2.0, one Python script) and `fdroidserver` (AGPL-3.0, publisher-side only) can produce a static repo the dashboard listener serves; `apt-cacher-ng`
  and `devpi` are resident daemons and fail the Pi floor; `aptly`, `bandersnatch` and `reprepro` are mirror-and-publish tools whose weight sits on a
  publisher, not on the node (§2).
- **Pick (§4): option 1.** Components, wheels, and (as pins) Termux debs and APKs go out as `blob/<sha256>` behind a separate hub switch with its own
  licence notice; the Termux apt directory and the APK catalogue wait for v1.1. It amends Layer 1 §"components" and Layer 6 §2.1(3) by one sentence each.

## 3. Findings

### 3.1 What the fetchers do today (a)

1. `1-bootstrap/README.md:227-246`: components are declared in `assets/components/<id>.toml` (embedded in the binary), "never shipped as bytes in a release";
   step 5 prints one notice line per program and records it before the download; payloads land in root-owned `cache/packages/<id>/`; a failed download is a
   receipt degrade branch; "a USB drop into the same directory is the offline alternative". `6-transport/README.md:113-117` repeats it and adds "There is no
   runtime fetch".
2. `install/packages.rs`: `PayloadFetcher::fetch(&self, url)` (`:253-262`) is implemented by the HTTPS `Fetcher`; `cache_binary` (`:498-535`) fetches the
   pinned URL, checks size and SHA-256, writes `atomic_write(.., 0o644)` into `cache/packages/<id>/`. `Fetcher::get` returns the whole body in memory
   (`util/http.rs:36`, capped), so a 77 MB Madmail is a transient 77 MB RSS; the same holds for the release payload (`04-kb-updates.md:57` in Layer 7).
   `http://` is a test-only exception today (`util/http.rs:4-7`); Layer 7 T6 adds the home hub's LAN address (`7-relay/README.md:910`).
3. Pip closures: `pip download --require-hashes -r <lock> -d cache/packages/<id>` in a throwaway venv (`packages.rs:480`, `:455`); if `python3`/`venv`
   is absent the closure is "not cached" (degrade, `:457-464`). The lock holds hashes, not filenames (`lxmf.lock.txt`: 167 `--hash` lines, "every file PyPI
   publishes for each pinned version, all platforms + sdist"). Enable then installs offline from the cache with `--require-hashes` (`6-transport/README.md:122`).
4. Sizes (from the declarations and `6-transport/TASKS.md`): `deltachat-rpc-server` 2.63.0: 26,811,824 B x86_64, 21,009,952 B aarch64, 21,897,944 B
   Android (`deltachat.toml:23-37`); Madmail 2.30.5: 77,331,312 B x86_64, 73,479,752 B aarch64, no armv7 or Android build (`madmail.toml:30-39`). Together
   **104.1 MB x86_64, 94.5 MB aarch64**. LXMF helper: 5.83 MB of wheels for this platform, 24.9 MB installed, cryptography 4.75 MB of the wheels
   (`lxmf.toml:35-40`); PyPI shows `rns` 1.5.7 as a 644,289 B wheel and `lxmf` 1.2.1 as a 70,324 B wheel (PyPI JSON, read). SimpleX is `kind = "none"` (D27:
   nothing pinned). MeshChatX is dropped as carrier (D26 (4)); the Meshtastic web client is not a component, it is a payload member (`1-bootstrap/README.md:43`),
   so the F6 release blob already carries it. The Termux trio and the debs are sized by the release manifest (`manifest.rs:27-41`), not in the repo yet.

### 3.2 Could a hub serve components in the origin form? (a)

5. **Yes for binaries, with no Layer 7 change except the admission rule.** The hub holds the bytes already when its own operator ran `111 install --components`:
   they sit in `cache/packages/<id>/` as mode 0644 files in a root 0755 directory, readable by the `node111` daemon, and the receipt records a sha256 for every
   one (`record_cache_hashes`, `packages.rs:226-248`). F6's rule "blobs whose sha256 and size match a pin" (`7-relay/README.md:867`) becomes "match a pin in
   the release manifest **or in an embedded component declaration** of an installed release". Disk cost to the hub: zero beyond what it cached for itself;
   up to 104.1 MB (x86_64) or 94.5 MB (aarch64) if the operator pre-caches to mirror. The hub keeps two releases (`1-bootstrap/README.md:111`), so a
   member one release behind still finds its old pin.
6. **For pip closures the origin form needs a filename the lock does not give.** `blob/<sha256>` carries no wheel filename and pip reads the platform tags from
   it. Cheapest fix: `gen_lock.py` also writes a files table (name, sha256, size) beside the lock, embedded the same way; the fetcher then pulls each wheel
   from the hub by hash and writes it under its name into `cache/packages/<id>/`, and enable's existing offline `--require-hashes` install is unchanged. Side
   effects: the hub path needs no throwaway venv (so no `python3-venv` at fetch time), and the table limits the set to one target's files (cryptography is
   the weight), not the 167 hashes of every published file.
7. **What Layer 1's fetcher needs:** an ordered origin list per component, like Layer 7 §9.3: `[home hub, pinned upstream URL]`, the hub's `origin_base` from
   enrolment (`7-relay/README.md:860`), a miss (404, wrong size, wrong hash) falling through to upstream, nothing new for an offline node with no hub.
   `PayloadFetcher` gains `fetch_pin(sha256, size, upstream_url)`. The consent chain does not change: the notice is printed and recorded before any
   download (`packages.rs:321`), now naming the source; enable stays offline. The "no runtime fetch" rule holds because the CLI verb runs at install time.
8. **Version skew and discovery.** A hub on an older release has no pin for a newer node's payload: 404, fall through to upstream. No advertisement is needed:
   Layer 7's `REGISTRY_REPLY origin {release}` (`7-relay/README.md:779`) stays as it is and a blob GET is its own probe.

### 3.3 Termux debs, APKs (b)

9. **Layer 1 does not use apt on the phone.** The manifest pins each deb (`[[deb]]` name, url, sha256, size, `manifest.rs:36-41`) and each APK
   (`[apk.termux]`, `-boot`, `-api`, `:27-34`); the host downloads them, the phone receives "pushed payload + prefetched .debs (on-device sha256 against the
   manifest before `dpkg -i`)" over `adb`, and the APKs go in with `adb install -r` (`1-bootstrap/README.md:44,68-69`). So the 111 requirement for a Termux
   source is **blob-by-pinned-hash for a host**, which is option 1 with no new tool.
10. **Where apt would matter** is a user's `pkg install` of Layer 8's own tools: `kiwix-tools 3.8.2` with `libzim 9.8.2` and `libkiwix 14.2.1` and their
    ICU, Xapian, libmicrohttpd, libcurl, pugixml, zstd, lzma, docopt dependencies (`01-datasets-hub.md:65-66`). A hub mirror of that closure is a Termux
    repo subset: `termux-apt-repo` builds one from a directory of `.deb`s (script read: `argparse` options `input output [dist] [comp] -s`; writes
    `Release` with `Codename: termux`, `Packages` and `Packages.xz`, hashes md5/sha1/sha256/sha512). Output is static, so the existing listener serves it
    (ETag/304 exist; `Range` does not, `01-datasets-hub.md:15-17`). Facts not obtainable here: the size of the subset, whether Termux `apt` accepts a
    third-party repo with `signed-by`, the fixed `com.termux` prefix of the debs (all **unverified**; packages.termux.dev and the Termux wiki were denied).
    A signed repo adds a **new key** (the hub owner's) and one on-device step per phone (add the key and source), which Layer 1's run-as channel can do only
    at provisioning.
11. **APKs cannot be re-signed by a hub.** The GitHub Termux builds carry a public test key (`1-bootstrap/README.md:165`) and the plugin APKs share Termux's
    uid by signature (the collision check, `:67`); a re-signed APK would be refused as an update and would break the shared uid. So "an APK directory signed
    by the hub owner's key" can mean only a **signed index over unmodified APKs**; the pin that authenticates an APK today is the sha256 in the signed 111
    manifest (`:67`, `:164`), and the hub only needs to serve that blob.
12. **fdroidserver builds that signed index.** Build chain (read from source): Python >=3.9; androguard >=3.3.5; asn1crypto, defusedxml, GitPython, oscrypto,
    paramiko, Pillow, PyYAML, ruamel.yaml, requests, sdkmanager and more (`setup.py:80-110`); `keytool` and `jarsigner` from a JDK and `apksigner` from
    Android build-tools (`common.py:441-478,961-1006`); a keystore (`examples/config.yml:150-154`). Output: `index-v1.jar`, `index-v2.json`, `entry.jar` plus
    the APKs, all static (`index.py:860,1102,1931`; `01-datasets-hub.md:101-105` already picked the `entry.jar` shape for datasets). A phone then needs the
    F-Droid client (GPL-3.0) installed and the repo added by URL and fingerprint. Licence of the **tool** is AGPL-3.0; the AGPL does not extend to the repo it
    writes (the index and APKs are other works). The publisher host carries the weight; the node carries none.
13. **Android install requirement** (user enables "install unknown apps" for the app that opens the APK; no `adb` on a phone, so every APK update is taps) is
    from general knowledge: **unverified**, developer.android.com was denied. Layer 9 already treats it as "a human-instruction proposal, no adb on a phone"
    (`9-evolution/research/06-critic.md:31`) against `1-bootstrap/README.md:160` ("APK refresh = Layer 9 maintenance task").
14. Meshtastic's and Delta Chat's own Android APKs are in no 111 manifest today (only the Termux trio, `manifest.rs:27-34`); the Meshtastic app is GPL-3.0
    (`Meshtastic-Android/LICENSE` read); `deltachat-android`'s LICENSE path 404'd (unverified). Hosting them is new scope, not a fix of an existing seam.

### 3.4 Mirroring duties: what each licence says the hub operator must do (c)

Facts with the licence line; a legal read decides how they apply to a private LAN.

15. **GPL-3.0** (kiwix-tools 3.8.2 debs, Termux app, Meshtastic app, meshmud and the Meshtastic web bundle in the release): "To 'convey' a work means any kind of
    propagation that enables other parties to make or receive copies. Mere interaction with a user through a computer network, with no transfer of a copy,
    is not conveying" (`:100-102`); "You may make, run and propagate covered works that you do not convey, without conditions" (`:165-166`). §6 (`:246-288`):
    object code needs the machine-readable Corresponding Source "in one of these ways": (b) a written offer valid three years (`:258-268`); (d) "offering
    access from a designated place ... and offer equivalent access to the Corresponding Source in the same way through the same place at no further charge",
    where the source "may be on a different server ... provided you maintain clear directions next to the object code saying where to find the Corresponding
    Source" and "you remain obligated to ensure that it is available for as long as needed" (`:276-287`); (c) is "allowed only occasionally and noncommercially"
    (`:270-274`). §4 (`:196-204`): "give all recipients a copy of this License". `LICENSING.md:226` says this is "Not yet written into the release process" and
    item 14 (`:266`) asks whether pointing at upstream satisfies §6 for files hosted by us.
16. **GPL-2.0 §3** (libzim, GPL-2.0-or-later, a dependency of kiwix-tools): 3(a) accompany with complete source, 3(b) a written offer valid three years (`:138-147`),
    3(c) "allowed only for noncommercial distribution and only if you received the program ... with such an offer" (`:149-153`); and "offering access to copy from a
    designated place, then offering equivalent access to copy the source code from the same place counts as distribution of the source code" (`:166-170`).
17. **AGPL-3.0** (Madmail; also fdroidserver as a tool): §6 has the same shape as GPL-3.0 (`agpl3.txt:233`); §13 (`:540-551`) binds "if you modify the Program", so an
    unmodified binary served by a hub does not trigger the network-source duty on the hub; running a modified one would. `LICENSING.md:238` already requires
    the pinned tag in the source offer.
18. **MPL-2.0** (`deltachat-rpc-server`): §3.2(a) the Covered Software "must also be made available in Source Code Form ... and You must inform recipients of the
    Executable Form how they can obtain a copy of such Source Code Form by reasonable means in a timely manner, at a charge no more than the cost of distribution"
    (`:174-178`); §3.2(b) the executable may go under the same licence (`:180-184`); §3.4 licence notices in the source stay (`:198-204`). An unmodified upstream
    release binary plus the pinned tag link is what the notice already names (`deltachat.toml`, `[license] read_at`).
19. **Apache-2.0 §4** (`:89-121`): give recipients "a copy of this License" (a); mark modified files (b); keep notices (c); a NOTICE file's content goes along
    with Derivative Works you distribute (d). An unmodified Apache-2.0 binary needs the licence copy beside it.
20. **Reticulum License** (read from `markqvist/Reticulum/master/LICENSE`, 1,510 B, byte-identical size in LXMF; this closes `LICENSING.md:56` "exact text is not in the
    repo"): an MIT text that grants "use, copy, modify, merge, publish, distribute, sublicense, and/or sell", on conditions: no use "in any kind of system which includes
    amongst its functions the ability to purposefully do harm to human beings"; no use "directly or indirectly, in the creation of an artificial intelligence, machine
    learning or language model training dataset"; and "The above copyright notice and this permission notice shall be included in all copies or substantial portions". So
    a hub may distribute, **keeping the notice with every copy**. No source offer (it is not copyleft). The `rns` 1.5.7 wheel has no LICENSE file in its dist-info
    (`METADATA` says `License: Reticulum License`) but `RNS/__init__.py` opens with the full licence header (wheel read), so an unmodified wheel carries the notice;
    the hub should still serve the licence text beside the blob. The two use restrictions travel to whoever uses it; nothing in a hub makes them harder to meet
    (no on-node training, D10, `LICENSING.md:230`).
21. **What D26 (5) changes when the hub is the source.** D26 (5) rests on one fact: the user's own machine fetches from "the public source" after a notice, so
    "111 and its author are not the distributor" (`DECISIONS.md` D26 (5); `LICENSING.md:237`). With a hub origin the copy a member receives comes from the hub
    operator's disk, and "convey" is defined by who enables others to receive copies (`gpl3.txt:100-102`). Therefore: (i) the operator, not the member, carries
    the §6, §3(b) and §3.2 duties for what the hub serves, and a member's recorded acknowledgement does not discharge them; (ii) if operator and user are one
    person serving only their own devices, whether that is conveying is the legal read already open at `LICENSING.md:266`; (iii) 111's author still writes no
    bytes of the program, but the hub code that serves them is ours and should give the operator the means: a licence text and source link per blob. These are
    facts about the text; the owner decides the posture.
22. **The same duty already exists for the 111 release the F6 origin serves** and Layer 7's spec does not mention it (grep of `7-relay/README.md` for "Corresponding",
    "source offer", "GPL": no §9 hit). `LICENSING.md:218-221` requires the Corresponding Source "from the same place as the binaries" for every conveyed binary of ours
    (GPL-3.0 §6(d), `git archive` beside each release). A hub that serves `blob/<payload>` conveys a GPL-3.0 binary (it bundles `meshmud` and the Meshtastic web
    client, both GPL); the clean fix is one more pinned blob (the release's source tarball) with a pointer in the origin's directory page. Cost: the tarball's size on
    disk (unmeasured).

### 3.5 Candidate verdicts with the Pi floor (d)

23. Only static output passes "weight nothing while off": the pinned-blob directory, `termux-apt-repo`/`aptly`/`reprepro` output, `fdroidserver` output, `dumb-pypi` output. Resident
    servers (`apt-cacher-ng`, `devpi`, `pypiserver`, bandersnatch on a timer) are rejected: a listener or a periodic job in the required configuration needs the owner's say
    (`AGENTS.md`, Pi floor). Tools that build repos run on the **publisher** (the owner's computer or a hub with Python), never as a node dependency.
24. `bandersnatch` is AFL-3.0 with a Python >=3.12 floor; it mirrors whole indexes or allow-lists. For six pinned wheels it brings a runner, a config and the version floor for
    no gain over the files table (§3.2 item 6).

### 3.6 Layer 9 interplay (joint contract)

25. Layer 9's hub "fix shelf" (`9-evolution/research/03-share-fixes-pr.md:134`, C2) "needs a Layer 8 style store and a fetch verb; v1.1", and its critic notes the hub origin
    "serves only release manifests and pinned blobs" (`06-critic.md` conflict 9). One admission rule serves all of them: **`GET /origin/v1/blob/{sha256}` answers if the hash
    is in a pin list the hub holds**; pin sources are the release manifest, embedded component declarations, and later a hub-owner-signed fix index. Components, debs, APKs,
    the source tarball and fixes then share one verb, one Range handler and one place on disk (a `blobs/` directory under `state/origin/`), as `01-datasets-hub.md:15-17` wants.

**Pick: option 1.** Reasons: it is the Layer 7 mechanism with one admission rule, no resident weight, no tool, no key, and it closes the three demands that exist (hub-to-hub

a capability the pins lack. Option 3 is honest and free but leaves README §8 half-true and the first offline hub with no route for the 104 MB it needs.

## 5. Recommendation

Take option 1 as a v1 task list: (1) the admission rule over pin sources; (2) a files table for pip closures from `gen_lock.py`; (3) an origin list in the installer's
`PayloadFetcher`; (4) `origin.components`, off by default, with a per-blob licence text and source link and one acknowledgement at the switch; (5) the 111 release's
source tarball as a pinned blob (item 22). Defer the apt directory and the APK catalogue to v1.1 with `termux-apt-repo` and the entry.jar shape as the references. The
D26 (5) text gets one sentence: when a hub is the source, the hub's operator is the one who conveys, and the member's acknowledgement records the member's own install only.

## 6. Open questions (owner or lead)

1. May an owner's hub convey third-party binaries to other people's nodes at all (critic fork 15), or only to the same owner's devices? The licence text does not decide it.
2. Is `origin.components` a second switch or part of `origin.serve`? (A second switch lets an operator serve the 111 release but not other people's programs.)
3. Does the Reticulum pending contact (`LICENSING.md` item 16) cover a hub serving the wheels, or only the helper?
4. The 111 release source tarball as a served blob: size and who builds it (release checklist step 5).
5. Who measures the Termux closure (the debs 111 pins, kiwix-tools' dependencies) and the APK sizes? Both wait for the first release manifest and a readable packages.termux.dev.
6. Does a hub keep a component blob after the operator disables the component and removes `cache/packages/<id>/` ("only a separate call deletes it", `1-bootstrap/README.md:241`)? Proposal: serving ends with the file.
