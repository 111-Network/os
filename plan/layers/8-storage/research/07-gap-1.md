# Layer 8 gap-fill G1: how the agent's state can be encrypted without breaking D26, L2 custody or the Pi floor

Scout: sonnet, code and spec read only, 2026-11-02. Nothing run, nothing written but this file. Prefixes: `A/` = `3-intelligence/crates/agent111/src/`, `N/` = `1-bootstrap/crates/node111/src/daemon/`, `M/` = `5-messaging/crates/mesh111/src/`. Figures marked "derived" are arithmetic from cited facts; "unmeasured" means no figure exists in the repo.

## 1. Summary

- **No mechanism breaks all three rules less than "111d is the only writer of the encrypted copy".** The agent never needs the key, a write route or a SQLCipher link if 111d persists what the agent already hands it in-band (chat) or announces (proposals, tasks). The two sweep picks each break a rule; this option breaks none.
- **Today history comes from the agent's files.** `GET /api/v1/chat/history` is a pure relay (`N/dashboard/api_v1/relay.rs:679-697`) to the agent, which reads `conversations/<id>.jsonl` (`A/chat.rs:385-405`, `A/store.rs:110-118`). 111d already sees every reply (`done` frame, `relay.rs:538-560`) and reacts to `proposal.written` / `task.done` (`relay.rs:797-835`): the hooks M1 and M2 need exist.
- **Chat can move wholesale (M1); proposals and tasks need the ingest path (M2).** M1 alone leaves proposals plaintext; M2 alone leaves conversations plaintext. The pair covers every file the L3 contract names (`3-intelligence/README.md:50`) except `events.jsonl`, logs and `work/`.
- **"Zero key material" is policy, not an OS boundary.** The agent is a child of 111d with no uid change (`N/supervise.rs:529`, `111node.service:24`), so it can already read `identity/keyset` (`1-bootstrap/README.md:103`). Agent-state encryption protects copies and backups, not a compromised agent.
- **M3 reverses an owner decision** (D26 (2): "No bearer exception at all", `plan/DECISIONS.md:383-`); **M4 breaks two rules** (L2 custody text and the Pi floor: +5.4 / +6.4 MB binary). **M5 is the zero-weight fallback** and needs only L3 text.
- **Pick: M1 + M2 into a 111d-owned second SQLCipher file** (new KDF tag, no new dependency, nothing added to the agent). Fallback if the owner will not accept the agent protocol edits: M5.

## 3. Findings with file:line

1. **Chat persistence is end-of-turn and agent-side.** The conversation is loaded in full each turn (`A/chat.rs:197-201`), new messages (user, tool calls, tool results, reply) are appended after the reply (`:276-280`). Trimming for long histories is "deferred" (`3-intelligence/TASKS.md:72`), so the files are unbounded (`A/store.rs:2`).
2. **111d's chat relay is a re-serializing proxy.** It parses the body (`relay.rs:296-304`), forwards `serde_json::to_vec(&req)` (`:616-627`) and translates `delta`, `tool_call`, `done` frames (`:536-560`). M1 adds `history` to the forwarded body and a `messages` array to the upstream `done` frame, stripped before the browser sees it. Both are additive to the agent contract (TASKS.md:27) and invisible to `openapi.yaml`.
3. **M1 needs one relay fix.** `chat_stream` drops the upstream connection when the browser leaves (`relay.rs:585-612`). Today the agent still finishes and appends; under M1 a closed browser tab would lose the turn unless the relay keeps draining until `done` (unverified how `emit` behaves with a closed client, `A/chat.rs:312`). Make "persist on `done`, even with no browser" an M1 acceptance test.
4. **Tool rows are optional for the UI.** The contract says the UI hides `role=tool` and null-content assistant rows (`openapi.yaml:717`), so a text-only record (user and reply) would pass the UI but would drop tool results from later model context. Store the full OpenAI messages (M1b) to keep behaviour identical.
5. **The proposal reader is the single decoder, and it already tolerates damage.** `proposals.rs:4-19` treats files as untrusted, skips unparsable ones and size-caps at 1 MiB (`:122`); `proposals.rs:133-134` fixes the directory. Moving the source to a DB removes the "two decoders" risk named in `00-code-seams.md` section 5 (e).
6. **The ingest trigger exists but is not enough.** `on_agent_frame` calls `proposals::summary` on `proposal.written` / `task.done`, only for events fresher than the subscriber start (`relay.rs:824-835`, `is_fresh`). M2 therefore needs a startup sweep for backlog, and must tolerate a half-written file (`std::fs::write` is not atomic: `A/store.rs:139,145`). Making the agent write temp+rename costs three lines and is worth doing under every option.
7. **The agent reads tasks back.** `orphan_running` marks tasks left `running` as `failed` at start (`A/tasks.rs:251-263`). Under M2 the running marker must stay readable by the agent (keep `tasks/` as a spool of running tasks only) or the sweep moves to 111d. Flag this in the build board.
8. **A wiped journal is already tolerated.** 111d resyncs when the agent's event journal restarts (`relay.rs:743-749`). So `events.jsonl` can stay a plaintext 1 MiB FIFO (`A/events.rs:3,19-21`; capacity-bounded already, contains kinds, ids and proposal titles) without harming any mechanism. Recommend: out of scope, stated in the spec.
9. **Outside every mechanism, state it.** `agent/work/<task>` (opencode files, gathered context JSON; `A/tasks.rs:360,397`) and the uncapped `agent/*.log` (`N/intelligence.rs:274-280`); whether llama-server logs prompts is unverified.
10. **The key cannot be hidden from the agent's uid.** Agent and daemon share a uid (`supervise.rs:529` shows only a `pre_exec` death signal; no setuid), so the L2 rule (`2-identity/README.md:224`) is enforced by what code holds the key, not by the OS. M4 hands the agent a store-scoped subkey (not seed, not signing key, not the X25519 scalar); it is still key material and still an amendment.
11. **D26 is a one-line invariant on purpose.** `bearer_write_refused` is a pure function of method and headers (`auth.rs:931-933`), checked first in `require_session` (`:31-37`), and a test fails if any non-GET leaves the agent (`3-intelligence/README.md:121-122`). A scoped write token turns that into an allowlist, which is exactly what D26 (2) declined.
12. **Separate file beats V5 tables for this data.** `SchemaTooNew` after a probation rollback keeps the fabric down (`04-local-store.md` finding 12); agent state in the same file would go with it. A separate file also avoids queueing behind Layer 7's V4 migration and needs no `Class` change in the prune order (`M/store/rows.rs:32-46`). Cost: a small helper that exposes the key-and-pragma open (`M/store/mod.rs:396-456` is private to the fabric store) and a known-answer vector for the new tag (`5-messaging/test-vectors/store-kdf.json` is the model).
13. **Wear is dominated elsewhere.** The idle per-minute `settings` write is 5.9 MB/day (`04-local-store.md` finding 7); a 100-turn day under M1 adds about 2.5 MB (derived).
14. **Pruning needs no wall clock** where a DB exists: `local_seq` distance is the store's age (`M/store/prune.rs:209-212`). M5 cannot, since file ids embed `SystemTime` nanos (`A/store.rs:164-171`).

## 4. Recommendation

Options:

- **A. M1 + M2 into `agent/state.db` (111d sole opener).** Trade-off: touches three places (agent chat body/frame, 111d relay, proposals reader) but no locked rule, no dependency, no new resident cost; leaves a short plaintext spool window for proposals and tasks. Locked text changed: L3 line 50 and the TASKS contract lines only.
- **B. M5, plaintext with atomic writes, caps and an L3 text amendment.** Trade-off: zero weight, a day of work, honest; but the L3 promise and README §8 ("encrypted local store") are not met for agent state, and message text stays in proposals (`kind: message` bodies, `N/fabric/proposal.rs:1-20`).
- **C. M3 scoped state token.** Trade-off: the smallest agent edit (the `Store` module becomes a loopback client; `ureq` is already a dependency, `Cargo.toml:21`) but it reverses D26 (2) and adds an allowlist where there is a one-line invariant.
- **D. M4 key to the agent.** Trade-off: simplest data path, no 111d changes; costs +5.4 / +6.4 MB, a C toolchain in the agent, an L2 custody amendment and a Pi-floor decision. Not recommended.

**Pick A.** Two refinements that cost nothing: write proposals and tasks via temp+rename in the agent (finding 6), and keep `events.jsonl`, `work/` and logs outside the claim (findings 8-9). **If the owner declines A, fall back to B**, not C or D, because B needs no rule change beyond L3 wording.

Spec wording under A: conversations, proposals, tasks and decisions are encrypted at rest in 111d's store; a proposal is plaintext on flash for a short window and its deleted file may leave flash remnants; encryption protects copies and backups, not a compromised agent (same uid).
