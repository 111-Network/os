## 1. Summary

- **G3 verdict: use the in-lock `bao-tree` outboard as the dataset sidecar, one file beside the blob, built once by the importing hub; Metalink stays an operator-side import aid, never a node dependency.**
  The blob's BLAKE3 root (32 B, in the signed catalogue entry) authenticates the 217 KB sidecar by itself, so the catalogue needs no separate sidecar hash,
  and the same root already serves Tier 2 (L5 §11). Cost: zero new crates (`bao-tree 0.16.1` and `blake3 1.8.7` are linked in `111` already, `1-bootstrap/Cargo.lock:101-104`).
- **The critic's figure checks out, off by one.** A 16 MiB block is `BlockSize::from_chunk_log(14)` (`BT/tree.rs:144`, `BT/tree.rs:159`). A 57 GB (57e9 B) file has 3,398 blocks and **3,397 hash pairs = 217,408 B**
  (formula `(blocks-1)*64`, `BT/lib.rs:504-513`); the critic wrote 3,396 x 64. 57 GiB gives 3,648 blocks and 233,408 B.
- **A resumed Range pull gets per-block verification against the root**, using calls that exist in 0.16.1: authenticate the outboard (`valid_outboard_ranges`), then check each downloaded 16 MiB block
  (`valid_ranges` on that block's `ChunkRanges`), re-fetch only blocks that fail. The bad-block cost is 16 MiB, as in 02's sha256 design. Two traps: L5's blob writer would emit a 3.56 GB `ob1k` for a 57 GB file (section 3, finding 8), and a 16 MiB block means a 16 MiB buffer per active call (finding 9).
- **G4 verdict: none of the three prior-art stacks publishes a kiwix-serve RSS.** The only primary-source figure is IIAB's "kiwix-serve needs >= 1024MB on Zero 2 W" with a 1,536 MB swap file (`IIAB/vars/default_vars.yml:259-260`):
  a RAM-plus-swap need on a 512 MB board, not an RSS. Conflict 7's RSS pair (128-256 MB vs "under 50 MB") stays **unresolved by published data**; a measurement is the only way to settle it (section 5 gives the method).
- **Mini ZIM size (conflict 7, second half): both numbers are dated, the 7.4 GB one fits Kiwix's own "about 95% smaller" statement, the 13 GB one does not** (section 4, finding 4). The spec should never hard-code a ZIM size; the signed catalogue entry carries `size`.
- **IIAB ships maps as plain PMTiles files behind stock nginx, on a Pi Zero 2 W class box**, with a 312 MB default (85 MB vector + 85 MB satellite + 35 MB search + base), and flags satellite imagery as CC BY-NC-SA. It prints the OSM data credit on a credits page that does **not** name the ODbL (section 4, finding 9).
- **Resident-cost fact for the Pi floor:** kiwix-serve's main thread wakes every 1000 ms for as long as it runs (`kiwix-tools/src/server/kiwix-serve.cpp:423,451`), `--monitorLibrary` adds a per-second file-timestamp stat (`:454`).
  Fine for an on-demand component; it means an idle detector cannot assume a quiet process, and `SIGHUP` (`docs/kiwix-serve.rst:107-109`) is the no-timer way to reload the library.

## 3. Findings: G3, bao-tree from source

1. **`BlockSize` is a log, not a byte count.** `pub struct BlockSize(pub(crate) u8)` is "the log2 of the size in bytes / 1024: 0 is 1024 bytes, 1 is 2048" (`BT/tree.rs:126-132`); `from_chunk_log(n)` (`:144`),
   `bytes() = 1024 << n` (`:159`), `from_bytes` accepts only powers of two >= 1024 (`:164-174`). So 16 MiB = `from_chunk_log(14)`; `BlockSize(14)` is not constructible outside the crate, use `from_chunk_log` (as `M/blobs.rs:100-105` does).
   0.16.1 has no upper bound (`u8`); **0.17.0 caps it at 64 MiB = `BlockSize::MAX`** and panics above (`CHANGELOG.md`, "Breaking Changes", #96). 16 MiB is inside both.
2. **Outboard size = `(blocks - 1) * 64` bytes, no size prefix.** `blocks = ceil(size / (1024 << n))`, min 1 (`BT/lib.rs:493-496,601-608`); `outboard_hash_pairs = blocks - 1` (`:504-506`); `outboard_size = pairs * 64` (`:511-513`),
   "without the size prefix". 64 B per pair = two 32 B child hashes. Computed by script from those formulas (nothing run in the repo):

   | file | 1 KiB groups (L5 `ob1k`) | 16 KiB (L5 `ob16k`) | 1 MiB | 4 MiB | **16 MiB** | 64 MiB |
   |---|---|---|---|---|---|---|
   | 7.4e9 B (mini, Nov 2024) | 462,499,968 B | 28,906,240 B | 451,648 B | 112,896 B | **28,224 B (442 blocks)** | 7,040 B |
   | 13e9 B (mini, Mar 2024) | 812,499,968 B | 50,781,248 B | 793,408 B | 198,336 B | **49,536 B (775 blocks)** | 12,352 B |
   | 57e9 B (nopic) | 3,562,499,968 B | 222,656,192 B | 3,478,976 B | 869,696 B | **217,408 B (3,398 blocks)** | 54,336 B |
   | 111e9 B (maxi) | 6,937,499,968 B | 433,593,728 B | 6,774,848 B | 1,693,696 B | **423,424 B (6,617 blocks)** | 105,856 B |

   Versus 02's 32 B-per-chunk sha256 list (108.7 KB for 57 GB): the outboard is 2x bigger because it stores internal nodes (both children per parent); it buys a root and sub-block verification.
3. **A sidecar outboard file on disk is the normal, already-used shape.** `PostOrderOutboard<D>{root, tree, data}` and `PreOrderOutboard<D>` are public generic structs (`BT/io/outboard.rs:104-111,129-136`); with `D = File` they implement `Outboard` through `ReadAt`
   (`BT/io/sync.rs:135-153` pre-order, `:239-258` post-order). `outboard_post_order(data: impl Read, tree, out: impl Write) -> Hash` streams the data once, writes sequentially, returns the root and does not write the size (`BT/io/sync.rs:700-713`);
   the size is the data length. L5 already does exactly this for `ob1k`/`ob16k` and reloads with `PostOrderOutboard{root, tree, data: File}` after checking `len == tree.outboard_size()` (`M/blobs.rs:452-466,536-556`). `PostOrderMemOutboard::create` (`BT/io/outboard.rs:183`) is the in-memory variant: wrong for 57 GB.
   Post-order is the right order for a file that is written once and read in pieces (the crate doc: "Post order outboard formats have advantages for synchronizing append only files", `README.md`).
4. **Range-set support exists, in two modes.** `ChunkRanges = RangeSet2<ChunkNum>` (`BT/lib.rs:232`), `ByteRanges = RangeSet2<u64>` (`:235`), `round_up_to_chunks` (`BT/io/mod.rs:135`) and `round_up_to_chunks_groups(ranges, block_size)` (`:155`) turn byte ranges into group-aligned chunk ranges.
   Mode A (slice transfer, Tier 2): `encode_ranges(_validated)` (`BT/io/sync.rs:420,457`) writes parents plus data; `decode_ranges(encoded, ranges, target: WriteAt, outboard: OutboardMut+Outboard)` verifies against the root and saves the parents it learns (`:567-625`).
   The crate's own example decodes into an empty `PreOrderOutboard{data: vec![]}` and then calls `valid_ranges(&ob, &decoded, &ChunkRanges::all())` to list what is verified (`BT/lib.rs:72-123`). Mode B (full outboard held locally, bytes from anywhere):
   `valid_outboard_ranges(outboard, ranges)` (`BT/io/sync.rs:979`) validates the outboard alone against the root; `valid_ranges(outboard, data: ReadAt, ranges)` (`:813`) re-hashes the data and yields the sub-ranges that match; holes and zeros are simply not yielded
   (the 0.17 changelog adds "data past the end of the file is invalid instead of failing", #98). Both are behind the `validate` feature, a default feature (`bao-tree` `Cargo.toml` `[features] default`), and `M/Cargo.toml:20` takes the default set.
5. **What a resumed HTTP Range pull gets (Mode B).** Plain HTTP Range returns raw file bytes, not bao slices, so the client needs the whole sidecar first. Flow, all on 0.16.1 APIs:
   (1) fetch the 217 KB sidecar from the hub (a static file next to the blob); (2) `valid_outboard_ranges(.., all)` against the catalogue's BLAKE3 root: a corrupt or swapped sidecar fails here, before any dataset byte moves;
   (3) request `Range: bytes=i*B-(j*B-1)` aligned to block boundaries (`B` = 16 MiB), write into the `.part` file; (4) `valid_ranges(&ob, &part, &ChunkRanges::from(block_i..block_j))` per block (or per run of blocks): a mismatch re-fetches that block only; (5) at the end the file root is already proven, because every leaf is under the pinned root (no second whole-file pass; an upstream sha256 is a cross-check the importer ran, not a node duty).
   **Resume** after a crash: keep a block bitmap next to `.part` and re-verify only the block(s) in flight; a full `valid_ranges(.., all)` rehashes every byte present (30 GB read = minutes on an SD card; an unmeasured, assumed order, do it only after an unclean shutdown). The bitmap is a hint; the hashes are the proof.
6. **The sidecar needs no hash of its own.** `valid_outboard_ranges` recomputes the tree from the leaf pairs up to the root, so a 32 B root in the catalogue is enough, replacing 02's "catalogue hashes the sha256 list" step. Two hash spaces remain (02 finding 5): the entry carries `blake3` (root) and `sha256` (upstream/sneakernet cross-check, since upstream publishes sha256 only).
   The BLAKE3 root is **the same at every block size** (`M/blobs.rs:688-689` test; `5-messaging/README.md:468-470`), so the sidecar block size is a per-file publisher choice recorded in the catalogue (`ob_log = 14`), and a later Tier 2 `ob16k` or `ob1k` adopts the same file with no re-signing.
7. **What L5 already pins for Tier 2.** `OBJ_ADVERT {hash, size, chunk_group, coding, object_key?}`, `OBJ_REQ {hash, ranges, session_tag}`, `OBJ_CHUNK` = `session_tag || chunk_idx || bao-verified bytes` (`5-messaging/README.md:239`; kinds 0x20-0x22, `:175`). Chunk group **1 KiB on LoRa/BLE (6.25 % outboard), 16 KiB on TCP (0.39 %)**,
   identical root (`:468-470`). v1 builds the store, addressing and outboard computation; v1.1 the wire (`:471-473`). Nothing in L5 mentions 16 MiB, Metalink or a dataset sidecar; the dataset sidecar is therefore a Layer 8 file format, not a conflict with L5, as long as it reuses the L5 root.
8. **Trap: L5's blob writer emits both outboards for every blob.** `write_*_from` loops `for group in ChunkGroup::ALL` (K1, K16) over the written data (`M/blobs.rs:96-98,452-466`). For a 57 GB dataset that is 3.56 GB of `ob1k` plus 222.7 MB of `ob16k` (table above), 6.6 % extra disk and a second and third full read to compute them.
   So datasets must not be ingested through `BlobDir` as it stands. Either keep datasets under their own tree (02's `blob/<sha256>`/`datasets/<id>/`, conflict 6) with one `ob16m` sidecar, or give `BlobDir` a per-ingest group list (an L5 amendment). The lead's call (fork A below).
9. **Trap: block size sets transient buffer size.** The sync encoders allocate `vec![0u8; tree.chunk_group_bytes()]` per call (`BT/io/sync.rs:429,492,659,731`) and the decoder `BytesMut::with_capacity(block_size.bytes())` (`:277,303,614`): **16 MiB per active call at `from_chunk_log(14)`**, 1 MiB at 10. `valid_ranges` reads a group buffer likewise (`:877`). On a 512 MB board that runs kiwix-serve this matters; at 4 MiB (`from_chunk_log(12)`) the sidecar is 869,696 B for 57 GB and a bad block costs 4 MiB.
   Since the block size is per file, ship 16 MiB for files >= 1 GiB, and let a Pi-class hub choose 4 MiB if its measurement says so. Not measured here.
10. **0.16.1 defects that bear on this, and which they do not hit.** 0.17 fixes `encode_ranges` for partial chunk groups ("written without the inner parent pairs the decoder expects", #83) and "stop decoding after the first error instead of verifying further items against unauthenticated hashes" (#84) (`CHANGELOG.md`).
    Mode B (aligned Range pulls, `valid_ranges`) uses neither path with unaligned ranges, so 0.16.1 suffices for the v1 fetcher (inference from reading the call sites, not a test). Mode A / Tier 2 needs 0.17 (already 02's prerequisite). 0.17 also raises the MSRV to 1.85 and changes two `serde` wire formats (`CHANGELOG.md`), neither used by L5's file outboards.
11. **BLAKE3 speed on a Pi is not measured.** blake3 enables its NEON path on `aarch64` by default (`B3/build.rs:367`: `!is_no_neon() && !is_pure() && is_aarch64() && is_little_endian()`); armv7 needs the `neon` feature (`B3/Cargo.toml:47`). The one-time import pass (sha256 + BLAKE3 + outboard in a single `Read`) is bounded by the SD card, not by a figure we have. Record it in `TASKS.md` when hardware exists.
12. **Metalink 4 and aria2, what could be established.** aria2 documents the behaviour we want from a sidecar: with piece hashes it re-downloads damaged parts only; "if both piece hashes and a hash of entire file are provided, only piece hashes are used"; `--piece-length` is "ignored if Metalink file contains piece hashes" (`aria2c.rst:79-90,1560-1565`);
    `--realtime-chunk-checksum` (default true) validates chunks while downloading (`:1637-1640`). That is the same two-level model (per-piece, whole-file) as Mode B. RFC 5854 section numbers (the critic's s4.1.4), the `<pieces length type>` attribute names and piece-hash algorithms are **(unverified)**: the RFC host is denied. Kiwix's mirror stack: offspot's downloader reads per-file digests "meant primarily to be used with MirrorBrain's automatic per-file-per-algorithm endpoints" (`OS/image-creator/README.md:75-76`); whether `download.kiwix.org` serves `.meta4` or piece hashes is **(unverified)**.
    The checksum algorithms that tool accepts are `sha-1, sha-224, sha-384, sha-512, md5, adler32` (`:71`), no sha-256 in the list as documented. Conclusion: Metalink is the HTTP-world twin of the design, useful where an operator pulls the first copy from a mirror with aria2 on a PC; it is not a node dependency (XML parser, second program, no root).

## 4. Findings: G4, prior art on Pi hubs

1. **IIAB, licence and shape.** `LICENSE` is the GPL-2.0 text ("Version 2, June 1991", `IIAB/LICENSE:1-2`). The Kiwix role downloads upstream `kiwix-tools_linux-<arch>.tar.gz` (`IIAB/roles/kiwix/defaults/main.yml`, `kiwix_arch_dict`, `kiwix_tar_gz`) and runs a systemd unit

   No `--monitorLibrary`: the library file is rebuilt by `iiab-make-kiwix-lib` when the role (re)enables the service (`roles/kiwix/tasks/enable-or-disable.yml`). If no `*.zim` exists it installs a `test.zim` (`tasks/install.yml:62-73`): the role itself ships **no Wikipedia**. IIAB's ZIM picker lives in its admin console and wiki (**unfetched**); the "ZIM list they ship on a Pi 4/5 or Zero 2 W" is therefore not established here.
2. **IIAB, nginx for kiwix.** `location ^~ /kiwix` proxies to `127.0.0.1:3000` with `proxy_http_version 1.1`, `Connection ""` and 600 s connect/send/read timeouts (`roles/kiwix/templates/kiwix-nginx.conf.j2`); no Range directive, because libkiwix answers `Range` itself (02 `response.cpp:691-720`, already verified in 02). `README.rst`: use `http://box:3000/kiwix` "to avoid the proxy".

The sentence is RAM-plus-swap sizing for the whole box, not an RSS, and does not say which ZIM.
4. **Conflict 7, mini vs nopic.** Kiwix's FAQ (search snippet): mini = introductions and infobox, "saves about 95% of space vs. the full version"; nopic = full text, no images, "about 75% smaller". Against the dated sizes in 01/05: 7.4 GB / 110 GB = 6.7 % (93 % smaller, consistent with "about 95 %"); 13 GB / 102 GB = 12.7 % (87 %, not consistent). But nopic 57 GB / 110 GB = 52 % (48 % smaller, nowhere near "75 %"), so the FAQ's percentages are stale for nopic and cannot date-calibrate mini.
   Reading: the English mini build was about 13 GB in March 2024 and about 7.4 GB in November 2024 (both secondary, both dated, nothing fetched from `download.kiwix.org`); budget the larger and read `size` from the signed entry at fetch time. This is an inference, not a measurement.
5. **Conflict 7, kiwix-serve RSS.** Published primary numbers: none found (IIAB, offspot, kiwix-tools README/man page). Search snippets: a self-hosting guide says RSS "stays low (256-512 MB)" and that reported memory is largely memory-mapped ZIM pages; forum posts claim "less than 50 MB" and a 130 GB dump on a 512 MB Zero 2; Kiwix's site says it runs on a Pi Zero with no figure.
   01's 128-256 MB and 05's "under 50 MB" are the same genre. **No source separates anonymous RSS from file-backed (mmap) RSS**, which is the distinction that matters for the Pi floor (file pages are reclaimable). IIAB's >= 1024 MB RAM+swap on a 512 MB board is the only hard hint that the whole box needed more than 512 MB; it is not an RSS.
6. **kiwix-serve flags and idle cost (source: `kiwix-tools/main/src/server/kiwix-serve.cpp`, raw, fetched).** `DEFAULT_THREADS 4` (`:44`, option text `:77`; man page `docs/kiwix-serve.rst:128-130`); `--ipConnectionLimit` default 0 = unlimited, "recommended >= 6" (`:82`); `--catalogOnly` (`:66`); `--blockexternal` (`:73`);
   `--monitorLibrary` "Monitor the library file and reload it automatically" (`:70`; man page `:103-105`), implemented inside the endless loop that sleeps `kiwix::sleep(1000)` each pass and, with `-M`, calls `newestFileTimestamp(libraryPaths)` every pass (`:423-466`, `:451-454`). The 1 Hz wake is unconditional (also without `-M`); the loop also polls the parent PID when one is set (`:424-437`).
   `SIGHUP` forces a library reload regardless of `-M` (man page `:107-109`). Threads: each worker has its own stack; the thread count is the only documented knob. A Pi-floor launch line: `kiwix-serve --library <file> --threads 2 --nolibrarybutton --port <p>` (bind-address option not re-checked), reload by `SIGHUP`, never `-M`. The thread count that is enough for one LAN is **unmeasured**.
7. **offspot / Kiwix Hotspot.** Hardware: "Raspberry Pi `3B` (802.11n only), `3B+`, `4B`, `400`, `5` and `500`. Those are arm64 devices with 1GB+ RAM" (`OS/overview/README.md`, "Hardware Support"). The builder's own example adds one small topical ZIM, `openZIM:wikipedia_en_climate_change:nopic` (`OS/overview/docs/Kiwix Hotspot Tutorial.md:49,120`); the full-Wikipedia flavours are not named in the fetched files.

Licence: every offspot repo fetched is GPL-3.0 (badges, e.g. `OS/offspot-config/README.md:6`); `kiwix-tools` is "GPLv3 or later" (`kiwix-tools/README.md:148-151`). 8. **IIAB maps: PMTiles served as static files.** Everything is `.pmtiles` named `<data_key>.<date>.<zoom_range>.pmtiles`, e.g. `openstreetmap-openmaptiles.2026-07-01.z00-z14.pmtiles` (`IIAB/roles/maps/FORMAT.md`); the catalogue is a JSON map of keys to URLs **with no hash field** (`roles/maps/maps-catalog.json`, grep for sha/md5/hash: none).

Sizes (README:23-58 and tables): ~170 MB (85 vector nat-z8 + 85 satellite z7); ~9.5 GB (8.3 vector z11 + 1.2 satellite z9); ~160 GB (80 + 80 at z14/z12); terrain ~980 MB / 6.4 / 29 / 106 GB; static search ~35 MB for 165,623 cities (pop >= 1000); Nominatim "basic" ~640 MB and "full" ~67 GB, **"not recommended for very low-power devices such as Raspberry Pi Zero 2 W"** (README:132).

9. **IIAB maps: Range, resume, licences.** nginx serves the maps tree as a plain static `root /library/www`; for `.pmtiles` it sets `chunked_transfer_encoding off; gzip off`, a workaround "to get around a bug in serving pmtiles.
