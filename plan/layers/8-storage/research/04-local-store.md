# Layer 8 research, lens 4: the encrypted local store, capacity pruning, budgets, backup, SD wear

Scout: sonnet, 2026-11-02. Prefixes as in `00-code-seams.md`: `M/` = `5-messaging/crates/mesh111/src/`, `N/` = `1-bootstrap/crates/node111/src/daemon/`, `A/` = `3-intelligence/crates/agent111/src/`. Web method: `raw.githubusercontent.com`, crates.io, WebSearch. `sqlite.org`, `zetetic.net`, `docs.rs` and `source.android.com` could not be fetched; those claims carry "(search snippet)" or "(unverified)".

## 1. Summary

- **"The encrypted local store" is one SQLCipher file today, and the L3 promise is not true as built.** `fabric/store.db` is encrypted; agent state (conversations, proposals, tasks, logs), display times, the Delta Chat core's DB, `rns/`, `state/*.json` and `identity/` are plaintext behind 0600/0700 ownership. Proposals of kind `message` hold the outbound message text in plaintext until deleted (`A/store.rs:120-134`).
- **Pick: widen the store by routing, not by adding engines.** Agent state moves into a second SQLCipher file opened only by 111d (new KDF tag, no new dependency, `agent111` stays dependency-free and reaches it over its existing bearer loopback channel). Foreign databases stay as they are (Delta Chat itself marked DB encryption deprecated). Datasets stay plaintext. No fscrypt or age is added to the required configuration.
- **The store key is recoverable from the 12/24 words; the contents are not.** `store_key` derives from the X25519 half of the keyset (`N/fabric/sealer.rs:126-138`, `M/keys.rs:101-114`), so a copied DB reopens after a words-only restore. A words-only restore on a blank disk loses all history, contacts, queued outbox and custody. The missing half is a store export. L2 section 8.5(i) specifies one in its own format; L5 section 21 says "age". These two disagree and must be reconciled.
- **Capacity pruning is built for messaging only.** A fixed 512 MiB watermark with no daemon setter, an export-before-prune that never runs, and nothing measuring `agent/`, `bridge/`, `rns/` or logs. Layer 8 adds a node-level budget that reports per class and prunes only safe classes; datasets are removed by the user or a consented proposal, never automatically.
- **SD wear: the one idle write is the only structural cost found.** The 60 s capacity pass commits `settings` every minute: derived 5.9 MB/day (2.2 GB/year) of logical WAL writes, removable by writing on change. No published SQLite-on-SD amplification figure was found; the report gives labeled arithmetic and a measurement to run on a Pi.
- **Rollback hazard:** a probation rollback (N to N-1) after N migrated the store leaves N-1 refusing the newer `user_version` (`SchemaTooNew`), and there is no pre-migration copy. The fabric boots to `Err`, not a crash. Take a pre-migration snapshot before any `MIGRATIONS` append (V4 by Layer 7, V5+ by Layer 8).

## 3. Findings that change the plan

1. **What is encrypted, what is not (as built).** Encrypted: `fabric/store.db` only (`M/store/mod.rs:396-456`). Plaintext: `agent/{conversations,proposals,tasks,decisions}` and `events.jsonl` (`A/store.rs:49-146`; `N/dashboard/api_v1/proposals.rs:13-16`), `agent/*.log` (`N/intelligence.rs:274-280`), `fabric/display-times*` (`N/fabric/times.rs:7-8`), `fabric/announce`, `fabric/settings`, `bridge/deltachat/accounts` (`N/bridge/deltachat.rs:1935`), `rns/`, `state/*.json`, `identity/mnemonic` and `keyset`. L7 adds `secrets/link-key` 0600 (`7-relay/README.md:236`), also plaintext.
2. **The mnemonic file is the key to the key.** `identity/mnemonic` is 0600 plaintext (`2-identity/README.md:294`) and `store_key` derives from the keyset, so the ownership boundary protects the store from a different user and from a copied DB, not from a stolen disk. L5 states this (`5-messaging/README.md` 10.2). Every encryption option below inherits the same residual; none of them fixes it without a user-held secret, which the "no policy, 100% freedom" posture and silent install exclude. Mode T (TPM) is the only real hardening and answers `Unsupported` today (`M/keys.rs:12-14`).
3. **Agent state.** Conversations are append-only and unbounded (`A/store.rs:2` leaves pruning to Layer 8). Proposals and tasks use `std::fs::write` with no temp file, rename or fsync (`A/store.rs:120-146`), so a crash can leave half a JSON that 111d must treat as untrusted (`proposals.rs:4-19`). A `kind: message` proposal carries the message body in plaintext (`N/fabric/proposal.rs:17-22`).
4. **Child logs are unbounded.** `open_log` opens `agent/111-agent.log` and `llama-server.log` with `create + append` and no cap or rotation (`N/supervise.rs:752-767`). The 111d journald namespace is capped (`SystemMaxUse=100M`, `1-bootstrap/systemd/journald.111node.conf:6`), the child files are not. Whether the journal lands on disk or in RAM depends on the distro default (unverified).
5. **Store pragmas as built** (`M/store/mod.rs:427-440`): WAL, `synchronous = NORMAL`, `FULL` for sequence allocation, epochs, clean record, receipts and migrations; `auto_vacuum = INCREMENTAL`; `secure_delete = ON`; `temp_store = MEMORY`. **Not set:** `wal_autocheckpoint`, `journal_size_limit`, `cache_size`, `mmap_size` (grep over `M/store`). So SQLite's compiled default applies: automatic checkpoint at 1000 pages (`sqlite3_wal_autocheckpoint(db,1000)` in `src/sqlite.h.in` on the SQLite master mirror, which also says the default is re-enabled by that call). The WAL file is not truncated after an auto-checkpoint unless `journal_size_limit` is set; Delta Chat's `housekeeping` comment says so and the SQLite source agrees (`wal.c`: truncation on reset only when `mxWalSize >= 0`). The store truncates only at clean close (`PRAGMA wal_checkpoint(TRUNCATE)`, `M/store/mod.rs:347-348`).
6. **WAL durability facts** (search snippet of the SQLite docs; `sqlite.org` denied): with `synchronous=NORMAL` in WAL mode the WAL is synced before each checkpoint, a committed transaction can roll back after power loss while the DB stays consistent, and NORMAL is the WAL default. One `FULL` transaction fsyncs the WAL and makes earlier commits durable. `Durability::Full` already uses this for sequence numbers and custody receipts; routine bookkeeping can lose its last commits on power loss.
7. **The idle write.** `save_capacity` sets `store_full`, the full-class mask, `disk_free` and `disk_total` on every 60 s pass (`M/store/prune.rs:866-888`, called from the pass at `:645`). Derived cost: one 4096-byte page plus 24 bytes of WAL frame header per commit, one frame if only the `settings` leaf changes: 4120 B x 1440/day = **5.9 MB/day, 2.2 GB/year of logical WAL writes**; at 1000 frames the auto-checkpoint copies each distinct page once, so the main-file write is a few KB per 16.7 h. This excludes filesystem journal and SD-controller amplification, which no source quantifies. The fix (write only on change, or only when a value crosses a threshold) is an L5 edit of one function. Measure with `/proc/<111d>/io` `write_bytes` over an idle hour on a Pi.
8. **Per-message cost.** Each received sequenced item is a `FULL` commit (`M/store/rx.rs:688-699`): roughly 3 to 6 WAL frames (12 to 25 KB, derived) and one WAL fsync. Delivery-first outweighs wear; do not weaken it. Blob writes are heavier (`sync_all` plus two directory fsyncs, `M/blobs.rs:444,466-488`), which is one more reason datasets must not pass through `fabric/blobs` (finding 11).
9. **`secure_delete = ON` costs writes** (freed pages rewritten; `incremental_vacuum` with no argument frees the whole freelist at once, `M/store/prune.rs:786`). Keep it; state the cost.
10. **Integrity tooling already exists in the engine.** SQLCipher has `PRAGMA cipher_integrity_check` (verifies page HMACs; `src/sqlcipher.c:3442`) next to SQLite's `quick_check` / `integrity_check`. Neither runs anywhere in the tree (grep `integrity_check|quick_check` over `M/` finds nothing). A wrong key is detected on page 1 only (`M/store/mod.rs:407-425`), so mid-file corruption surfaces as a read error at use time. The update guard's torn-payload pattern is a startup hash check of the current release with a flip to N-1 (`1-bootstrap/crates/node111/src/update_guard.rs:57-80`); the store analogue is a startup `quick_check` gate that, on failure, quarantines the file and boots from the last snapshot (finding 12), never silently re-creates (L2 "never silent re-key" posture).
11. **Where datasets must not live.** Blob files count as live bytes against the fabric watermark (`M/store/prune.rs:468-481`) and public blobs are plaintext by design (`M/blobs.rs:4-6`). Datasets are public, signed and large; encrypting them at rest buys nothing (they are published to anyone who asks, and a hub serves them over HTTP). **Datasets are plaintext on purpose**; their protection is signature verification. They need their own tree and ledger (lens 0 pick A).
12. **Migration and rollback.** `migrate()` runs each `MIGRATIONS` entry in its own `FULL` transaction (`M/store/schema.rs:311-347`). A newer `user_version` is refused (`StoreError::SchemaTooNew`, `M/store/mod.rs:87-88`) and `boot_with` returns `Err`, so the fabric stays down (`N/fabric/mod.rs:372-378,461`). Probation reverts the binary only (`update_guard.rs`). So: N migrates V3 to V4, fails probation, N-1 boots, sees `user_version 4`, and messaging is offline until a newer binary returns. Mitigation is one file copy: before any migration, `wal_checkpoint(TRUNCATE)` and copy `store.db` to `store.db.pre-v<N>` (same key, same owner), delete it after probation confirms. Syncthing keeps the old DB after migrating for the same reason (`db_open.go`).
13. **Restore from words: what returns, what is lost.** Returns: identity, the store key, and the ability to open any copied `store.db` (`M/keys.rs:9-11`). A words-only restore onto a blank disk loses everything in `store.db`: contacts (and the enrolled home hub, rebuilt only from the store), history, outbox and undelivered items, `tx_state`/`rx_state` (a new epoch is minted, L2 A3), custody rows (members' mail the hub holds), cursors and blobs. Peers re-appear by announce and INTRO; history comes back only from an export (`2-identity/README.md` 8.4-8.5).
14. **Two export formats are specified.** L2 8.5(i): `version(1) || ephemeral_pk(32) || ciphertext || node_sig(64)`, encrypted to the node's own X25519 key, signature verified before decryption, hub-storable, never public. L5 section 21 and the KB `age` entry: an "`age` recipient-mode export", reserved. Only one should exist. L2's is signed, needs no new dependency and is already specified; age is a standard format other tools open, but its default tree (`hpke`, `ml-kem`, `p256`, `scrypt`, `i18n-embed`) is build weight the owner has not accepted and an age file carries no sender signature (KB `age`). Whether the `age` crate builds an X25519 identity from raw scalar bytes (bech32 is its documented path) is unverified.
15. **Snapshot mechanics under SQLCipher.** Zetetic staff say the backup API works encrypted to encrypted; the shell `.backup` does not. `VACUUM INTO` is reported to keep the source's encryption parameters ("apparently"); `sqlcipher_export()` into an attached encrypted DB is the documented route but drops `user_version` and `auto_vacuum` (all search snippets). The cheapest verifiable route: `wal_checkpoint(TRUNCATE)`, copy the single file under the write lock, open the copy with the same key, run `quick_check`. Every route needs that acceptance test.
16. **Prior art converges.** Signal Desktop: raw key, WAL, `synchronous = FULL`, `cipher_migrate` at open (`Server.node.ts:925-989`). Delta Chat: WAL, `NORMAL`, `auto_vacuum = INCREMENTAL`, periodic `housekeeping` (checkpoint, incremental vacuum) and its own time-based prunes (2-day tombstones, 90-day reactions), which are its policy inside the bridge, not ours (`src/sql.rs`). Briar: one DB, random key, password-wrapped. Syncthing: WAL, incremental vacuum, periodic `VACUUM; PRAGMA optimize; wal_checkpoint(truncate)` (`basedb.go`). None uses a second encryption engine for a second store. Our store matches the strongest of them; the gaps are scope, capacity and backup, not the engine.
17. **The Pi floor.** A second SQLCipher file adds no binary weight and no resident process (111d links SQLCipher already), only one more open connection and page cache while 111d runs. SQLCipher inside `agent111` would add a second vendored OpenSSL (the +5 to 6 MB measured for 111, `5-messaging/README.md` 10.1) and break the agent's "No new deps" rule (`3-intelligence/TASKS.md`).
18. **UI and API gaps** are mapped in `00-code-seams.md` findings 24-25: no filesystem free/total, no per-class bytes, no settable budget. The consent shape for a large or destructive action is `409 consent_required` (`N/components/mod.rs:13-15`).

## 4. Recommendation: forks and picks

### Fork 1. What goes into the "encrypted local store"

Four options: **A** fabric only (today); **B** fabric plus agent state in a second 111d-owned SQLCipher file, the rest by ownership; **C** B plus fscrypt/FBE as documented hardening; **D** everything in `store.db` as V5 tables. Datasets stay plaintext in all four; Delta Chat's DB stays plaintext in A, B, D.

- **A**: simplest, but L3's promise stays false; message text sits unencrypted in proposals.
- **B (pick)**: new tag `111/agent-state/v1` through the same `KeyProvider` (`00-code-seams.md` finding 1); 111d is the sole decoder, which also ends the "two decoders for proposals" risk (`proposals.rs:133-134`). `agent111` calls three narrow loopback routes on its existing bearer channel; its file layout and its dependency list do not change. Whatever is picked, `save_proposal` and `save_task` should become atomic (temp, rename, fsync).
- **C**: documentation, not a build item. Termux and FUSE-less phones cannot use fscrypt; FBE already covers app-private data on Android (search snippet). State the limit: fscrypt leaves sizes and structure visible and gives nothing against a running compromised system (kernel doc, verified).
- **D**: one pruner, one backup file, but agent rows have no `local_seq` age semantics, and a store corruption then takes the agent with it; an L7 V4 / L8 V5 migration queue would serialize the two layers.

State plainly in the spec: encryption here protects copied files, backups and synced app dirs, not a stolen disk with a readable identity directory.

### Fork 2. Node-level capacity pruning (budgets and what the user sees)

- **Budget unit:** one per-node `keep` figure in bytes, default disk-relative (not a fixed 512 MiB), settable; a `disk_free` floor below which everything refuses growth. Defaults (proposals for the owner, derived, not measured): phone, min(2 GiB, 10 % of free at install); Pi (SD), min(2 GiB, 15 % of free) for the sum of the auto-pruned classes; hub (4A/4B), 25 % of the volume for the fabric and agent classes, datasets outside it.
- **Classes and rule per class:** fabric store (existing 10.4 order, existing quotas) ; agent state (oldest conversation first by a total-bytes cap, modelled on the 1 MiB FIFO of `A/events.rs:3`, never by age); logs (ring buffers: a size cap per file, rotate by size); foreign DBs (reported only; the only knob is "reset account", a user action); datasets (never auto-pruned; user removal, or a proposal the user accepts; install checks free space first); components cache and releases (existing: two releases kept).
- **No time anywhere.** Age is `local_seq` distance (`M/store/prune.rs`), never a wall clock; the agent store uses a monotonic counter column. Dataset removal and any destructive prune beyond step 3 asks for consent (the `409 consent_required` shape).
- **What the user sees:** per-class usage, `keeps X of Y`, filesystem free/total, `store_full` and the new `disk_low`; one Storage page as a lazy chunk (the `l6` precedent, `00-code-seams.md` finding 27).
- **What the agent may do:** read (`storage.read`), propose (raise the budget, export history then free it, remove dataset X, rotate logs). It never prunes. Fixed tools, D10 proposal flow; a `kind` for storage proposals is a Layer 3/9 contract addition.
- **Mechanism:** a thin node111 `budget` module that asks each owner for `bytes()` and calls its own `reclaim(n)`; mesh111's pruner stays the owner of its class. Wire `set_watermarks` and the export offer (both have no caller today). Hang the bookkeeping on the existing 60 s pass; no new timer.

### Fork 3. Backup of the store

- **A. Words only (today):** history lost on any disk loss. Honest, free.
- **B. Pick (v1): on-demand `111 store export` to a file**, encrypted to the node's own key, signed, using whichever single format the owner picks (below). Never reachable over HTTP, like `identity backup` (`2-identity/README.md:296`).
- **C. Automatic encrypted snapshots to the home hub as private objects** (random `object_key`, ciphertext-addressed; `5-messaging/README.md` 10.3). Needs Tier 2 transfer (v1.1) and a hub that opted in. v1.1.

Sub-fork on the format: **L2 8.5(i)** (own 6.4 construction, signed, no new dependency, already specified) vs **age** (standard tool, big default dependency list, no sender signature). Pick L2's, amend L5 section 21 and the KB `age` entry to match; age remains a documented future option for hub-side tooling. If the owner prefers age, the dependency sign-off row in `LICENSING.md` and a Pi-floor build-size measurement come first.

### Fork 4. SD-card wear policy

- **A. Do nothing.** Leaves the 60 s write.
- **B. Pick: change nothing in durability, change cadence.** (1) Capacity facts written only on change (finding 7). (2) `journal_size_limit` set (for example 4 MiB, about the 1000-page auto-checkpoint size). (3) `FULL` stays where it is. (4) Child logs capped. (5) Pi guidance: an endurance-class card (SanDisk MAX ENDURANCE 32 GB is rated 15,000 hours of video, no TBW given: search snippet); logs to RAM when the card is not disposable; F2FS only if the user already runs it (one anecdotal benchmark, nothing measured on wear).
- **C. Move to `synchronous = OFF` or an in-RAM write buffer.** Reject: breaks custody receipts ("the receipt promises the hub holds it", `M/store/rows.rs:1008`).

**Measurement gate before build:** idle hour and loaded hour on a real Pi, `write_bytes` from `/proc/<pid>/io` for 111d and the agent, plus `/sys/block/mmcblk0/stat` sectors written for the device; record RSS, binary size and listeners as AGENTS.md requires.

### Fork 5. The store API for other layers

- **A. mesh111 `Store` stays fabric-only; Layer 8 adds a node111 `state` service** with typed, namespaced calls: `put(ns, id, bytes)`, `get`, `list(ns)`, `append(stream, bytes)`, `read_stream(stream, since)`, `delete`, `usage()`, `reclaim(bytes)`; namespaces `agent/conversations`, `agent/proposals`, `agent/tasks`, `heal/journal` (Layer 9). The agent reaches it over the existing loopback bearer API; Layer 9 modules call it in-process.
- **B. Expose raw SQL or the whole `Store` to other layers.** Reject: couples every layer to the schema and blocks migrations.
- **C. Each layer keeps its own files.** What exists; rejects the capacity goal.

Pick A. The namespaces, byte counters and the `reclaim` hook give Layer 9 a journal that is bounded by capacity and visible in the same usage figures. Layer 9's state (heal journal, incident records) lands in a namespace, not a new file format.

## 5. Open questions for the owner

1. May agent state move behind 111d in an encrypted second file (Fork 1 B), accepting a loopback API dependency for the agent's persistence, or must `agent111` keep owning its files (then only atomic writes and caps, plaintext, and an L3 text amendment)?
2. Is it acceptable to cut the idle per-minute `settings` write to on-change only, and to set `journal_size_limit` (both L5 edits)?
3. Backup format: L2 8.5(i) or age (Fork 3)? Should the export-before-prune offer ship in v1, given step 3 never runs today?
4. Should the node budget default be disk-relative as proposed, and who sets it on a Cat 2B phone (install default, user, agent proposal)?
5. May a pre-migration snapshot (one extra copy of `store.db`, transient) be added to the update path before V4/V5 migrations run?
6. Delta Chat's own database stays plaintext: accept, document, and point at fscrypt for Linux operators who want it?
7. Are log size caps (`agent/*.log`) a Layer 8 task or an L1 amendment?
