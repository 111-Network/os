# Layer 9 gap-fill 1 - hub code-fix pipeline: containment and offline feasibility

Scout report, 2026-11-02. Question: can a Cat 4A/4B hub safely generate, and internally validate, a code fix for the 111 Rust workspace while offline, and what does the minimal contained pipeline cost? Read-only research; no cargo, no opencode, nothing run. Network facts: raw.githubusercontent.com, static.crates.io, static.rust-lang.org, registry.npmjs.org and crates.io were reachable; tinycomputers.io and forge.rust-lang.org were not. "(search snippet)" = WebSearch only.

## 1. Summary

- **The hole is concrete, not theoretical.** Headless `opencode run` without `--auto` auto-rejects anything that resolves to `ask` (`run.ts:791-810`, v1.19.5), so `external_directory` and `.env` reads fail closed. But bash and webfetch resolve to `allow` by default (`agent.ts:119-121`), and the agent writes no permission block. A prompt-injected or confused model can run `curl -X POST 127.0.0.1:11180/api/v1/proposals/<id>/decision`: no bearer is presented, so loopback counts as the human (`auth.rs:3-10,996`) and the bearer write gate never applies. That is a self-approval path. It also breaks "no host shell for the agent" (`3-intelligence/README.md:55`).
- **Denying the tools is a five-line config and it works offline.** `"*": "deny"` plus `read/glob/grep` (and `edit` only inside a scratch copy) removes bash, webfetch and websearch (websearch is not even offered with a local provider, `tools.mdx:260`). Fix it now, independent of any option: the existing `patch` kind is exposed today.
- **No runtime npm install for our provider.** `@ai-sdk/openai-compatible` is a static import in opencode's bundled-provider table (`provider.ts:158`, v1.19.5; line 117 in 1.18.18), so `Npm.add` (`provider.ts:1871`) is never reached. Pre-seeding is unnecessary; a different `npm` value in `opencode.json` would trigger a download, so the agent must not accept one.
- **The hub has no source tree and today's release cannot give it one.** The payload is `bin/111` + `share/kb/` + assets (`1-bootstrap/README.md:39`); no source tarball, no vendor tree. A pinned source asset is about 1.7 MB gzipped (Rust and manifests, measured with `git archive`).
- **A full offline build is three unlike costs.** The two pure-Rust workspaces (`2-identity`, `3-intelligence`: 64 and 108 locked crates, no `ring`, no OpenSSL, no SQLite) need only a Rust toolchain (111-127 MB xz) plus 4.5/14.4 MB of crates (compressed). The `node111` workspace (316 registry crates, 84 MB compressed, 37.7 MB excluding Windows/Apple/wasm targets) also needs a C compiler, make and perl (`openssl-src`, `libsqlite3-sys`), the musl cross compilers (`cross-build.sh:3`) and the built UI.
- **Pick:** ship option B (draft-only, tools denied, applied-cleanly check, upstream CI after the human opens the PR) for v1, option C (sandboxed `cargo check/test` for the two pure-Rust workspaces) as a later opt-in component, and treat "typed only" (A) as the floor everyone has. Honest wording for B: "drafted and applies cleanly", never "validated".

## 3. Findings that change the plan

**F1. Headless `ask` is fail-closed; the defaults are the problem.** `opencode run` registers only `question`, `plan_enter`, `plan_exit` as denied in non-interactive mode (`cli/cmd/run.ts:431-448`). On `permission.asked` it replies `reject` unless `--auto` (`run.ts:791-810`, tag v1.19.5, raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/cli/cmd/run.ts). `--auto` is "dangerous!" (`run.ts:245`); `agent111` does not pass it (`tasks.rs:28-32`). So `ask` is safe; what is dangerous is the default ruleset `"*": "allow"` with only `doom_loop`, `external_directory` and `.env` reads on `ask` (`agent/agent.ts:119-135`; `permissions.mdx:172-178`). Rules merge defaults, then agent, then the user's `permission` last (`agent.ts` explore: `Permission.merge(defaults, ..., user)`), and the last match wins (`permissions.mdx:92`). A config of `"*": "deny"` first, then the three read tools, therefore wins over the defaults.

**F2. The deny block, copied from the docs' own syntax** (`permissions.mdx:46-58,95-165`; keys listed at `:150-165`): `{"permission":{"*":"deny","read":"allow","glob":"allow","grep":"allow","edit":"deny","bash":"deny","webfetch":"deny","websearch":"deny","external_directory":"deny","task":"deny","skill":"deny","lsp":"deny","question":"deny"},"autoupdate":false,"share":"disabled"}`. Env for the child (all in the `cli.mdx:748-784` table): `OPENCODE_DISABLE_MODELS_FETCH=1`, `OPENCODE_DISABLE_AUTOUPDATE=1`, `OPENCODE_DISABLE_LSP_DOWNLOAD=1`, `OPENCODE_DISABLE_CLAUDE_CODE=1`, `OPENCODE_DISABLE_EXTERNAL_SKILLS=1`. Do not set `OPENCODE_DISABLE_PROJECT_CONFIG`: the provider block lives in the project `opencode.json` (`tasks.rs:494-508`). LSP is off unless `lsp` is set (`config.mdx:679`). Whether a denied tool is hidden from the model or only refused at call time is unverified; either is fail-closed.

**F3. `HOME` leaks.** The child keeps the node's `HOME` (`tasks.rs:394-509`): opencode keeps its database and `auth.json` under `~/.local/share/opencode` (`cli.mdx:142`) and reads `~/.claude` unless disabled. Point `HOME` and the XDG dirs at the per-task work dir. The child is a daemon child, so it runs as the daemon's uid (`1-bootstrap/README.md:31`) and, without a sandbox, can read whatever that uid can (identity files are 0600/0700 to it, `1-bootstrap/README.md:183`). Only the namespace contains that.

**F4. Provider packages are bundled.** `provider.ts:148-174` (v1.19.5) is the `BUNDLED_PROVIDERS` table; line 158 holds `@ai-sdk/openai-compatible` (dependency pinned `2.0.41`, `packages/opencode/package.json`). The loader returns before `Npm.add` (`provider.ts:1856-1872`). Any other `npm` string takes the install path, so `write_opencode_config` (`tasks.rs:496`) must keep the constant, and the sandbox's lack of network is the backstop. No pre-seeding needed, no runtime download.

**F5. Model endpoint through a network namespace needs ~100 lines of glue.** The model sits on `127.0.0.1:11181`, the daemon on `:11180` (`3-intelligence/crates/agent111/src/config.rs:94,99`). Inside `--unshare-net`, host loopback is gone, so opencode's `baseURL` (must be TCP, not a unix path) needs a forwarder in the namespace: a tiny `111` re-exec that listens on the namespace's loopback and relays to a unix socket that `111-agent` bind-mounts in. This is new custom glue; `socat` (GPL-2.0) would be a second separate program. Landlock cannot replace it (F-table: TCP-connect rule needs kernel 6.7, Fast Open bypass).

**F6. Source provenance does not exist yet.** No source in the payload (`1-bootstrap/README.md:39`); the build pins an asset by hash in the signed manifest (pattern: `meshmud-build.sh:25,97`, KB tarball). A hub source asset would be `git archive` of the release tag in CI (the CI-side git is fine): Rust crates + manifests + `Cargo.lock`, **1.7 MB gzipped**; all layers 2.5 MB; whole tracked Rust/TOML/MD text 7.7 MB raw. Recommend a hub-only manifest asset, hash-pinned, not prefetched on a Pi (the `prefetch = false` pattern).

**F7. Dependency volume** (this task's own count; HEAD `Content-Length` of each `static.crates.io/crates/<n>/<n>-<v>.crate`; compressed, vendored directories are larger, factor unverified):

| Lockfile | Registry crates | Compressed | Excluding windows/apple/wasm |
|---|---|---|---|
| `2-identity` | 64 | 4.5 MB | 63 / 4.5 MB |
| `3-intelligence` | 108 | 14.4 MB | 104 / 11.7 MB |
| `5-messaging` | 150 | 41.8 MB | 136 / 25.8 MB |
| `1-bootstrap` (node111) | 316 | 84.2 MB | 251 / 37.7 MB |
| union of all four | 349 | 87.6 MB | 284 / 41.1 MB |

The largest are `windows` 0.57 (9.7 MB), `openssl-src` (7.2 MB), `sqlite-wasm-rs` (6.0 MB), `libsqlite3-sys` (5.4 MB), `linux-raw-sys` (3.0 MB). "The 111 workspace" is really four separate lock graphs (`find -name Cargo.lock`); `6-transport` has none. `cargo vendor` has no stock platform filter (unverified).

**F8. Build prerequisites differ per workspace.** `cargo tree` facts from the locks: `ring`, `openssl-src` and `libsqlite3-sys` appear only in `1-bootstrap` and `5-messaging` (SQLCipher + vendored OpenSSL, `1-bootstrap/scripts/cross-build.sh:6-9`).  `openssl-src` needs perl, make and a C compiler (from its design, unverified). The release embeds the UI (`cross-build.sh:22-26`), so even `cargo check` of `node111` needs `4-interface/ui/dist` or `--allow-no-ui`. CI uses `cargo fmt/clippy/test --workspace` per layer (`.github/workflows/ci.yml:75-77`).

**F9. Published build time/RAM is thin.** Only one usable number: a Raspberry Pi CM5 (Cortex-A76, 4 cores, 8 GB) did a clean `cargo build --release` of `ballistics-engine` in 69.7 s mean; Orange Pi 5 Max 58.7 s; fastest x86 13.7 s (search snippet, tinycomputers.io/posts/rust-compilation-performance-benchmark-report.html; project size unknown, page not fetchable). No N100 figure found. Qualitative (search snippet): linking dominates memory; a 1 GB board needed `--jobs 1` (github.com/rust-lang/cargo/issues/9735). Our release profile is `lto = "thin"`, `codegen-units = 1` (`1-bootstrap/Cargo.toml`). Validation does not need release: `cargo check` and debug `cargo test` in a sandbox with `-j` capped. **Do not quote a figure for the owner; the lead should measure on the Pi 5 and N100 before the board promises one.** Repo size: 174,513 lines of Rust, 117,976 under `1-bootstrap/crates`.

**F10. Toolchain as a consented component is feasible but not free.** Compressed 111-127 MB (F-table), pinned by the manifest like `madmail` (77 MB, `LICENSING.md:70`, `prefetch = false`); a hub with an N100 or 4B GPU box has the disk, a Pi 4A does not. Unpacked size and the extra gcc/make/perl packages are not measured here. Android hubs: no.

**F11. A pass is weak evidence** (`02-change-validate.md` section 1: deleted functionality satisfies validators; SWE-bench+ leakage). With Qwen3-4B as the default model, expect low first-try diff validity; a cheap mechanical "applies cleanly" gate beats a heavy build.

## 4. Options

| | A. Typed only | B. Draft-only diff | C. B + sandboxed check/test (pure-Rust workspaces) | D. C + node111 release build |
|---|---|---|---|---|
| What happens | no code fixes; agent proposes typed actions and prose | opencode, deny block, reads a read-only source tree, returns a unified diff; 111-agent checks it applies to the pinned tree, signs the proposal; human opens the PR; upstream CI runs | B, then in bwrap/nsjail with no network: `cargo check`/`test --offline --frozen -j N` on `2-identity`/`3-intelligence` | adds gcc, make, perl, musl cross, UI dist, 84 MB crates |
| Resident weight when off | 0 | 0 (opencode already opt-in, 211 MB on disk) | 0; disk: toolchain 111-127 MB xz + 4.5-14.4 MB crates | 0; disk adds ~84 MB crates + C toolchain |
| New sign-off rows | none | `diffy` (MIT OR Apache-2.0), source asset (our own GPL source); no new binary | + Rust toolchain (MIT OR Apache-2.0), bubblewrap (LGPL-2.1, separate program) or nsjail (Apache-2.0); crates are existing lock rows | + gcc/make/perl (distro packages, GPL, separate) |
| New custom glue | none | permission block, scratch copy, apply check (~tens of lines) | + netns forwarder (~100 lines, F5), sandbox launcher, vendor step in CI | + a cross-build mirror of `cross-build.sh`; not recommended |
| "Internally validates" means | the typed action's own verify | the diff parses and applies cleanly to the exact release source; **not** compiled | compiles and the crate's tests pass on this hub's architecture against the pinned source; evidence, not proof; hub-arch only | same for the daemon, the heaviest and least portable |
| Cost | none | small | medium; time and RAM unmeasured (F9) | high |

**Pick: B for v1, C as an opt-in hub component later, A remains the floor.** B closes the containment gap, needs no toolchain and no download, and it is honest: validation by upstream CI after a human opens the PR, with the human as the final gate. C is the right second step only for fixes inside `agent111`/`id111`, which is where the self-healing logic itself lives; it is not worth shipping before a measured Pi 5/N100 build time exists. D is not recommended.

Mandatory under every option (correction to the as-built tree): (1) write the deny block in `write_opencode_config` and test it in a namespace gate (G-style: a prompt that asks for `curl 127.0.0.1:11180` must produce no connection); (2) `HOME`/XDG into the task dir; (3) no `--auto` ever; (4) the proposal is signed by 111-agent, not by opencode, and `patch` output is stored as text only. Containment tiers: deny block (all hubs) < plus bwrap with no shell mounted and `--unshare-net` (where userns works) < plus Landlock FS rules. Landlock net rules are not the boundary.

## 5. Open questions for the owner

1. Is "code fixes in v1" wanted at the draft-only level (B), given the validation wording "applies cleanly, not built"?
2. May the channel manifest carry a hub-only source asset (about 1.7 MB gzipped), and may the hub prefetch it? It changes release CI, not the node.
3. Should loopback-is-human (`auth.rs:3-10`) stay on a node whose agent can spawn children? The sandbox makes it moot for opencode, but the rule is the root cause.
4. Is a Rust toolchain (111-127 MB compressed) an acceptable consented component on 4A hubs, or only on 4B?
5. Measure cold `cargo check` of `3-intelligence` (time, peak RSS) on a Pi 5 and an N100 before option C is promised?
