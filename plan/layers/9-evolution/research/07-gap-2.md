# Layer 9 research 07: gap G2, AGENT_OP and delegation for Cat 2A/3 over the fabric

Scout: gap-fill, 2026-11-02. Read: 06-critic.md (§3, §5 G2), 05 F6/F7, 01 §3.2 and §3.4, 03 §1 (PATCH sizes), the Layer 3 agent crate, the node111
intelligence module, the mesh111 envelope/store/fabric code, `5-messaging/README.md`, `7-relay/README.md` (a DRAFT, read at its state on this date),
`1-bootstrap/README.md:160` and the installer's APK code. Nothing run, nothing fetched from the web (nothing needed it). Repo lines are cited inline.
Prefixes: `A/` = `3-intelligence/crates/agent111/src/`, `M/` = `5-messaging/crates/mesh111/src/`, `N/` = `1-bootstrap/crates/node111/src/`.

## 1. Summary

- **`AGENT_OP` is a reserved kind and nothing else.** A byte (0x10), SIGNED-mandatory, interactive priority, a store class, a few envelope tests. It has no
  payload schema, no stream id, no send API, no consumer: an inbound one lands as a textless row in the sender's chat thread (F1).
- **LAN offload, the only delegation the sweep covered, does not exist on the hub side as built.** The phone-side guard admits a private-IP model base; the
  hub's `llama-server` is spawned with `--host 127.0.0.1`, no key, and the phone's model client sends no `Authorization` header. "LAN binding + pairing auth"
  (`3-intelligence/README.md:48,110`) is prose; Layer 3's own gate G3 (`:86`) is open (F2). Off-LAN it cannot work at all: the target is a private IP literal (F3).
- **Pick: `AGENT_OP` in v1, one narrow op pair (`diagnose` request, `diagnosis` reply), home hub only, size-gated to links that fit it, reply is a
  proposal the phone's human accepts and never auto-applies.** It costs less than building the LAN-offload auth it replaces for diagnosis, it reuses the
  sealed, attributed, queued-until-link fabric that is already built, and it moves about 0.5 KB each way instead of the 6,000-token context (F4, F5).
- It needs three additive L5 changes (a send API for non-MSG kinds, a stream id, a consumer hook that stops filing `AGENT_OP` as chat) and two small
  L3/L7 ones (a structured foreign-incident input for `diagnose`; a role bit). A Layer 7 carrier ride is not a candidate: the carrier moves frames between
  two paired hubs, never to or from a member, and a put addressed to a hub itself is refused (F9).
- **APK refresh** is a `human_step` proposal: the daemon never reads the manifest's APK pins today, the receipt records none, a phone has no adb, and the only
  honest v1 text is "from your computer run `111 install --phone`", with a hub-origin download of the pinned file as a later convenience (F10).

## 3. Findings

### F1. What exists for `AGENT_OP`: a byte, a signature rule, a store class
- Kind table: `0x10 AGENT_OP | node ↔ node | interactive | per stream | §4; SIGNED` (`5-messaging/README.md:173`); the hand-off line is
  "**Layer 9:** `PATCH` class, `AGENT_OP`, `RECEIPT_STRONG`; the apply→verify→undo engine (P4)" (`:832`).
- SIGNED is mandatory for it (`5-messaging/README.md:139-140`; `M/envelope.rs:566-576`, `requires_sig`); it is not a public class, so `sig` binds the recipient NodeId
  (`M/envelope.rs:576-586`; the review that added this: `plan/layers/5-messaging/review/crypto.md:23,74-75`). It carries a `msg_seq` (`M/envelope.rs:558-565`),
  is interactive priority (`:586-593`), maps to `Class::Agent` (`M/store/rows.rs:36-37,76-80`), and `RECEIPT_STRONG` names it (`5-messaging/README.md:267-268`).
- Tests: a signed op with a 16-byte JSON payload `{"op":"restart"}` seals and opens (`M/test_double.rs:1140-1165`); an unsigned one is refused
  (`M/envelope.rs:1478-1482`); `INTRO` on it is refused (`:1850-1854`). The payload is opaque to the crate: there is no op schema.
- **Receive path:** `k if k.carries_msg_seq() => self.on_data(&opened)` (`M/fabric.rs:2596`); from a non-contact it is dropped, from a contact it becomes a
  `messages` row (`:2631-2700`), which the UI renders as a textless row (Layer 8 seams report, `plan/layers/8-storage/research/00-code-seams.md:138-146`,
  items 17-18; the same holds for `KB`/`UPDATE`/`PATCH`). **Send path:** none; the one public producer is `send(to, text)` on `STREAM_1TO1` only
  (`M/fabric.rs:856`; `M/ids.rs:22`; Layer 8 `00-code-seams.md:21`). The UI quota editor refuses to offer `agent_op` (`4-interface/README.md:409`).
- Consequence: a consumer is a Layer 9 build task on top of three additive L5 changes (R1 to R3, §5), not a flip of a switch.

### F2. Layer 3 offload as built: the client half only
- Phone side: `model_base` defaults to `http://127.0.0.1:11181`; `guard_model_base` admits loopback or an RFC1918/ULA/link-local IP literal and refuses
  public IPs and hostnames (`A/config.rs:94,325-350,405-421`). `derive_state` reports `offloaded` for any non-loopback base (`A/status.rs:24-34`).
- The model client builds `{base}/v1/chat/completions` and probes `{base}/health` with `ureq`; there is no header call at all (`A/model.rs:170-190`; a grep for
  `Authorization|.header(|.set(` in `model.rs` finds none). The header comment says "Plain HTTP only ... encryption is Layer 5's job" (`A/model.rs:3-4`), but no
  Layer 5 path carries it.
- Hub side: `111d` spawns `llama-server` with `--host 127.0.0.1 --port 11181` and no key, and a unit test pins exactly that
  (`N/daemon/intelligence.rs:186-191,413-420`). The agent's own `--lan` flag binds `:11182` to `0.0.0.0` (`A/lib.rs:56-60`), but its Host guard answers 403 to any
  Host that is not 127.0.0.1/localhost/[::1] (`A/http.rs:49-72`), so a phone cannot use that either, and the spec's wording "the hub's `--lan` binding"
  (`3-intelligence/README.md:86`, gate G3) conflates the two. G3 is listed deferred ("2A→hub offload over a real LAN", `3-intelligence/TASKS.md:72`).
- Spec text: "A model-less node's `111-agent` points its model base URL at a nearby hub ... In v1 offload stays on the LAN binding + pairing auth"
  (`3-intelligence/README.md:48`); "hub offload endpoints authenticate peers by node identity" (`:49`); Layer 7 repeats it (`7-relay/README.md:798,1086,1319`).
  No code or contract anywhere defines "pairing auth" for the model port.
- What a phone-run `diagnose` would send: `gather_context` = node id, category, daemon health, the 30 newest journal events and up to eight 8 KiB KB entries
  (`A/tasks.rs:42-47,358-380`; 01 §3.4 sizes it at about 6,000 tokens, an estimate), as a user prompt to that port, in clear on the LAN. The incident record's
  evidence excerpts (01 §3.2) would ride in it.

### F3. What breaks off-LAN
- The offload target is a private IP literal with no DNS (`A/config.rs:325-350`; `7-relay/README.md:798`), so a phone on mobile data or another Wi-Fi
  dials an address that is unreachable or, worse, someone else's. The state flips to `unavailable` (`A/status.rs:24-34`); the human sees a dead hub.
- `tcp-lan` is the only link built for member ↔ hub (`5-messaging/README.md:361`); the hub's listener is `:11183`, LAN-bound only when the node acts as a hub or LAN
  sharing is on (`:370`). Meshtastic/MeshCore/LXMF links are Layer 6 optional components; nothing in a stock phone install reaches a hub off the LAN.
- A sealed AGENT_OP survives this where an HTTP call does not: the phone's outbox holds it `queued` until a path to the hub exists (`5-messaging/README.md:238`,
  "re-seals on retransmit"; `M/fabric.rs:855` "`queued` until a path exists"), and a reply waits in the hub's outbox. Nothing polls for it: the existing redial
  back-off (`7-relay/README.md` §7.7) and the link-up attribution are the wake sources already running.

### F4. What an `AGENT_OP` would carry for Layer 9, and the size against Tier 1
Proposed op set (closed; v1 has two): `diagnose` (phone → hub) and `diagnosis` (hub → phone); a third, `refuse {reason}`, answers a request the hub will not serve.
Deterministic CBOR like `MSG` bodies (`5-messaging/README.md:183`), a `schema` byte first so an old node ignores a newer op, every field length-capped.
- **Request** (about 450 to 600 B, my arithmetic: a trimmed 01 §3.2 record, which 01 itself estimates at 600 to 1,000 B before trimming): `req_id` (the sender's
  `epoch ‖ n`, 3 to 5 B), `fingerprint` (layer 1 B, subject <= 24 B, `reason_code` <= 24 B), severity, count, `release` calver (10 B) + target triple + category,
  the playbook checks that ran as `{check_id, result}` pairs, the cause ids already ruled out, and up to three evidence excerpts of <= 120 B each. Nothing else.
- **Reply** (about 400 to 600 B): `req_id`, the hub's `release`, `cause_id` from the closed playbook enum (or `unknown`), `confidence` as the two separate fields
  01 §3.4 requires (checks satisfied, rule/model agreement), up to three typed actions drawn from Layer 9's vocabulary (each <= 80 B: action id, target,
  verify spec), and a narrative <= 256 B. The model's free text is data and is never parsed for actions (F7).
- **Fit** (`5-messaging/README.md:143-148`, `M/envelope.rs:2110-2140`): TCP carries up to 65,445 B in one frame, so both fit Tier 0. At the 233 B Meshtastic profile a
  SIGNED payload is 78 to 80 B, 76 to 78 B with Tier 1 fragment fields (the unsigned 69-71 B column drops 2 B the same way); 16 fragments is about 1.2 KB, so a 600 B
  op needs 8 to 10 fragments, about 2 KB on air. Using L7's own scale (3.2 KB in 30 to 55 s on LongFast, `7-relay/README.md:916`, R04, unverified from here), that is about
  20 to 35 s each way before duty-cycle waits. At the 160 B MeshCore floor a SIGNED fragment carries 3 to 5 B, so Tier 1's 16 fragments hold 48 to 80 B: **no
  Layer 9 op fits a 160 B flood frame**, and `5-messaging/README.md:150` already says SIGNED classes are Tier-2 or TCP in practice.
- **Rule:** the sender checks `payload_budget(profile) * 16 >= len` for the path's profile before sealing and otherwise leaves the request `queued` with the
  reason "needs a longer link" (the existing fit logic, `M/envelope.rs` tests at `:2110-2140`). v1 therefore delegates over `tcp-lan` and over 233 B bearers; 160 B
  bearers wait. No Tier 2 object transfer is needed (it is built in v1.1, `5-messaging/README.md:239`).
- Receipts: `RECEIPT_STRONG` on the request (the hub proves it decrypted this payload, `:267-268`) gives the phone a transferable "your hub got it"; the reply is
  a normal signed op whose ACK the hub reads. Idempotency: the op is keyed by `req_id`; a duplicate request gets the same stored reply (no second model run).

### F5. The Pi floor, both ends
- Phone: the request is composed when an incident opens with no T0 cause match and the home hub is the contact with `trust = enrolled` (5-messaging §7.1). That is
  an event in 111d's existing observer (01 §3.1), one `send` into the existing outbox, no thread, timer or poll for the answer. Closing the incident marks the
  request cancelled, and a reply arriving for a closed `req_id` is dropped: no wire cancel, no wall clock. The reply is handled by the fabric task already running.
- Hub: the arm runs in the fabric actor that exists (`M/fabric.rs:2596`); the diagnosis is one `POST /v1/agent/task` to its own resident agent over loopback
  (`3-intelligence/README.md:78`), serialised to one at a time by 111d (the agent does not serialise concurrent turns, `3-intelligence/TASKS.md:72`). The model
  loads on demand and `--sleep-idle-seconds` unloads it (01 §3.4); a hub with no model answers from the T0 playbooks alone, which costs milliseconds.
- New resident weight: none on either end. Binary size and the hub's per-request RSS go to `9-evolution/TASKS.md` when built, as AGENTS.md requires. The L5 added
  code is a kind-specific arm and a send wrapper in code that already ships.
- The pending-request table is at most one open request per incident and 64 incidents (01 §3.2): 64 rows of `req_id` and state, in the `heal/journal` namespace if
  Layer 8 Fork 5 A lands (`8-storage/research/04-local-store.md:91-95`), else in the incident file.

### F6. The trust rule (c): the home hub, nothing else
- The relation exists and is already authenticated: a node has one home hub (`5-messaging/README.md:330`); enrolment stores the hub as `trust = enrolled` on both
  sides after a single-use code (`:319-330`, `:291-293`); a connection counts as the hub's only after a fresh `pair_mac`-verified packet (`:375-378`).
- Rules: (1) the **hub** accepts a `diagnose` only from a sender whose contact row is `enrolled` here and whose connection is attributed; contacts (`oob`, `tofu`) and
  strangers are dropped and counted, like `REJECT_UNENROLLED` (`M/fabric.rs:2830-2831`). (2) the **phone** accepts a `diagnosis` only from its `home_hub` contact,
  on an attributed connection, for an open `req_id`; anything else is dropped and counted. (3) A contact is never a delegate in v1: Layer 9's
  sharing of fixes with contacts is `PATCH` (03), a different class with its own rule, and conflating them would let a contact steer a phone's repair.
- A hub does not store a member's `AGENT_OP` for others: a put whose `dest` is the hub itself is refused, since a hub holds custody only for enrolled members and
  never for itself (`M/fabric.rs:2830-2833`; `7-relay/README.md:401-404`: a hub's own messages never enter its custody table). So delegation is a direct 1:1
  exchange with queue-at-the-sender, which is the property wanted: the member's phone, not the hub, owns the pending state.
- **What the hub may read:** exactly the F4 request, built by 111d from the incident record, never by the agent. The record's evidence is "pointers plus bounded
  excerpts from typed sources (service record, health JSON, counters, our own child log tail), never message bodies" (01 §3.2). No text of a conversation can
  reach it by construction. One hole: a child's log tail is free text, and the Layer 6 adapters' logs (`bridge/*`, the Meshtastic presence sidecar) can hold
  contact names or previews. Rule: the delegation view carries no excerpt from a bridge adapter or presence log, only counters and reason codes for them
  (Q3). Nearby names are RF-origin strings and stay in a labelled untrusted block wherever they appear (`7-relay/README.md:1085-1087`, `3-intelligence/README.md:110`).
- **What it returns:** a signed reply that becomes a proposal on the phone (F7). The hub cannot write on the phone: the agent's bearer is refused on every write
  (D26 (2), `plan/DECISIONS.md:392`), and an `AGENT_OP` reaches the phone's 111d, not its agent.
- **Hub consent:** serving members is a hub switch, off by default, like every Layer 7 hub role (`7-relay/README.md:67`); `heal.serve_members`. The phone learns
  that its hub serves from a signed role bit rather than by asking: L7 reserves bits 3 to 5 (`:765-768`) and bit 6 of the u16 is free, set in node111 beside
  `appdata` with no mesh111 change (`:758-760`). Reusing bit 4 `ROLE_OFFLOAD` ("serves model inference to paired LAN members") is possible but wrong for a hub with
  no model that can still serve newer playbooks. Layer 7 is a draft being edited live: ask its owner, do not edit it from here.

### F7. The foreign-incident input the hub's agent lacks
- `diagnose`/`propose` take `{kind, refs, note}` (`A/http.rs:163-167`) and `gather_context` fills the prompt from the **hub's own** health and journal
  (`A/tasks.rs:358-380`). Run as is for a member's incident it would diagnose the hub, or, with the member's summary pasted into `note`, put a foreign node's text in
  the trusted prompt slot ("Note: ..." is interpolated into the user turn, `:336-340`).
- Needed (additive, Layer 3): an optional `incident` object on `diagnose`, validated against the F4 schema, rendered in a labelled untrusted block, which also
  turns off the hub's own `daemon_health` and `recent_events` for that task so a member's request cannot read the hub's logs back through the model's narrative.
  This is the lens-4 point (04 §4.3, critic conflict 8) applied to the delegation path: foreign text is data, and the typed fields, not the prose, drive the proposal.
- On the phone, the reply's actions are **re-validated against the phone's own closed action vocabulary and scope** (02's `Action` family, scope list), the
  narrative is rendered preformatted, and provenance reads "from your hub <alias>, not checked by this phone". A reply naming an action the phone does not know
  is shown as advice only. **A delegated reply never auto-applies, even under an opt-in auto-apply rung** (critic fork 1): the auto rung is for the phone's own
  playbook actions. D26 (2) holds: the human accepts (`POST /api/v1/proposals/{id}/decision`).

### F8. The Layer 5 amendment (additive, the AGENT_OP consumer only)
R1. **Send API:** `Fabric::send_op(to, stream, kind, payload, receipt_strong) -> msg_id`, kind restricted to `AgentOp` in v1, the size gate of F4, the same
    FULL-commit-before-seal rule as `send` (`5-messaging/README.md:190-192`). The existing `send(to, text)` stays byte-for-byte.
R2. **Stream id:** `STREAM_AGENT = 1` (`M/ids.rs:22` has only stream 0). `tx_state`/`rx_state` are already keyed by `(peer, stream)`
    (`5-messaging/README.md:445-446`), so a long op never blocks chat's cumulative ACK. Named in §4 as "per stream", `sig` already covers the stream varint
    (`:134-135`). To confirm in the amendment's tests: a non-zero stream through `offer_fragment` and the ACK piggyback.
R3. **Consumer hook:** an inbound kind-0x10 packet is delivered to a registered consumer (a node111 module) and ACKed, **instead of** `on_data`'s `messages` row.
    The row is dropped from the chat thread (this also fixes the textless-row defect Layer 8 flagged, `00-code-seams.md:287`, for this one kind). `Class::Agent`
    keeps its quota accounting; the consumer receives `(sender, stream, msg_seq, payload, verified_sig)`. The consumer, not mesh111, applies F6's trust rule.
No change to the wire, the kind table, the domain tags or the sizes; old nodes drop the kind as today (unknown or unconsumed). Domain tag for op payload
digests: none new (the existing `111/msg/v1` signature covers the payload hash).

### F9. Alternative: a Layer 7 carrier ride does not apply
- The carrier "moves opaque sealed frames between two paired hubs: the same `CUSTODY_PUT` and `CUSTODY_ACK` packets the pair would exchange on `tcp-lan`"
  (`7-relay/README.md:603-606`); it is "not a `Link`" (`:612`); pairing is hub to hub (`:324-336`). A phone is a member with one home hub; it has no carrier of its own.
- A member's put to a non-member `dest` is forwarded only toward a hub (`:408-421`), and the far hub's `carrier_inbound` accepts a `dest` that is its own member or a
  member of a leaf pair, else `REJECT_UNKNOWN_DEST` (`:422-424`). A put whose `dest` is the far hub itself is refused, so even a hub-to-hub delegation would need a
  further Layer 7 amendment, and it would violate the home-hub-only rule (F6). The frame bound is 2,937 B (`:427`, `:644`), which an op fits.
- What remains true: a hub (a Cat 2B Pi hub with no model, say) delegating to a paired hub with a model is a legitimate later case; it needs "the hub is the
  destination" support in L7 §5.2 and is out of this gap (Q6).

### F10. The APK hand-off (`1-bootstrap/README.md:160`)
- Today: three APKs are pinned in the manifest (`[apk.termux]`, `[apk.termux-boot]`, `[apk.termux-api]`, `N/manifest.rs:27-34,422-424`), installed by the host-side
  installer with `adb install -r`, a signature-continuity check and a `versionName` verification via `dumpsys` (`N/install/phone/apk.rs:1-4,48-118`,
  `APK_PACKAGES` with 0.118.3 / 0.8.1 / 0.53.0 at `:13-17`). The running daemon never reads them: `termux_apks()` has only the installer as a caller (grep), and the
  receipt module mentions no APK, so a phone **does not know which APK versions it runs**. "Self-update covers the `111` binary only; APK refresh = Layer 9
  maintenance task" (`1-bootstrap/README.md:160`). A phone cannot run `dumpsys`/adb itself (05 F6), and the GitHub Termux builds share a public test key, so the
  install of a foreign-signed Termux fails by design (`apk.rs:95-100`).
- **What the proposal is:** kind `human_step` (05 F6's "human-instruction" proposal; no applier action, nothing for 111d to run), titled "A newer Termux add-on is
  pinned". Trigger: the signed manifest (already fetched by the updater, and checked from the hub origin when present, `7-relay/README.md` §9.3) names an
  `apk.*` sha256 that differs from the one this phone last installed. The record of "last installed" does not exist and is a Layer 1 addition (a `receipt.apk` map written by the
  phone installer, additive; Q5). Fields: package id, pinned versionName, sha256, size, source order, and the steps.
- **Steps (v1, all human):** "On your computer, connected to this phone, run `111 install --phone` again" (the existing flow re-verifies pins, collision-checks and
  verifies the result), or, with the file in hand, "open this file from your phone's file manager" (below). The notice states plainly: the system installer will ask
  for one confirmation per package; MIUI/HyperOS may ask for the per-APK prompt it already warns about (`install/phone/mod.rs:411`); updating the Termux app
  itself closes Termux and 111d, and Termux:Boot starts them again at the next boot or the next open.
- **A hub may hold the APK (Layer 8/7):** the hub origin serves "blobs whose sha256 and size match a pin" it verified (`7-relay/README.md:866-867`), "its own target's
  payload; another only when listed in `origin.targets`", and Layer 8 owns the bulk-file side (`8-storage/research/06-critic.md` G2 lists APKs and debs as uncovered).
  If the hub lists the `apk.*` pins, a phone can fetch `http://hub:11180/origin/v1/blob/<sha256>` (T6 allows http for the home hub, `7-relay/README.md:910-911`), verify
  sha256 against the signed pin, and leave the file where the user can open it. Whether Termux may write to a place the Android installer can read is Q5/unverified.
- This is not a delegation: the proposal is local, composed by 111d from the manifest; the hub's only role is being a byte source. It does not need `AGENT_OP`.
  Do not let the proposal text imply an automatic install: no phone-side code can install an APK without the system installer, root, or adb.

## 4. Recommendation

Fork G2, for the lead's options brief:
1. **Pick B:** `AGENT_OP` in v1, op pair `diagnose`/`diagnosis`, home hub only (`enrolled` contact), size-gated (TCP and 233 B bearers; 160 B waits), hub switch
   `heal.serve_members` off by default, reply = a proposal the human accepts and never auto-applies, hub-side `diagnose` gains a foreign-incident input. Cost: R1 to R3,
   one L3 field, one role bit, one L9 op schema (`schema` byte, closed fields).
2. **Or A:** no fabric delegation: T0 on the phone and a "needs a hub" badge; the owner opens the hub's page. Zero amendments; T2 and model diagnosis stay hub-local.
3. **Never C for Layer 9:** a model port on the LAN (plain HTTP, no auth as built) is a weight and a hole this layer should not own.
Keep `patch`/code ops out of the op set until G1 closes. The APK proposal (F10) ships either way.

## 5. Open questions (for the owner or the lead)

1. May Layer 9 add the three L5 changes (R1 to R3), or does the owner want `AGENT_OP` to stay reserved (pick A)? R3 also removes `AGENT_OP` from chat threads.
2. Is a delegated reply never auto-applied acceptable, even where the owner later enables the opt-in auto rung (critic fork 1)?
3. Evidence excerpts from bridge adapters and presence logs: excluded from the delegation view (pick), or sent redacted?
4. Layer 3's chat offload has no hub-side listener or auth (F2). Does the owner want it fixed in Layer 3/7 (a key, an authenticated port, or chat over this same fabric
   op), or is chat offload dropped from v1 and the README text amended?
5. APK: does the installer record `apk.*` pins in the receipt (Layer 1 additive), and does the hub origin list them? Which folder can Termux write that the Android
   installer reads (needs `termux-setup-storage`, which the provisioner may not grant)?
6. Hub-to-hub delegation (a model-less hub using a paired hub's model): v1.1, with an L7 §5.2 "hub as destination" amendment?
7. The `ROLE_HEAL` bit: a new bit 6 (pick) or widen bit 4; Layer 7's owner decides, since the draft is being edited.
8. Per-member request limit on the hub: "one open request per member, queue capped by count" is a capacity defense, not a rate policy; confirm it fits
   README:79's "no rate limits" (critic fork 8).
