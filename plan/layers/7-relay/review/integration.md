# Layer 7 spec v0.1 — panel review, lens I (integration: seams, buildability, verification)

Judge: fable, read-only, 2026-11-02, tree `30ffc1d` (the draft commit; its base `ec9954b`; mesh111 unchanged since `3bf545b`). Sections judged: §0–§2
(reading guide, scope, presence, the `111` Nearby kind), §7 (registry, sealed query), §10 (radar), §13 (API additions against
`4-interface/api/README.md` and `openapi.yaml`; agent tools against `3-intelligence` conventions), §15 (every gate), §17–§19 (completeness
against D30 F10 and the brief §4; cross-layer lists; deviations). Every `M/`, `N/`, `NI/`, `A/`, `UI/`, `MD/`, `API`, `L1`, `L2`, `L5`, `L6` line
the draft cites in those sections was re-read; all resolve to the text the draft describes except where a finding says otherwise. The mdns-sd
0.21.5 lines were read in the local registry source; `tokio-rustls` is absent from `1-bootstrap/Cargo.lock` and `rustls 0.23.45` / `ring 0.17.14`
sit at the cited lines.

**Verdict: amend-then-lock.** The shape (event-derived presence, a `111` Nearby kind, a DNS-SD record inside the daemon that already runs, the
sealed query pinned for v1.1, an SVG radar, additive routes) matches D30 and the code, and the gates are the right gates. One claim is wrong
against the code and must be fixed before the lock: the per-transport evidence of §2 cannot be derived from the fabric's event stream without a
Layer 5 read the draft says it does not need. Six majors are places where a builder would build the wrong thing: the consent round-trip and the
problem-code pins break pinned contract shapes, the heartbeat switch has no transport and no defined write path in v1, the `rnpath` hop read has
no route or bound, and two D30 narrowings are not in the deviation list.

## Blockers

| id | where | what | fix |
|---|---|---|---|
| I1 | §2.1 items 3–4, §2.2 row 1, §2.3 `evidence[].transport` | **Per-transport evidence for an inbound message is not derivable from the event stream, and the draft says no Layer 5 change is needed.** `FabricEvent::Message { id, peer, change }` (`M/fabric.rs:418-428`) carries no route; `MessageChange` is `New`/`State`/`Request` (`:380-388`); `LinkView.peers` is a `usize` count, not the attributed NodeIds (`:586-597`); `HubView` knows only the home hub (`:601-616`). So the daemon cannot say whether a contact's message came over `tcp-lan` or "through your hub", and "a 111 contact heard on the LAN and through its hub has two facts" is unbuildable as written. | Pick one and say it: (a) v1 keeps **one** `111` fact per contact, `evidence[].transport` = `"111"` (path unknown) for messages and `"tcp-lan"` only for the hub/paired-hub rows (where `FabricStatus` does say so), and §2.1(3) narrows "per transport" to foreign sources vs 111; or (b) add a read-only `Fabric::attributed_on(peer) -> Option<LinkKind>` (or a `via` on the `Message` view) as a flagged change beside D1 (D12 in §19, "outside the twelve, read-only, byte-identical"), and have G8 assert the LAN-vs-hub split. Either way §2.2's first row names the rule. |

## Notes

- Good: every §0–§2, §7, §10, §13 and §15 citation except I7 resolves; the mdns-sd lines (`:69`, `:441`, `:476`, `:696-701`, `:1705-1708`,
  `:1844-1850`) read exactly as described; kinds `0x0C`/`0x0D` are free (`Kind::ALL` is 18, `0x0A`–`0x0F` unassigned); `tokio-rustls` is
  absent from the lock and `rustls 0.23.45`/`ring` sit where the draft says.
- Good: the agent tools follow the L6 shape (reads are GET wrappers, the write is a proposal through the agent's own store, the bearer never
  POSTs); the 17 → 20 pins are the right two files; the CI mapping names real jobs and `check.sh` really includes `5-messaging/scripts/check.sh`.
- Good: §17 carries every D30 F10 v1.1 item; §18's Layer 5 list is the twelve plus D1 and nothing else lands in v1; `0x0A` stays free for the
  envelope test.
- Watch in the build: the `111` source's `id` is 64 hex where `reticulum` is 32 hex — the UI's per-kind id validation and `nearby.rs`'s
  `is_hex32` need a `111` arm; the SSE `nearby` frame coalesces per change, so a hub with hundreds of contacts should publish per tick, not per
  fact.
- Watch: §7.7's browse on a member needs that member's mdns-sd daemon, which exists only with LAN sharing on; the UI copy for "Find my hub"
  should say so when it is off (`409 lan_off`).
- Watch: `/relay` carries `paired_hubs[].node_id` to the agent as untrusted text; keep `label` and `endpoint` out of any string the model
  could read as an instruction (the `presence.read` untrusted block rule applies to `gateway.read` too).
