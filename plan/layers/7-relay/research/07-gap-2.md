# Layer 7 gap-fill 2: one cross-hub custody shape

Code scout, 2026-11-01, no web, nothing run. `M/` = `5-messaging/crates/mesh111/src/`, `N/` = `1-bootstrap/crates/node111/src/daemon/`. Sizes computed from L5 section 3.

## 1. Summary

- **One shape: single-copy PUSH hand-over of custody, from a hub to a paired hub or to its own carrier.** A forward row is a `custody` row whose `dest` is a non-member, plus a `fwd` column. The receiving hub needs no change: a paired hub is an enrolled member that `CUSTODY_PUT`s for the receiver's members, which today's gate already accepts (`M/fabric.rs:2830-2833`).
- **Home-hub discovery:** the sender adds the 8 B hint as ext TLV `0x02` inside the hub-sealed `CUSTODY_PUT` (11 B, optional). Without it the custodian asks each paired hub in turn and remembers the first `ACCEPTED`. Signed member lists and enrol mirrors are rejected.
- **`Dir::Transit` is the wrong container.** It is a `messages` row (`M/store/rows.rs:131-148`) needing peer, stream, epoch and n, which a hub cannot see in a sealed item. Use `custody.fwd`; prune step 1 already evicts handed-over rows (`M/store/prune.rs:229-232`).
- **A+ pull is dropped.** `custody_seq_floor` and member cursors keep their meaning; forward rows never touch them. No per-origin cursor table.
- **Evidence:** the first hub's `ACCEPTED` earns `relayed` (new reason `forwarding`); later hops earn no state; `delivered` comes only from the recipient's `ACK`, an ordinary item on the reverse path.
- **12 L5 amendments, all additive or default-off** (section 3); nothing is added to non-hub nodes.

## 2. The design

**Pairing.** Two hubs run the section 7.3 ceremony in both directions. Each records the other in a new local `FabricSettings.paired_hubs {node_id, leaf, gateway}` and dials it through the daemon's hand-configured `peers` (`N/fabric/settings.rs:49-66`). `home_hub` stays single (`M/fabric.rs:1793`); a paired hub is never a home hub.

**Forwarding rules.** A row has no TTL, so loop freedom is structural. `fwd` records where the row came from.

| `fwd` | accepted when | may go to | never |
|---|---|---|---|
| 1 member | an enrolled member puts a non-member dest and a target exists | a paired hub (hint first, then probe) or this hub's carrier | elsewhere |
| 2 leaf hub | sender is a paired hub marked `leaf` here, and this hub has a carrier (this is the 5A/5B gateway) | the carrier only | another hub |
| 3 carrier | `carrier_inbound`; dest is a member here or of a `leaf` hub | own member (normal row) or a `leaf` hub as a final put | the carrier again |
| other paired hub | never; gate stays today's (dest must be a member) | none | forwarding |

Two leaf hubs paired directly use `fwd=1` only. With no pairing and no carrier the gate is today's.

**Sequence A: paired-hub forward (M_A on hub A, D on hub B).**
```
M_A --CUSTODY_PUT{D, item, TLV0x02 = B[0..8]}--> A           (sealed to A)
A: D not a member; sender is a member; paired B matches hint
   -> custody row (dest=D, fwd=1, committed=0)  [protected]
A --CUSTODY_ACK ACCEPTED--> M_A      M_A: relayed, reason "forwarding"
   (trigger: row inserted, link up, contact event; no timer)
A --CUSTODY_PUT{D, item}--> B         (A is an enrolled member of B)
B: sender enrolled, D enrolled -> normal member row     [gate unchanged]
B --CUSTODY_ACK ACCEPTED|DUPLICATE--> A
A: row committed=1 (evict-first; pkt_ref kept)
   REJECT_UNKNOWN_DEST: next paired hub; all refuse: row stays, re-offered at next peer link-up
B --MAILBOX_ITEM--> D ; D --COMMIT--> B ; D --ACK item(dest M_A)--> reverse path ; M_A: delivered
```

**Sequence B: 5A gateway flush (hub G, carrier off while offline).**
```
M --CUSTODY_PUT{D,item}--> G ; no paired hub claims D, G has a carrier -> row fwd=1
G --ACCEPTED--> M                                    M: relayed (forwarding)
(netlink/WAN event) G spawns the carrier child
G.forward_take(Carrier,n) -> [{custody_seq,dest,item}] --> carrier --> remote mailbox tag(D)
carrier -> forward_done(seq,Taken) => row committed=1 ; child exits
```

**Sequence C: 5B inbound (gateway hub G', carrier child held open).**
```
carrier --item(dest D)--> G'.carrier_inbound(D,item)
 D member of G'        -> custody_put(dest=D, fwd=3); pkt_ref DUPLICATE -> drop
 D member of leaf X'   -> CUSTODY_PUT to X' (final put; X' accepts members only)
G' --push_to(D)--> D (existing PushWindow) ; D --COMMIT--> G'
D's ACK item (dest M) -> fwd=1 at D's hub -> toward the carrier (Sequence B)
```
Carrier acceptance is an internal hub fact, not a message state.

### Answers

1. **Home hub of a non-member.** `CUSTODY_PUT` is `dest(32) ‖ item` and rejects trailing bytes (`M/mailbox.rs:83-97`), so the hint needs a carrier. The sender already has it: `contacts.home_hub`, 8 B from the dest's signed appdata (`M/store/schema.rs:66-79`; `hinted_elsewhere`, `M/fabric.rs:1844`). `Inner.ext.unknown` carries any unregistered TLV today (`M/envelope.rs:641-700`; "unknown type ⇒ skip", `5-messaging/README.md:110`), so `pump_hub` (`M/fabric.rs:2182`) adds `0x02 dest_hub` when the hint differs from the hub's id. That allocates a registry entry; it does not change the envelope. The custodian matches the hint to paired hubs' `NodeId[0..8]`; a hint equal to its own id is rejected (stale-hint semantics kept). With no hint (a `node1…` contact) it probes paired hubs in fixed order, stops at the first `ACCEPTED`/`DUPLICATE`, and caches dest→hub in memory (≤ 256 entries, ~16 KB). A yes is proof (the answerer's gate checked `is_enrolled(dest)`); a no holds for that connection only. *Rejected:* signed member lists and an enrol mirror (both leak the roster to peers, go stale with no clock, and do nothing for a carrier, which addresses by a tag of `dest`).
2. **Push or pull; who holds custody.** Push, because the accepting hub must apply its own gate when responsibility moves. Pull needs a nested item form and a per-origin cursor; `MAILBOX_FETCH` returns only the caller's own NodeId's items (`M/fabric.rs:2910-2940`). Holders: t0 sender outbox; t1 sender + A (protected); t2 sender + A (evict-first) + B; t3 D stores, COMMITs. The sender keeps its copy until `delivered` (README section 9), so a failure costs a retry.
3. **Floor and cursors.** `custody_floor` reads `WHERE dest = ?1` (`M/store/rows.rs:1117-1125`), so forward rows never lower a member's floor. `custody_high` is global; forward traffic only raises a first enrolment's floor, monotonically, skipping nobody. A paired hub's own floor and cursor are vestigial (nobody holds items with `dest` = a peer hub). No replicas in v1, so no origin cursor.
4. **Write and evict.** Write via `custody_put` plus `fwd` (V4 migration after `M/store/schema.rs:55-57`) and a quota-only `Class::Transit` (`M/store/rows.rs:32-70`), so strangers' items cannot starve member custody; fwd rows use `admit(Class::Transit)` at `rows.rs:1018`. Evict: protected while `committed=0`, because they are other people's undelivered items (the "never" tier, `prune.rs:32`). On hand-over `committed=1`, which step 1 already selects (`prune.rs:229-232`) by size × age. Kept, not deleted: `pkt_ref` is the loop guard. Over quota with only protected rows, new forward puts get `REJECT_FULL`. The `Dir::Transit` enum and the "delivered transit copies" query (`prune.rs:236-240`) stay unused.
5. **States.** Hop 1 `ACCEPTED` ⇒ `relayed`, reason `forwarding` when `hinted_elsewhere` is true (set at `M/fabric.rs:3049`). Honest: a mailbox node durably holds it in a protected row; the 6.2 clause "for a known member" is widened. Hop 2 and the carrier: no state. `delivered`: only the recipient's `ACK` (`apply_ack`, `M/fabric.rs:2793`). With no hint the UI shows plain `relayed`.
6. **Loops and duplicates.** (a) `pkt_ref` UNIQUE (`rows.rs:1014-1017`; `DUPLICATE` at `M/fabric.rs:2840`), kept after hand-over, so a bounced item is `DUPLICATE` and counts as done. (b) The origin table. (c) The receiver's prefix/ranges (L5 section 4). Retransmits reuse stored sealed bytes (`M/fabric.rs:2189-2230`) and dedup; a re-sealed copy is caught only at the end.
7. **Amendments.** Section 3.
8. **Bytes on tcp-lan** (3 B frame header counted; 100 B text, one fragment, item I ≈ 190 B):

| hop | frame | bytes |
|---|---|---|
| M → A `CUSTODY_PUT` | I + 120 wrap + 11 hint + 3 | ≈ 324 |
| A → M `CUSTODY_ACK` | 64 + 8 + 18 + 16 + 3 | ≈ 110 |
| A → B `CUSTODY_PUT` | I + 120 + 3 | ≈ 313 |
| B → A `CUSTODY_ACK` | same | ≈ 110 |
| B → D `MAILBOX_ITEM` | I + 90 + 3 | ≈ 283 |
| D → B `COMMIT` | 64 + 8 + 3 + 16 + 3 | ≈ 95 |
| forward total | | ≈ 1.2 KB (6.3× the item) |

   The delivery `ACK` (≈ 100 B item) crosses the same hops: ≈ 0.95 KB more. Wrap: `CUSTODY_WRAP` (`M/frag.rs:64`). The hint adds 11 B to the member put only (`plan_mtu`, `M/fabric.rs:1855`, would use 131).
9. **Resident cost, hubs only.** One held connection per paired hub, each side sending a 3 B keepalive every 25 s (`M/link/tcp_lan.rs:125`): ≈ 2.4 sends + 2.4 receives per minute against the ≈ 205 wakeups/min baseline (`00-code-seams.md` 3.1(a)), so +2.4% per pair. ≈ 0.4 MB/day per pair (3 B + ~52 B IP/TCP, both directions; ≈ 0.75 MB/day with ACKs). A down peer is redialled by the existing back-off to 60 s (`tcp_lan.rs:128`), as a configured `peers` entry is today. The forwarder is event-driven: no timer, no poll. **Non-hub nodes:** every new path starts behind `holds_custody()` (`M/fabric.rs:2830`, `:2911`); their `paired_hubs` is empty and nothing is dialled or stored. The carrier child is spawned on event (5A) or one held connection (5B), zero while off.
10. **Link trait vs hand-off.** As a `Link` a carrier needs `remove_link` (absent; `add_link` only appends, `M/fabric.rs:1587-1609`), a `send` that returns at once (`M/link/mod.rs:262-268`), a new `LinkKind` plus an `openapi.yaml` enum edit (`link/mod.rs:225-252`), and `Route::Via` with per-route planning (`fabric.rs:1821`, `:1852`); `PeerAddr::Opaque` exists (`link/mod.rs:122`). The hand-off form needs none of these: `forward_take(target,n)`, `forward_done(custody_seq, Taken|Rejected|Retry)`, `carrier_inbound(dest,item) -> CustodyStatus`, and a "forward pending / target up" event, over a loopback JSON-lines pipe (the LXMF helper pattern). Paired hubs use the existing tcp-lan link (`dial_peer`, `M/fabric.rs:976`). **Pick the hand-off API; `Link` stays untouched in v1.**
11. **Stays v1.1.** LoRa hint custody (needs an unwrapped form: the 120 B wrap exceeds the 160 B floor, `MtuTooSmall`; plus Layer 6's A1/A3/A6/A7). Multi-copy replication (set reconciliation over `pkt_ref`). Chains beyond the table (a plaintext hop count, an envelope change). A signed forward receipt (the dest hub's `custody-sig`). Member-gateways (a nested `MAILBOX_XITEM`). Sweep-before-ack.

## 4. Costs

- **Per message:** ≈ 1.2 KB forward plus ≈ 0.95 KB return ACK (100 B text, tcp-lan).
- **Per hub:** one column, a ~16 KB cache, a pending map bounded by the Transit quota. Wakeups +2.4% per paired hub; zero with none paired and on non-hub nodes.
- **Carrier:** none while off (5A); ≈ 0.2 MB/day held connection (5B, lens 2); frame overhead is the carrier's (`02-gateways-global.md` finding 4).
- **Build:** no new dependency; one migration, one class, one TLV, three fabric entry points.
- **Pairing over the public internet** exposes `dest_hint`, counters and sizes (`02` finding 17); use a VPN until Layer 6's online Noise IK.

## 5. Fork

| option | what | trade-off |
|---|---|---|
| **F1 (pick): hub-resident push, `fwd` rows, hand-off API** | everything above | Smallest delta; reuses ENROLL and `CUSTODY_PUT/ACK`; no new wire kind. The carrier must sit on a hub: a phone that is only a member cannot carry others' items |
| F2: rendezvous with nested items (lens 2) | peer hubs and gateways are members of a rendezvous hub, which holds `D ‖ item` under `dest` = the member hub; they pull with FETCH/COMMIT and cursors | Allows member-gateways and cursor resume; needs a new `MAILBOX_XITEM` kind, a `custody.dest` that is not the real dest, `on_item` changes (`fabric.rs:3066`) |
| F3: A+ pull (seams report) | peers fetch each other's custody by per-origin cursors | Needs member lists, a cursor table, replica flags; §4 vectors unbuildable; largest and least private |

F2 only if non-hub phones must carry others' traffic; F1 does not preclude it.

## 6. Owner questions

1. **May Layer 7 amend locked Layer 5 with exactly the section 3 list**, all additive or default-off? Nothing else in L5 changes.
2. **Is `relayed` (reason `forwarding`) acceptable at the first hub?** The alternative is `sent` until the dest's hub accepts, which needs a new `CUSTODY_ACK` status and a second ACK that is hearsay unless signed. Without a hint the UI cannot say "forwarding".
