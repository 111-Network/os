# Layer 7 research, 07: gap 1 — adopted carrier and internet link security

Scout, 2026-11-01. Fills critic gap G1 (`06-critic.md` §2). Reads on top of `02-gateways-global.md`; its candidates A-D are re-scored here with the KB gates. Method note: api.github.com and the GitHub MCP (scoped to this repo) are closed, so commit counts, bus factor and issue response could not be read; release dates come from proxy.golang.org, PyPI and crates.io. About 45 lookups, 12 of them one-line registry calls: over the 30 cap.

## 1. Summary

- **No candidate can pass `testing` from desk research** (`0-knowledge/README.md:93`), so the rule's operative branch is "prototype the best candidate" (`:97`), not "build". Lens 2's A is not a new transport: tcp-lan and the hub mailbox are built (L5); A adds glue plus a reach layer.
- **Three problems were mixed.** *Mailbox* (holds bytes: ntfy, chatmail, Nostr, LXMF, our hub). *Reach* (two always-on ends meet without a public address: Yggdrasil, WireGuard, Headscale/Tailscale). *Link crypto*. Reach tools are not store-and-forward: two intermittent 5A islands never meet through them.
- **ntfy is the lightest adopted mailbox.** 111d's ureq + rustls can POST and GET it: no new process or crate. Defaults: 12 h in-memory retention, 4,096 B bodies, no custody evidence, so the ceiling is `sent` (end-to-end `delivered` still works, finding 6).
- **yggstack removes hub A's public-address need** without root, but it is a resident Go process on both ends, RSS unmeasured, and it shows no semver tag (release gate fails on what I could read).
- **Link security: rustls RFC 7250 is feasible and is my pick over `snow`.** No new crypto crate (rustls 0.23.45 + `ring` in the lock); cost is verifier/resolver glue plus a tokio adapter (or `tokio-rustls`, one LICENSING row). A tunnel needs no 111 code.
- **Pick:** ntfy prototype behind a `carrier` seam, hub A + A+ as the evidence-grade path, TLS 1.3 RPK for tcp-lan over the internet (§4).

## 3. Findings that change the plan

1. **Desk research cannot pass `testing`** (`0-knowledge/README.md:93`), so "which candidate passes the gates" has no answer today. The workable rule is: pick the candidate with the best release gates and the lowest weight, prototype it, write the smoke log. By release and commit evidence ntfy and Yggdrasil look healthy; bus factor and issue response are unread for every candidate (api.github.com closed).
2. **ntfy as a mailbox is real but thin.** Poll with `GET /<topic>/json?poll=1&since=<message-id>`; `since` also takes a duration or timestamp, and the docs say to pass the last message ID when polling repeatedly (`docs/subscribe/api.md:240-300`). Publish is a PUT/POST body; "message length 4,096 bytes, longer messages are treated as attachments" (`docs/publish.md:4949`). Practical shape: base64 sealed packets in the body, at most about 3 KB raw per post. A message of 16 fragments at the 160 B floor (about 1.07 KB, `5-messaging/README.md:238`) fits one post; TCP-sized frames (up to 65,535 B) do not and need chunking or the attachment path.
3. **Retention is the weak spot.** Default cache is in-memory, 12 h, lost on restart; durability needs `cache-file` (`server/server.yml:120-152`, `docs/config.md:513`). A self-hosted server can set any `cache-duration`; ntfy.sh's own values I did not read. A 5A phone away for days loses its mailbox on a default server. This is tolerable by design: the sender keeps its copy until `delivered` (`concepts/store-and-forward-states.md`), so carrier loss costs a resend, never a message.
4. **Rate limits are public-instance policy, not ours.** Defaults: burst 60 requests then one per 5 s, 30 open connections per visitor (`docs/config.md:1951-1957`, `docs/publish.md:4950-4954`); ntfy.sh: 250 messages/day anonymous. Batching per message (lens 2, finding 3) keeps a flush inside them. A held 5B connection is one of 30.
5. **Topic names are the only default access control.** Anyone who knows the topic can read it and write to it (`auth-default-access: read-write`, `server.yml:187`). A topic hashed from the NodeId is derivable by anyone who knows the NodeId, so use a topic from a pairing secret, or enable `auth-file` ACL tokens on a self-hosted server. The operator sees client IP, topic, size, timing and the packet header, including the cleartext `dest_hint` and counters (`5-messaging/README.md:90`).
6. **Evidence ceilings differ by carrier type.** A store-and-forward carrier returns an HTTP/mail/relay acceptance, which is not a 111 `CUSTODY_ACK` (needs a mailbox-role node for a known member), so the ceiling is `sent`. A hub over a reach layer can earn `relayed`. `delivered` is the recipient's own sealed ACK and rides any carrier that has a return path, so it works on ntfy too if the far gateway publishes back to a reverse topic.
7. **Yggdrasil is reach, not a mailbox.** yggstack offers SOCKS5, `-remote-tcp` (expose a local port on the node's Yggdrasil address) and `-local-tcp`, no TUN, no root (yggstack `README.md`). A hub behind CGNAT would expose 11183 this way; `dial_peer` takes a configured `SocketAddr` (`fabric/mod.rs:516-517`; an IPv6 literal fits). Termux evidence is one anecdote (snippet). `yggdrasil-android` is MIT (yes) but a VPN-service app (one system VPN at a time, u). Public peers are a community list, possibly offline (`public-peers` README): traffic through strangers is an egress consent item. The README calls Yggdrasil "early-stage".
8. **Tunnels carry tcp-lan unchanged but need privilege or a server.** WireGuard needs an interface (root on Termux). Headscale needs a public control host; client log upload is off under Headscale and `TS_NO_LOGS_NO_SUPPORT` disables it (snippet). A stock Tailscale client logs to its vendor: a KB telemetry auto-fail.
9. **rustls RFC 7250 is confirmed usable (my read of the local source).** `only_raw_public_keys` on `ResolvesClientCert` (`src/client/client_conn.rs:127`) and `ResolvesServerCert` (`src/server/server_conn.rs:132`); `requires_raw_public_keys` on both verifier traits (`src/verify.rs:143,272`); a ready signature check `verify_tls13_signature_with_raw_key` (`src/webpki/verify.rs:213`); Ed25519 signing for TLS via `any_eddsa_type` and SPKI export on the ring provider (`src/crypto/ring/sign.rs:73,393`). rustls depends on `ring` in our lock (`1-bootstrap/Cargo.lock:2003-2013`).
10. **The fabric is tokio, the lock has no `tokio-rustls`** (`fabric/mod.rs:108-109`; no `tokio-rustls` entry). Two ways: a ~150-line adapter driving `rustls::Connection::read_tls/write_tls` on a tokio stream, or add `tokio-rustls` 0.26.6 (MIT OR Apache-2.0, crates.io, updated 2026-09-28).
11. **Link key rule:** L2 says link keys are random, attested, never seed-derived and never the identity key (`2-identity/README.md:372`). So the RPK is a fresh Ed25519 key per node, pinned from the hub card; attesting it needs a new `transport_id` (L2 registry change, lens 2 finding 7). Pin-without-attestation is possible in v1 as TOFU from the card; the attestation is the upgrade.
12. **Snow:** 0.10.0, 2025-07-19, 30.2 M downloads, Apache-2.0 OR MIT (crates.io); unaudited (`2-identity/README.md:252`); buffer-based, so no async glue.

## 3b. Link security costed

| | (a) TLS 1.3 + RFC 7250 via rustls | (b) Noise IK via snow | (c) tcp-lan in an adopted tunnel |
|---|---|---|---|
| new crates | none required; optional `tokio-rustls` 0.26.6 | `snow` 0.10.0 plus any transitive crate not already in `id111` (check `cargo tree`; not run) | none |
| new programs | none | none | tunnel daemon or kernel module per end (separate process) |
| LICENSING.md sign-off rows | 0 (rustls, ring, rustls-webpki rows exist, `LICENSING.md:117` etc.); 1 if `tokio-rustls` | 1 for snow, plus rows for any new transitive crates | 1 per program: Headscale/Tailscale BSD-3-Clause, or WireGuard (GPL-2.0 tools/kernel, separate process, aggregate) |
| 111 code | verifier/resolver pinning one SPKI, stream wrap (~100 lines, estimate) | handshake + framing (~150 lines, estimate) | none; audit: rustls not in L2 §11 table (u), snow unaudited |
| hidden from on-path | frame types, `dest_hint`, counters; static keys inside encrypted handshake | same | same |
| still exposed on path | IPs, ports, timing, record sizes | IPs, timing, sizes, length prefix unless encrypted | tunnel endpoint IPs, timing, sizes |
| far end sees | `dest`, size, `prio_flags`, `dest_hint`, counters (`5-messaging/README.md:409`) | same | same, plus control plane sees keys and IPs |

## 4. Recommendation

### 4.1 Carrier fork (v1 asynchronous store-and-forward between islands)

| option | what | trade-off |
|---|---|---|
| **P. ntfy first, behind a `carrier` seam** | gateways POST/GET sealed batches to an owner-run or public ntfy server; hub A+ stays the evidence-grade path | zero new process or crate, works through NAT with no public address on either island, 5A weighs nothing off. Ceiling `sent`; 12 h default retention; topic-secret and operator metadata; bus factor unread |
| **Q. A + reach layer** | hub with a public address, or a home hub exposed by yggstack or a tunnel; custody and A+ | only path to `relayed`; our semantics; but the A+ build comes first, and yggstack adds a resident process on both ends |
| **R. B chatmail as the default** | existing L6 Delta Chat component | works today, ceiling `sent`, heavier (rpc-server per account) and metadata is mail addresses |

**Pick: P + Q.** Spend the first v1 task on a ntfy carrier prototype: it is the lightest adopted candidate, it also yields the smoke log the KB needs, and the seam it forces (`carrier` link kind, send returns at once, lens 2 finding 16) is the same one every other mailbox would use. Keep Q as the path where evidence matters, with the reach layer left to the owner: public address first, yggstack second (opt-in, one process), tunnel documented as zero-code. R remains available.

### 4.2 Link security fork (tcp-lan over the internet)

| option | trade-off |
|---|---|
| **a. TLS 1.3 RPK (rustls)** | no new crypto crate, widely deployed stack, interoperable with OpenSSL 3.2+; needs verifier glue and a tokio adapter |
| **b. Noise IK (snow)** | matches L2's SHOULD, small and async-agnostic; unaudited, one new crate |
| **c. adopted tunnel** | zero 111 code; privilege, a resident daemon, mixed Termux support |
| **d. nothing (v1 as locked)** | content stays sealed; `dest_hint`, counters, sizes visible on path |

**Pick: a** as the 111 default for hub-to-hub over the internet, **c** documented as the no-code alternative, **b** only if the (a) spike shows the glue costs more than the audit gap. Run a small spike either way.

## 5. Open owner questions

1. May the carrier prototype use the public ntfy.sh for tests, or must it be an owner-run server from day one? (Public default means a third party sees IP, topic and timing.)
2. Is a 12 h default retention acceptable when documented, or must 111 ship a recommended self-host config (`cache-file`, `cache-duration`)?
3. Does the owner accept `sent` as the ceiling for the first carrier and require A+ before any `relayed` claim crosses islands?
4. Which gate failures are acceptable for a prototype: ntfy bus factor and yggstack's missing semver tag are unread or failing here?
5. Is `tokio-rustls` an acceptable new lockfile entry (build-time weight needs your say), or write the adapter?
6. May a gateway use public Yggdrasil peers (stranger-run nodes, egress to them), or only peers the user names?
7. Is the new `transport_id` for an attested link key in scope for Layer 7 (L2 registry change), or is pin-from-card enough for v1?
8. Bench items: ntfy `since=<id>` after the id has been evicted; ntfy.sh retention; yggstack RSS and Termux survival; a rustls RPK handshake against OpenSSL 3.2.
