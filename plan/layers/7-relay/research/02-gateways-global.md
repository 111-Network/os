# Layer 7, lens 2: gateways and the global store-and-forward transport

Research scout report, 2026-11-01. Tree on branch `claude/layer-6-implementation-006mte`. Fetched facts win over training; "(search snippet)" = seen only in a search result; "(unverified)" = could not be fetched. Code is cited as `file:line` under `/home/user/os`. Arithmetic is my own (stated assumptions inline). No code was written or run.

## 1. Summary

- **"The global network" in v1 is not a global 111 swarm.** It is (a) another 111 island's hub, reached over the internet, or (b) a third-party mailbox that stores opaque sealed bytes until the other gateway comes online. Nothing else is honest: 111 has no global address space, no public directory and no global broadcast source of its own.
- **Split the candidates by what they actually give.** *Mailbox-type* carriers store bytes while the receiver is offline (Nostr relay, chatmail/Madmail, LXMF propagation node, SimpleX SMP queue, a 111 rendezvous hub). *Connectivity-type* carriers need both ends online at once (iroh, Reticulum TCP/I2P links, WireGuard, Tor onion service, a direct `tcp-lan` dial). README section 7's "asynchronous store-and-forward transport" is the first kind; the second kind only helps a 5B permanent gateway reach a hub.
- **Only a 111 hub gives the L5 evidence model end to end.** `CUSTODY_ACK` -> `relayed` -> recipient `ACK` -> `delivered` (`5-messaging/README.md` section 9). Nostr `OK`, SMTP accept and LXMF propagated sends all end in `sent` (KB `store-and-forward-states`: "LXMF propagated sends end in SENT").
- **Recommended v1 shortlist (two carriers):** (A) **hub-to-hub over `tcp-lan` with a Noise-wrapped stream and replication A+**, with a 111 hub that has a public address as the rendezvous (no new third-party software); (B) **a chatmail/Madmail relay as the dumb mailbox** for people with no public hub, via the Layer 6 Delta Chat component. Nostr (L2 `0x01`), iroh and LXMF propagation are v1.1 candidates, not v1.
- **Two things need the owner.** The gateway claim must not be probed against 111's own servers (today's 60 s probe is a first-party phone-home timer, `daemon/services/probe.rs:46`), and advertising "I have internet" to the whole mesh is a privacy choice, not a default.
- **Hardware-gated:** only the rate-shaping into a real LoRa link and Android Termux background behaviour. Everything else is checkable with netns stubs.

## 3. Findings that change the plan

1. **README section 7 asks for a mailbox, and most candidates are not one.** iroh, Reticulum links, Tor and WireGuard are pipes (iroh README: "connect to a peer by its key"). Mailbox duty is already inside 111: hub custody (`5-messaging/README.md` section 9). The question is how two hubs reach each other and what holds bytes while one is away.
2. **Cross-hub custody does not exist yet and every mailbox carrier waits on it.** A hub accepts custody "only for its own members (and only from members)" (`5-messaging/README.md` section 9); hub-to-hub replication A+ is "Not built in v1" (same section, section 21). A gateway is a new member class: "a hub whose members are gateways". Layer 7 must define it (enrol a peer hub as a member of a rendezvous hub, or A+ itself), because `REJECT_UNKNOWN_DEST` fires for any dest the hub does not own.
3. **A carrier must not break the fragment plan.** Fragments are sealed individually and reassembled at the destination only (`5-messaging/README.md` section 5, Tier 1); the plan is fixed at queue time (`plan/layers/6-transport/research/00-code-seams.md` section 3, finding 3). A gateway therefore forwards sealed packets as opaque bytes, never re-fragments, and a message planned at tcp-lan size cannot continue over LoRa. Carrier batching (several packets of one `msg_id` in one carrier payload) is glue, not envelope change.
4. **Overhead on Nostr is large for small frames.** My arithmetic (base64 content, 32-hex mailbox tag, 64+64+128 hex id/pubkey/sig): one 160 B sealed packet becomes a ~601 B event (3.8x); 7 fragments batched, ~1.9 KB (1.7x); 16 fragments, ~3.8 KB (1.5x). Batch per message, not per fragment. Limits seen: NIP-11 example `max_message_length` 16384 (https://raw.githubusercontent.com/nostr-protocol/nips/master/11.md); strfry `maxEventSize = 65536` (https://raw.githubusercontent.com/hoytech/strfry/master/strfry.conf); nostr-rs-relay `max_event_bytes = 131072` commented default (https://raw.githubusercontent.com/scsibug/nostr-rs-relay/master/config.toml). Live public-relay limits could not be read: `relay.damus.io` and `nos.lol` answered 403 at CONNECT (unverified).
5. **Nostr's storage kinds fit only one mode.** Ephemeral kinds 20000-29999 are "not expected to be stored" (NIP-01), so they stream (5B) but are no mailbox. strfry rejects ephemeral events older than 60 s and deletes them after 300 s (`strfry.conf`). Replaceable and addressable kinds keep only the latest, which would eat a queue. A mailbox needs a regular kind, which relays may refuse by allowlist (`event_kind_allowlist` in nostr-rs-relay) or retention 0 (NIP-11 draft, search snippet).
6. **Nostr timestamps fight `since` polling.** NIP-59 randomises seal and wrap `created_at` (sample: within the previous two days, https://raw.githubusercontent.com/nostr-protocol/nips/master/59.md); bitchat resubscribes with a 24-hour lookback (https://raw.githubusercontent.com/permissionlesstech/bitchat/main/WHITEPAPER.md). We would not randomise (packets are already sealed; a throwaway signing key hides the gateway), so a fixed `since` window plus dedup by `pkt_ref` suffices; NIP-77 negentropy is the upgrade. NIP-40 expiry is a wall-clock tag relays "may not delete ... right away" (NIP-40): carrier-side only, never crypto.
7. **L2 anticipated Nostr, and also Meshtastic and Reticulum.** `TransportId` is `0x01` nostr-secp256k1, `0x02` Meshtastic, `0x03` Reticulum (`2-identity/crates/id111/src/attest.rs:155-209`). The attested key is a separate secp256k1 key; the Nostr use of it is gateway identity (allowlisting, paid relays), not message authenticity. A hub-to-hub carrier needs a new id (L2 registry change) if its link key is attested.
8. **Public-relay spam defences are the real cost of Nostr.** NIP-13 difficulty is leading zero bits of the event id; `min_pow_difficulty` example 30 (NIP-11). At an assumed 2 MH/s per core: d=20 is ~0.5 s, d=24 ~8 s, d=28 ~134 s, d=32 ~36 min, each bit doubling. Fine for a gateway flush, unusable for a phone sending per message at 28+. Paid relays (`payment_required`) put money and an identity in the flow. Both are relay policy we can meet, not set.
9. **Chatmail numbers, verified.** From the relay's own ini template (https://raw.githubusercontent.com/chatmail/relay/main/chatmaild/src/chatmaild/ini/chatmail.ini.f): `max_message_size` 31457280 B, `max_mailbox_size` 500M, `delete_mails_after` 20 days, `delete_large_after` 7 days (messages over 200k), `delete_inactive_users_after` 90 days, `max_user_send_per_minute` 60, burst 10. These are commented defaults; operators change them. The README states unencrypted mail is rejected and "all messages must be correctly signed with DKIM and OpenPGP-encrypted" (https://raw.githubusercontent.com/chatmail/relay/main/README.md). A sealed 111 packet batch therefore rides as an attachment of a Delta Chat message (the client does the OpenPGP), which is exactly the Layer 6 component. At 60/min a gateway can flush 3,600 batches/hour; a 7-fragment message is one mail.
10. **Madmail federates by HTTP, with no DNS if IP-only.** "Madmail-to-Madmail delivery posts over HTTPS to the recipient's domain" and with `--simple --ip` "HTTP federation can work using the bracketed IP domain"; PGP encryption "is enforced on inbound" on `/mxdeliv` (https://raw.githubusercontent.com/themadorg/madmail/main/docs/project/user-guide/12-dns-mail-auth.md). So an owner-run Madmail on a public address is a rendezvous that needs no domain. Costs (KB): AGPL section 13 source duty, ~35 MB RSS while on, glibc 2.38 floor, push notices to `notifications.delta.chat` unless `madmail push off`. Madmail's own size and retention limits were not documented in what I read (unverified).
11. **LXMF propagation is real infrastructure with a price.** `PROPAGATION_LIMIT` 256 KB, `MESSAGE_EXPIRY` 30 days, `PROPAGATION_COST` 16 with floor 13, `PEERING_COST` 18, `MAX_PEERS` 20, `AUTOPEER` True (https://raw.githubusercontent.com/markqvist/LXMF/master/LXMF/LXMRouter.py). No storage limit by default. Propagation nodes peer among themselves, so a message dropped at one is available at another. Rule 1: carrying sealed bytes needs one more command on the helper (`send_opaque {to, bytes}`), which is the same Python process that already imports RNS (`6-transport/README.md` section 6; `LICENSING.md` section 1). It does not need a new program. Present "a NEW program of ours importing RNS" only as a rule question, never the default; it is not needed here. Internet reach is rnsd's job: Backbone/TCPClient and I2P interfaces (https://raw.githubusercontent.com/markqvist/Reticulum/master/docs/source/interfaces.rst); I2P's need for an external router is unverified.
12. **dtn7-rs/BPv7 gateway-to-gateway, re-evaluated.** On IP the 37-57 B per-fragment block (KB) and the clock-based lifetime stop mattering. It still loses: no custody (BIBE is a draft), nobody in our fleet speaks DTN, an old dependency set (`sled` 0.34.7, `axum` 0.5, `hyper` 0.14), no aarch64 asset, and an unauthenticated local HTTP API (KB `dtn7-rs`). The 111 envelope already carries ids, receipts and custody. Keep ECLA as a later interop seam.
13. **iroh solves NAT, not storage.** Ed25519 keys like our NodeId, ~90 % direct connections (KB `iroh-nodeid`), self-hostable `iroh-relay` with allowlist, shared token or HTTP callout, TLS certificates required (https://raw.githubusercontent.com/n0-computer/iroh/main/iroh-relay/README.md). Default discovery is n0's DNS and public relays (KB), which breaks "no phone-home" unless replaced. A 5A phone and a 5B hub are rarely online at once unless the hub is the always-on side, so iroh helps a phone reach a hub, not two phones meet. L5's +13 MB objection becomes, for a CI-built off-by-default component, "a second Rust program in our tree".
14. **The probe that defines "gateway" today is a first-party timer.** `WAN_INTERVAL` 60 s (`1-bootstrap/crates/node111/src/daemon/services/probe.rs:46`), `wan_probe` HEAD to `https://install.111.network/204` then `static.111.network/204` (`install/preflight.rs:14-15`; `probe.rs:259`). That tells 111's servers, at 60 s granularity, that a node is online. Gateway "internet" should mean "the owner's chosen carrier endpoint is reachable", evaluated on a netlink address/route change (the timer-free hook exists, lens 1 finding 6: `transport/netlink.rs:18-54`) and on a carrier attempt, never by contacting 111.
15. **Meshtastic MQTT is a bridge category, not a 111 carrier.** Each MeshPacket is wrapped in a `ServiceEnvelope`, payload encrypted with the channel key; the public broker applies a zero-hop policy and favours NodeInfo, text, position, telemetry, MapReport and routing (https://raw.githubusercontent.com/meshtastic/meshtastic/master/docs/software/integrations/mqtt/index.mdx). Layer 6 moves readable text only and `LinkKind::MeshtasticClient` is a seam (`5-messaging/crates/mesh111/src/link/mod.rs:225-235`), so sealed 111 frames over MQTT need a private broker plus the 111-over-Meshtastic driver.
16. **A new link kind is an additive contract change.** `LinkKind` holds five values and the OpenAPI enum matches (`link/mod.rs:225-252`; seams section 3.1(b)). A `carrier` kind (stream, `reliable`, `Bulk`, no airtime) lands with an `openapi.yaml` edit and `pnpm gen:types`. `PeerAddr::Opaque` suffices for a mailbox peer. `Link::send` must return at once (finding 7 of the Layer 6 seams); carriers queue and return.
17. **tcp-lan over the internet leaks metadata** (`dest_hint`, counters, sizes; `5-messaging/README.md` sections 8.1, 18). L2 section 6.6 allows an upgrade to Noise IK (random link key bound by L2 section 10) or TLS 1.3 RPK. `rustls` 0.23.45 is in the lockfile (`1-bootstrap/Cargo.lock`); RFC 7250 support there I could not confirm (unverified). `snow` is unaudited per `2-identity/README.md:252`.
18. **Tor is not ready as a v1 rendezvous.** Arti's OnionService doc warns of "many serious problems", no Vanguard support and no meaningful DoS protection (search snippet; `gitlab.torproject.org` does not resolve from this box). The Briar Mailbox pattern (KB `briar-mailbox`) stays a design reference.

## 4. Recommendation

### 4.1 What "the global network" is, for v1

Two things, both opt-in, neither global: **(a) a peer 111 island** reached hub-to-hub; **(b) a dumb mailbox** that holds opaque sealed bytes between two gateways that are not online together. 111 does not host, index or relay a worldwide stream. "Global broadcasts" are signed public frames from a publisher the user follows; there is no firehose to subscribe to.

### 4.2 Fork: which carrier(s)

| option | what it is | trade-off |
|---|---|---|
| **A. 111 rendezvous hub + A+ over `tcp-lan`, Noise-wrapped** | A hub with a public address; peer hubs and 5A/5B gateways dial out; custody and replication as specified | Our semantics and receipts, no third-party software, no new process. Needs someone with a public address (VPS, friend, ISP static IP) and the A+ build |
| **B. Chatmail/Madmail mailbox** | A gateway account on a public chatmail relay (or owner-run Madmail); sealed batches ride as attachments | Works with no public address and no VPS, verified size/retention, component already shipped. Evidence stops at `sent`; relay sees sender/recipient addresses and timing; public relay terms unverified; one Delta Chat account per gateway |
| **C. Nostr relays** | Regular-kind events with a hashed mailbox tag, throwaway keys | Largest free infrastructure and L2's reserved id. Public acceptance, PoW and paid-relay policy unverified; 1.5-3.8x overhead; a new carrier binary with secp256k1 and websockets |
| **D. Reticulum/LXMF propagation** | One more helper command | Zero new component for people with network 2 on. 30-day expiry, 256 KB, sender stamp; `SENT` only; thin public propagation set (unverified) |

**Pick: A + B.** A is the plainest and the only one that earns `relayed`/`delivered`; B covers the person with no public address using something already built and measured by us (Madmail IP-only spike, KB). C, D and iroh are v1.1: C waits for a bench that reads real public-relay limits (this box could not), D for the foreign-model work on the helper, iroh for an owner call on a second Rust program. If the owner prefers the L2-anticipated path, swap B for C; the cost is the unverified relay policy.

### 4.3 Gateway mechanics (event-driven, no heartbeat)

- **5A intermittent:** flush on a connectivity-change event (netlink address/route group on Linux; on Termux no netlink is assumed available, so flush on app open and on a user tap, unverified) and on `fabric` events. Start the carrier child, push the outbox, fetch the mailbox, stop. Zero weight while off.
- **5B permanent:** one held connection (a paired hub or one chatmail IDLE session). Keepalive, assuming a 3 B frame + 16 B tag + ~52 B TCP/IP every 30 s (the interval is "a transport detail"): ~70 B x 2,880 = ~200 kB/day, ~6 MB/month, 2,880 wakeups/day. Doze kills held sockets, so phones are 5A by default (lens 1 finding 9).
- **Advertising:** a gateway says so inside the sealed hub offer to enrolled members and as a role bit in the next announce (L2 A8 has `[ver][roles u16]`; `2-identity/README.md:357-359`), not as a periodic public beacon. Whether to put it in the public announce is an owner question (open question 2).

### 4.4 What a gateway must never do

Proxy inference or any WAN request on behalf of a peer (Layer 3: a hub never proxies inference to the WAN); forward anything unsealed except frames that are public by the author's intent (signed `BROADCAST`) or a bridge the user turned on (Layer 6); bridge into a link marked licensed/amateur without a human confirming per link (KB `lora-airtime-budget`: "On amateur-licensed regions no sealed traffic is sent", obscuring rules, not re-fetched this pass; unverified here); send a carrier byte on a metered connection past the user's data budget; run on a metered link by default.

### 4.5 "Global broadcasts"

A broadcast is a **signed public frame** (`0x30`, `5-messaging/README.md` section 3.2, section 12). Who signs: the publisher's NodeId, or for software the L1 minisign release key (lens 4 owns that). Which the gateway forwards: only publishers the user follows (the user's allowlist, not our policy). Shaping into LoRa is physics advertised by the adapter, not a limit of ours: a 4 KB manifest costs 40 s of LongFast airtime unsealed and 69 s sealed (KB `lora-airtime-budget`), a 1 % band stretches wall time 100x. The 160 B floor leaves under ~90 B after a 64 B signature and header, so a LoRa broadcast is a **pointer** (publisher, hash, size, short text); the object is fetched over a `Bulk` link (`OBJ_ADVERT`, Tier 2, built in v1.1). Broadcasts rank below user messages and wait for airtime.

### 4.6 Consent and metered links

Off by default (Cat 5 is opt-in). Consent names who sees what: a chatmail relay sees addresses, sizes, timing; a Nostr relay sees the mailbox tag and your IP; a rendezvous hub sees `dest` (32 B NodeId in `CUSTODY_PUT`), sizes, timing. A hashed mailbox tag (BLAKE2b of NodeId, a new L2 domain tag) hides the NodeId from relays that do not know it. A daily data budget and a metered flag gate bulk classes; reading Android's metered flag from Termux is unverified.
