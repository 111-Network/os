# Layer 6 draft v0.1 — judge 1: bridge semantics, relay safety, foreign-text threat model

Reviewed 2026-10-19 against `60-transport/README.md` at `23283ba`; law: D23, D25 (F1, F7, F8), D17, D19, D20, D22; L5 v1.2 §4, §6, §7, §10.4, §15, §17, §18; L2 §10 / A10; D10. Read-only; no builds or harness runs.

## Verdict

**amend-then-lock.** The shape is right and obeys the owner: own tables rather than pseudo-NodeIds (D25), explicit directed non-transitive edges enabled only by a human (F7), per-target fan-out with honest refusal (F8), `delivered` only on recipient evidence, foreign text as data everywhere. The defects are textual but real: the loop guard's marker is built from an untrusted name and parsed by a strict pattern that the draft's own `split` option and plausible board names defeat, so two reverse edges on two nodes can loop with growth; `Retry::Later` has nothing that wakes it; the state table calls transmitted texts `failed`; consent is a point-in-time check while the facts it rests on (MQTT uplink, licensed mode, channel key) change on the board; and the untrusted-text rule stops at the proposals view, which renders Markdown. None of these needs a decision reversed. Fix in place, re-check, lock.

## Blockers

**B1. The relay marker loops under two documented cases (construction and parse disagree).** *Where:* §8 guard 3 ("`[<name ≤ 10 B>/<TAG>] ` at the start of the text … treats a text that starts with a registered marker as already relayed"), §15 item 1 (`^\[[^\]/]{1,10}/(M|LX|DC|SX)\] `), §8 "`split` (numbered parts, explicit)", §9 "numbers parts `(1/3) `". *Why:* (a) The draft never says the marker precedes the part number. With `(1/3) [alice/M] …` no part starts with a marker, so a second node (or the same node's reverse edge, where only the cross-node marker layer holds, since guard 1 is row-local) relays it back; the return copy is marker-plus-part-prefix, longer, split again, and never starts with a marker: an unbounded loop with growth whenever both edges of a pair use `split`. (b) `name` is the origin's untrusted `sender_name` on the first hop and the bridge board's own `long_name` after that. A name containing `]` or `/` (a callsign-style `W1AW/7` is ordinary) or cut at byte 10 inside a UTF-8 sequence makes the strict pattern fail on our own marker, so the copy is relayed back; a bridge whose own name contains `/` loops indefinitely across two nodes. Guard 2 does not help: the copy arrives from the *other* bridge's node. *Fix:* define marker construction normatively: name is reduced to a marker alphabet (no `]`, `/`, Cc/Cf, cut at a UTF-8 boundary, non-empty else `?`), the marker is the first bytes of **every** part, and the parser accepts an optional `(k/n) ` before it; G1 adds a two-node `split`-both-ways case and a `]`-named board case.

## Majors

**M1. `Retry::Later` never wakes.** *Where:* §4 "`Later` (re-queue on an adapter event: link up, peer announce, key learned, a free queue slot) … **No timer retries**"; §5 `DUTY_CYCLE_LIMIT`/`RATE_LIMIT_EXCEEDED` ⇒ queued. *Why:* a duty-cycle refusal clears with time; no adapter event fires, and `QueueStatus` with free slots arrives only when something else is sent. A queued row can sit until the user sends again or the board reconnects, against "delivery is non-negotiable". The draft confuses "no wall clock in ordering" with "no monotonic tick": L5's pump already retries on ticks (`tracker.last_tick`). *Fix:* retry `Later` rows on the monotonic tick with capped back-off (a mechanism, not a policy cap); keep "no wall clock".

**M2. On-air NAKs are mapped to terminal `failed`, and `relayed` then NAK is unspecified.** *Where:* §5 "`NO_ROUTE`, `GOT_NAK`, `TIMEOUT`, `MAX_RETRANSMIT`, `NO_CHANNEL`, `TOO_LARGE`, `NO_RESPONSE`, `NOT_AUTHORIZED`, `PKI_FAILED` ⇒ `failed`"; §4 "`failed` is terminal unless a later `delivered` …"; reason `max_retransmit` "no neighbour was heard relaying it". *Why:* `MAX_RETRANSMIT`, `TIMEOUT`, `NO_RESPONSE`, `NO_ROUTE` arrive after the board transmitted up to 3–5 times (R01 §3.7); a channel text so labelled went out on air, and a DM may already be `relayed` (implicit ack) when the NAK lands, which the monotone order forbids regressing and the reason text contradicts. Calling it `failed` is dishonest and the "user may retry by hand" gives up on DMs where L5's model keeps the copy. *Fix:* `failed` only for refusals before air (`region_unset`, `NO_CHANNEL`, `TOO_LARGE`, `NOT_AUTHORIZED`, `PKI_*`, `GOT_NAK`); post-air NAKs keep `sent`/`relayed` with the reason shown ("transmitted, not confirmed"); a DM NAK is `Retry::Later` on the next NodeInfo from that node.

**M3. Consent is checked once, at enable; the facts it rests on move.** *Where:* §8 "Add-ons when true: … the destination is on an MQTT-uplinked channel; the destination account is licensed"; `warning_hash`, `ham_confirmed` columns; §5 MQTT "off by default, one switch per channel"; §10 `PATCH /bridge/settings` carries HAM confirmations and per-channel switches with no round-trip. *Why:* after enable the board owner can turn `uplink_enabled` on, set `is_licensed`, or re-key the channel (a new conversation, but the old `dst_conv` row still names the air channel by name). Nothing says the add-ons are re-evaluated per copy, that the per-channel uplink switch gates relay copies as well as user sends, or that accepting a `bridge_edge` proposal shows the warning and records the hash (only the direct POST does). D25 F7 and D17 #10 require the human act for exactly these facts. *Fix:* consent facts are read live per copy; a change in the add-on set pauses the edge with `consent_required` and the new text; `decideProposal` on `bridge_edge` runs the same 409 round-trip; HAM and uplink confirmations use the same text-plus-hash record; the uplink switch gates every send on that channel.

**M4. Which write routes refuse the bearer is per-route today and the draft names two.** *Where:* §8 "The agent's bearer is refused with `401` on `/bridge/edges` writes, as on message sends (`N/dashboard/api_v1/messages.rs:26-28`)"; §10 table. *Why:* `refuse_bearer` is called route by route (`contacts.rs`, `fabric.rs`, `messages.rs`, `proposals.rs` only); `POST /services/{id}/restart` and `POST /devices/{id}/identify` (`{"consent": true}`) do **not** call it, so the bearer already reaches a restart and a consented probe. §10 adds `POST …/conversations/{conv}/messages`, `POST …/conversations`, `PATCH /bridge/settings`, `/bridge/components`, `PATCH /transport/posture` without stating the rule. *Fix:* one normative sentence: every mutating route in §10 refuses the bearer, `identify` included; G1 asserts `401` for each; `service.restart` (M5) is the only named exception.

**M5. `service.restart` is a foreign-text to radio-outage path.** *Where:* §13 "The one narrow exception … reachable with the bearer, for supervised children only, rate-limited"; §15 item 6. *Why:* `bridge.read` hands the model stranger-written text; a text that steers the model to restart `meshtastic` or `transport` every five minutes drops the board session each time (inbound text lost, R01 §3.11), stops the LXMF child (§6 rule 1), and needs no human. D17's tool table lists the tool, so this is not a contradiction, but the draft itself says "the panel may prefer to route it as a proposal". *Fix:* route restarts of radio-bearing services (`meshtastic`, `transport`, `reticulum`) as a `device`/`service` proposal; keep the direct call for `agent` and `model` at most, refused while a send is `pending`.

**M6. The edge has no relay high-water mark; shed copies make history relayable again.** *Where:* §8 "Only inbound rows with `local_seq > cursor_seq` … that are not relayed copies"; §3 step 2b sheds `queued` copies; §3 step 4 "the origin or copy rows an enabled edge's cursor window still needs for loop guard"; §8 guard 6. *Why:* "already relayed" is only derivable from the existence of a copy row. After 2b sheds a copy the origin looks un-relayed and is re-queued when capacity returns (hours-old text on air, "history is never relayed" broken in spirit), or shed again in a churn loop. "Cursor window" is undefined, and step 4 protects copies while 2b sheds them. *Fix:* persist per edge `relayed_seq` (highest origin `local_seq` handed to a copy, advanced on shed too); inputs are `cursor_seq < local_seq` and `> relayed_seq`; delete "cursor window" and state that guard 6 needs only `origin_msg`/`edge_id` on live rows plus own-echo by sender.

**M7. Pruning: no shaping quota for `Class::Foreign`, and relay backlog starves user sends on air.** *Where:* §3 "the class is not quota-refusable: foreign inbound is pruned, never refused"; §4 "stay `queued` and drain in `local_seq` order"; §15 item 11. *Why:* L5 §10.4 quotas are capacity *shaping* (evict that class first) with refusal as the second half; the draft drops both, so an MQTT-fed channel can drive the store to the watermark between passes and the 1 % disk floor into continuous prune churn (`secure_delete`, incremental vacuum) with 111 rows protected only by order. Separately, the single Meshtastic queue is strict `local_seq` order at 2.1 s per packet: a 300-copy relay backlog puts the user's own message 10 minutes out. *Fix:* give `Foreign` a shaping quota (evict-first, never refuse); the adapter queue takes user-composed rows (`group_id` set) ahead of relay copies, stated as ordering, not a cap.

**M8. Proposal bodies are Markdown; `bridge_message` bodies carry text verbatim.** *Where:* §9 "body = … the text verbatim"; §15 item 1 "rendered as text only (never HTML or Markdown)"; `UI/views/agent/proposal-body.tsx:1,9` (`parseMarkdown`, with `[text](url)` external links). *Why:* the agent quotes a foreign body into a `bridge_message`; the human reads it rendered, with clickable external links and formatting a stranger chose. *Fix:* proposal kinds `bridge_message` and `bridge_edge` render the text part as a preformatted text block; the contract says so.

**M9. The untrusted-text rule stops at Cc.** *Where:* §3 "control characters stripped"; §15 item 1; `A/src/tools.rs:529-546` strips bidi controls, the store does not. *Why:* bidi overrides and zero-width joiners are Cf, not Cc; a Meshtastic `long_name` or LXMF display name with U+202E reverses the rendered line, and zero-width characters let a stranger mimic another sender's name or the chip copy; the marker name (B1) inherits it. *Fix:* at ingest strip Cc and Cf (keep `\n`, `\t`), NFC-normalise, then cap; one function shared by names, bodies and the marker name; the agent scrubber for bodies uses the `messages.read` shape (4096 chars `clean_text`), not `nearby.read`'s 256-char `clean_line` the draft cites (§13).

## Minors

1. **Dedupe collision is silent loss.** §3 `UNIQUE(conv, sender_native, native_msg_id)` with a 32-bit Meshtastic id (10-bit counter plus random, per board) over a conversation's lifetime: a repeat drops a new message. *Fix:* treat as duplicate only within a `local_seq` window (the firmware's own window is 20 ids) and when the body hash matches; otherwise insert.
2. **Attention wording is ambiguous.** §10 "a DM to the board raises the same unread and attention signal as a 111 message": `UI/lib/attention.ts` counts proposals, errors and *requests*, never unread 111 messages; requests are quota-bounded (L5 §7.2, 256) with ignore. A stranger's DM has neither. *Fix:* say "unread only, never the badge" or give foreign DMs request semantics (owner question 1).
3. **`network_message` coalescing does not bound a flood of distinct messages** (§10). *Fix:* coalesce per conversation per tick for unpinned channel traffic (conv plus highest seq).
4. **`bridge_edge` bodies.** §8 "`from: <network>/<conv>`" with §15 item 6 "never text": if `<conv>` is the native id, `ch:<name>:…` carries a stranger's channel name. *Fix:* `fc-` ids only.
5. **§13/§15 item 6 overclaim.** "Foreign text never reaches a tool argument without the human reading it first" is false by construction (`messages.send {text}` is a tool argument). *Fix:* "never reaches a send or an edge".
6. **Own-echo with several accounts.** §8 guard 2 "our bridge node" is singular; two boards of ours on one channel hear each other as inbound. *Fix:* "any account of this node".
7. **One-sided A10 records.** §14 "feeds only the loop-guard hint … where we hold both sides" is muddled; say plainly that a `node_sig`-only record drives no drop or suppression, only the "already bridged by node X" notice.
8. **Pending rows after a crash.** §4: does a `pending` row block later rows in the same conversation? Say no. Also note the firmware drops ids seen in the last 20 (§5), so a crash resend *with the same packet id* is idempotent for recent sends; the draft forbids id reuse without weighing this.
9. **Split-target state and cancel** (§9): one row with parts or one row per part; aggregation of `sent`/`delivered`; cancel of a half-sent split cancels unsent parts only.
10. **Inbound queue overflow** (§4) is a silent text loss with a log counter; surface it in `/networks` and the banner.
11. **"Table constraint backs it"** (§8 DM endpoints) is cross-table; needs a denormalised `src_kind`/`dst_kind` with CHECK or a trigger.
12. **Packets before `config_complete_id`** cannot map channel index to `conv`; buffer or label.
13. **Delta Chat residual** (§7, §15 item 2): the core's own DB holds plaintext for every contact that writes to the bridge account, opted in or not; the warning implies otherwise.
14. **HAM via PATCH** lacks the exact-text record §5 promises; use the 409 round-trip (folded into M3).
15. **Marker byte count:** `{1,10}` must be bytes, cut at a UTF-8 boundary (folded into B1).

## Owner questions

1. Should a stranger's Meshtastic DM to the board raise the header badge on a phone (like a message request, with ignore), or only unread in Messages?
2. Keep `service.restart` as a direct agent action for the radio-bearing services now that foreign text feeds the agent, or route those as proposals?
3. When an edge's facts change after enable (MQTT uplink turned on, board switched to licensed, channel re-keyed): pause until re-confirmed (recommended) or keep relaying with a visible flag?
4. Is a monotonic-tick retry with capped back-off for `duty_cycle`, `rate_limited` and NAKed DMs acceptable under "no timer retries", or must those be retried by hand?

## Sound

Pseudo-NodeIds rejected and own tables (D25) · `local_seq` from the one counter, no clock anywhere · PSK keyed-hashed, never persisted · DMs unrepresentable as edge endpoints, `src ≠ dst`, non-transitive · human-only enable with the exact warning recorded · `delivered` only on recipient evidence; propagated LXMF stops at `relayed`; `delivered` sticky (R07 check 7) · own copies never re-relayed on the same node · `honour_ok_to_mqtt` as an off-by-default per-edge switch (F7) · fan-out refuses before queueing and never truncates (F8) · `fm-`/`fc-` ids are no worse than `msg-<row>` today · unknown SSE events ignored, route order rule · `attested-111` needs both signatures; Meshtastic cannot reach it on 2.7.x (R01 §3.18) · evidence tags I spot-checked match the research (R07 checks 4, 5, 7; R01 §3.7–§3.12, §3.19; R02 §3.9–§3.10; R04 §4.4) · MQTT leak facts (§15 item 4) match R01 §3.12 · Termux residual stated.
