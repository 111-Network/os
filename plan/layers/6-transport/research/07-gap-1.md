# Layer 6, gap scout 1 — MeshChatX actually run (2026-10-19)

Evidence tags: **run** = executed on the lead box (x86_64 WSL2, system Python 3.10.12, no hardware, two network namespaces, no internet route); **src** = read from the installed 4.10.7 wheel; **doc** = web page only. Nothing in the repo or system was changed; one stray log my first `--help` wrote into `~/.reticulum-meshchatx/` was removed. No test script imports RNS or LXMF: the harness is `rnsd`/`rnstatus`/`meshchatx` as processes plus a 60-line aiohttp client.

## 1. Summary

- **MeshChatX works as the LXMF carrier. It attaches to rnsd's shared instance, sends and receives, survives an rnsd restart and sends nothing to the internet.** It needs Python ≥ 3.11, which Debian 11 and Ubuntu 22.04 lack, and its full closure is heavy.
- **Hybrid proven (run):** rnsd 1.5.7 stays on the distro Python 3.10.12, MeshChatX runs from a bundled CPython 3.11 (python-build-standalone) as a shared-instance client, messages flow both ways. So the floor problem is "ship one extra interpreter" or "raise the floor", not "change rnsd".
- **Slim closure (run):** `lxst`, `numpy`, `pycodec2`, `miniaudio`, `wasmtime`, `bleak`, `dbus-fast`, `aioquic`, `pylsqpack` are lazily imported (voice, WASM plugins, BLE, WebTransport). Without them (35 wheels, 33 MB, 128 MiB on disk, 75 MB RSS, 0.4 s start) messaging worked, and every wheel exists for manylinux and musllinux on x86_64 and aarch64. The full 44-wheel closure is 251 MiB and has no `miniaudio` wheel on aarch64.
- **Traps found:** `--auth` is a no-op (API open until setup plus a config PATCH); MeshChatX started before rnsd becomes the instance and silently partitions the node; message state is not monotonic; default inbound stamp cost is 8; a peer must announce before it can be answered. The receive event is `lxmf.delivery`, not `lxmf_message`.
- **Verified for the relay marker:** field 16 `app_extensions` round-trips intact (nested JSON). Fields 0xFB-0xFD can be neither sent nor seen (src). There is no signature-valid flag.
- **Pick:** A, in its slim form, behind the carrier trait. C (importing RNS) stays the contingency. Details in section 6.

## 2. Pass/fail per check

## 5. Egress log

Sniffer: AF_PACKET logger on each veth (tcpdump cannot drop privileges inside the user namespace), logging every IP packet not between 10.99.0.1 and .2, with DNS names and TLS SNI; plus `strace -f -e trace=connect` on every MeshChatX. Positive control: `getent hosts example.com` and `curl https://example.org` from inside A produced `UDP 10.99.0.1 → 10.255.255.254:53 dns=example.com` (also `example.com.telekom.ip`, qtype 1 and 28) every 5 s.

Static scan (src) shows what a browser or an explicit action could reach: `tile.openstreetmap.org`, `nominatim.openstreetmap.org`, `*.openfreemap.org` (map UI, browser-side, in the CSP allow-list; `map_tile_server_url` default is OSM), `meshchatx.com/api/mcx-interfaces` (community directory, never fetched server-side in the run), `cdn.quad4.io` (updater, off for pip installs, switch `MESHCHATX_UPDATE_DISABLED`), `pypi.org` (repository-server feature). So the server side is silent; a hosted Map panel on an online browser would still call OSM. Also: `meshchatx --help` writes `~/.reticulum-meshchatx/logs/meshchatx.log`, so the supervisor must set `HOME`; Landlock and seccomp self-sandboxing were auto-enabled on this kernel (log lines).

## 6. Consequence for the owner's fork

| Option | What it takes | Trade-off |
|---|---|---|
| **A-full**: MeshChatX, full closure | Interpreter ≥ 3.11 (PBS or newer OS), 251 MiB, aarch64 miniaudio build | Upstream-supported set; heavy; Pi-class build step |
| **A-slim (pick)**: MeshChatX minus 9 optional packages, behind the carrier trait | Same interpreter rule; 128 MiB; CI lockfile per arch | Subset is not upstream-supported (only voice, WASM plugins, BLE RNode and WebTransport break, by lazy import; unproven beyond messaging); sunset 2027-01-01 remains |
| **B**: Reticulum MeshChat 2.4.0 (liamcottle, MIT, released 2026-07-06) | Source clone plus Node frontend build (releases are Electron AppImage/exe/dmg only, no PyPI); 5 pip deps; 14 Python files that parse on 3.10 (not run) | Lower Python floor, but no auth at all, no `app_extensions`, no extra API surface; build chain in CI |
| **C**: sidecar importing RNS/LXMF | Owner changes D17 #12 and `LICENSING.md` §1/§7 | RNS/LXMF need only Python ≥ 3.7 (PyPI), so it fits every distro and Termux with no extra interpreter; gives `signature_validated`, custom fields, state callbacks; no web UI to secure; no sunset |

Others: LXMF-Tools (SebastianObi, MIT, last push 2025-03-19, no releases) has `lxmf_bridge_mqtt` (needs a broker and paho; beta), `lxmf_bridge_meshtastic`, `lxmf_bridge_matrix`; stale, not run, reference only. `lxmd` is inbound-only (lens 2). No MeshChatX successor is announced: v5.0.0 is the last release, "fork/rebranding ready"; 15 forks, none above 1 star.

**Pick: A-slim as the v1 carrier, hybrid with rnsd on the distro Python, with C ready.** It meets every hard rule, passed all runs, and keeps the owner's "full UI plus text in Messages" in one adopted program. It does not meet the device floor on Ubuntu 22.04 or Debian 11 unless PBS is accepted, and not on Termux without compiled or CI-built wheels. If the owner will not add an interpreter and wants those targets, C is the only fit.

Adapter rules from the run: start rnsd, wait until rnsd (not a child) owns the socket, then children; do setup plus the auth PATCH right at startup (the API is open until then); stamp cost 0, auto-resend off, scheduled announces; key by LXMF hash and never regress `delivered`; relay marker in `app_extensions` **and** a visible text prefix (stock apps ignore field 16); label senders "unverified" (a source in the announce table was signature-checked: inference).

## 7. Open questions for the owner

1. Is a bundled CPython (python-build-standalone, MPL-2.0 repo, PSF interpreter, ~47 MB per arch) an acceptable new L1 dependency, or do we raise the floor to Debian 12+/Ubuntu 24.04+?
2. Is the slim subset acceptable, or must we run the full upstream closure (+120 MiB, aarch64 source build)?
3. A-slim now and C when v5.0.0 lands (my default), or decide C now? Who maintains a fork after 2027-01-01?
4. Announce policy and bridge display name (default "Anonymous Peer"; announces cost airtime on LoRa).
5. Must the Messages view show verified versus unverified senders (forces C), or is "unverified" enough for v1?
6. Does a Termux phone need its own LXMF carrier, or only the hub?
