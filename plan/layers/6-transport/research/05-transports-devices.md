# Lens 5 — Transports and the device core, scoped without hardware

Date: 2026-10-19. Scout: lens 5 of the Layer 6 sweep (D23). Facts marked **(verified)** were fetched or run today; **(unverified)** = memory or secondary source. Experiments ran on the lead box (Ubuntu 22.04.5, WSL2 kernel 6.6.87.2, Python 3.10.12) from `/tmp/claude-1000/-home-kia-projects-111network-os/af41ab70-058e-4e3c-bc5e-eec7688f5c7a/scratchpad/r5/exp/` (`rns-netns.sh`, `rnode_stub.py`, `run-attach.sh`); nothing in the repo was touched.

## 1. Summary

- **D19 c holds, with two corrections.** The MeshCore KISS modem exists upstream, documented, maintained through 2026-09, with PlatformIO envs for Heltec V3/V4, RAK4631, T-Beam, T3S3 and 60+ other variants. But CI never builds it (only companion/repeater/room-server workflows), and the data-type registry wants a *working demo before* an ID is granted, so "registered with upstream before Layer 6 locks" (D20) cannot happen without the two-board bench. Use the free dev range `FF00–FFFF` until then.
- **Sequence bridge-first on a minimal transport spine.** The LXMF bridge needs rnsd to be reachable (`share_instance = yes`, a TCP listener), which today's `config.tmpl` forbids; nothing in the bridge needs a 111-owned LoRa board. The kiss-modem link is the largest hardware-gated unknown and adds nothing to the owner's headline goal.
- **Hardware-less verification is better than the brief assumed (all verified today).** Unprivileged `unshare -Urnm` gives nested netns + veth; real `rnsd 1.5.7` runs a Backbone server and a TCP client across them, AutoInterface sees its peer across the veth, and a 40-line pty "RNode" stub (no RNS code) brings a real `RNodeInterface` to *Up*. `rnstatus --attach/--detach/--reload` changes interfaces live, so the applier does not need to restart rnsd.
- **Meshtastic 2.8 is a moving target.** Stable is still 2.7.26 (2026-06-24); 2.8.0 was revoked over a signing bug and 2.8.1 (2026-10-01) is a pre-release that changes node numbering, adds XEdDSA signing, a Traffic Management module and a new region/preset table. The Layer 5 presence reader pins `meshtastic==2.7.11`, which predates the 2.8 protobufs; meshmud has one star and two commits.
- **Reticulum:** PyPI is ahead of the GitHub mirror (1.5.7 vs tag 1.5.5), so "latest upstream" must resolve from PyPI. Offline RNode install works by pre-seeding rnodeconf's update cache; `--autoinstall` is an interactive TUI, not an applier action.
- **Android reality is unchanged:** Termux has no 2026 release; TCP-to-hub is still the only reliable phone path; no adoptable helper exists for multicast, USB-to-TCP or hotspot. Build none of them in v1.

## 3. Findings that change the plan

**MeshCore**

1. The KISS modem is real and documented: 115200 8N1; KISS framing; max unescaped frame 512 B; Data ≤ 255 B, larger frames silently dropped; one pending TX (a second Data frame gets `Error/TxBusy 0x07`); p-persistent CSMA with TXDELAY default 500 ms; `SetRadio` = freq Hz (4) + BW Hz (4) + SF (1) + CR (1), little-endian; `GetAirtime(len)` → ms; `TxDone 0xF8`, `RxMeta 0xF9` (SNR×4, RSSI); `GetVersion` returns one byte; `GetIdentity` returns the modem's own Ed25519 pubkey, generated on first boot. https://github.com/meshcore-dev/MeshCore/blob/main/docs/kiss_modem_protocol.md (verified)
2. Envs: `Heltec_v3_kiss_modem`, `heltec_v4_kiss_modem`, `RAK_4631_kiss_modem`, `Tbeam_SX1262_kiss_modem`, `LilyGo_T3S3_sx1262_kiss_modem`, all `+<../examples/kiss_modem/>`; serial is USB CDC unless `KISS_UART_RX/TX` are defined (none are for those three). https://github.com/meshcore-dev/MeshCore/blob/main/variants/heltec_v3/platformio.ini , https://github.com/meshcore-dev/MeshCore/blob/main/examples/kiss_modem/main.cpp (verified)
3. No kiss-modem artifact is ever built or released: workflows are `build-companion-firmwares`, `build-repeater-firmwares`, `build-room-server-firmwares`, `firmware-builder`, `pr-build-check`, none mention kiss. https://github.com/meshcore-dev/MeshCore/tree/main/.github/workflows (verified). D17 #9's "CI-built, manifest-pinned images" is therefore mandatory, not optional.
4. Allocation policy: dev range `FF00–FFFF` needs no request; IDs are granted by PR to `docs/number_allocations.md` only after the project is demonstrably working. Allocated so far: `0100` MeshCore Open, `0110–011F` Ripple, `0120`, `0130–013F`, `0140` Nelos (2026-10-07). https://github.com/meshcore-dev/MeshCore/blob/main/docs/number_allocations.md (verified). This contradicts D20's "registered before Layer 6 locks" unless the bench happens first.
5. GRP_DATA is young: companion support landed ~March 2026, the data-type field was widened to 16 bit and the timestamp dropped on 2026-03-19 (companion_protocol.md history), so ≥ v1.15.0 (2026-04-19) is the earliest sane companion baseline (unverified which tag carried it). Repeater flooding is header-driven, so our opaque payload is unaffected. https://github.com/meshcore-dev/MeshCore/commits/main/docs/companion_protocol.md
6. 1.18.0 (2026-10-15): "Repeater, loop-detect minimal now default (#3239)" per the release post, but `cli_commands.md` still says default `off`: the two disagree (unverified which is true). Minimal drops a packet when the repeater's own 1-byte hash appears ≥ 4 times, so only very long paths are at risk. Also a new Remote CLI contact permission: a MeshCore companion contact granted it can reconfigure and reboot a node, so the agent must never grant it. https://blog.meshcore.io/2026/10/15/release-1-18-0 , https://github.com/meshcore-dev/MeshCore/blob/main/docs/cli_commands.md
7. Radio presets live on a server API (`api.meshcore.nz`); an offline node cannot fetch them, so MeshCore region/preset values must come from the KB (agent never guesses). https://github.com/meshcore-dev/MeshCore/blob/main/docs/radio_presets.md (verified)

**Reticulum**

8. Version truth: PyPI `rns` 1.5.6 (2026-10-02), 1.5.7 (2026-10-05); `lxmf` 1.2.1 (2026-10-13); the GitHub mirror's last tag is 1.5.5 and the author says releases now ship over Reticulum (`rngit release`) and PyPI. The `rns==1.5.6` placeholder in `10-bootstrap/README.md:42` is already behind. https://pypi.org/pypi/rns/json , https://github.com/markqvist/Reticulum/releases (verified)
9. Live interface management (1.5.5): `rnstatus --attach|--detach|--reload NAME`; attach re-reads the config file and starts that stanza; `enable_interface_management` defaults on. Run today against 1.5.7: attach added a listener, detach removed it, reload worked, a missing name returned "does not exist". Posture keys (`share_instance`, `enable_transport`) still need a restart. Reticulum.py:771-830, 1967-1990, 553-556 (verified, plus run)
10. `rnsd` has no validate/dry-run flag; `--exampleconfig` only prints a sample (using.rst:252-269). The brief's "parse with `--exampleconfig`" does not validate anything. Validation = start rnsd on a scratch `--config` dir, read `rnstatus`. An interface that cannot open (missing serial port) shows *Down*; rnsd keeps running (`panic_on_interface_error` defaults off, Reticulum.py:295). (verified, plus run)
11. rnodeconf offline mechanics (rnodeconf.py:1233-1411, 365-368): cache at `~/.config/rnodeconf/update/<ver>/<fw>.zip` plus `<fw>.zip.version` containing `"<ver> <sha256>"`; with `--nocheck --fw-version <ver>` it uses the cache and verifies SHA-256, else downloads from GitHub or `--fw-url`. `--use-extracted` needs five files extracted from a *connected RNode of the same model* (`~/.config/rnodeconf/extracted/`), so it is not an image-pinning mechanism. `--autoinstall` is interactive (`input()` throughout); `--flash` with `--platform/--product/--model/--hwrev` is the scriptable path (unverified without hardware). Upstream `release.json` lists a SHA-256 per zip for 1.86: mirror it into the signed manifest. https://github.com/markqvist/rnode_firmware/releases/latest/download/release.json (verified)
12. Interfaces for the phone-relay pattern (interfaces.rst:34-430, verified): `BackboneInterface` (Linux and Android only; interchangeable with TCPServer/Client; auto-blocks fast-flapping clients), `TCPClientInterface target_host/target_port`, `kiss_framing` only for soundmodem-type peers (never between 111 hubs), AutoInterface UDP 29716/42671 with `group_id`; RNode `port` accepts a serial path, `tcp://`, `ble://`; `airtime_limit_short/long` exist per RNode interface. 1.5.0 added prioritised inbound queues; 1.2.5 added path-request ingress/egress control (release notes, verified).
13. Columba embeds Python RNS (APK names `…official-rns-py…`), so redistributing it means shipping Reticulum-licensed code inside someone else's MPL app: a LICENSING.md call. Crash reporting (Sentry) is on in the default APKs; `-no-sentry` variants exist (needed for the no-telemetry rule). README lists BLE, TCP, RNode; AutoInterface and USB serial are not mentioned (fetch, unverified for USB). https://github.com/torlando-tech/columba/releases/tag/v2.2.6
14. Rust: leviculum's `lnsd` is a wire-compatible drop-in, musl-static amd64/arm64 builds, AGPL-3.0-or-later, still pre-1.0. AGPL-3.0 and GPL-3.0 are mutually compatible, but it is an independent reimplementation, not "Reticulum run as-is" (D17 #12 rule 1). https://codeberg.org/Lew_Palm/Leviculum

**Meshtastic**

15. Release train: stable 2.7.26 (2026-06-24); 2.8.0 (2026-08-30) and 2.8.1 (2026-10-01) are pre-releases; 2.8.0 revoked ("a problem was found in the 2.8.0 packet signing code"). 2.8 changes: node numbers derived from the public key, XEdDSA signing, position/telemetry opt-in, new NodeDB, Traffic Management module, LoRa config applied live without reboot, US first-time default LongTurbo (cannot hear LongFast), licensed operators barred from rebroadcasting to/from unlicensed users. https://github.com/meshtastic/firmware/releases/tag/v2.8.1.8e6a88d
16. 2.8.1 `config.proto` has 37 region codes (incl. ITU 2m/70cm/1.25m amateur regions) and 17 modem presets; the KB region table must be generated from this file, not memory. https://raw.githubusercontent.com/meshtastic/protobufs/v2.8.1/meshtastic/config.proto (verified)
17. Traffic Management rate limiting is opt-in config (window s, max packets; zero = disabled), excludes ROUTING/ADMIN, and sits in the receive path (`TrafficManagementModule.cpp:1165-1176`); whether packets originated by our own client are exempt is not confirmed (unverified). Text payload ceiling stays 233 B (protobufs 2.8.1 comment on `HostMetrics`). https://github.com/meshtastic/firmware/blob/develop/src/modules/TrafficManagementModule.cpp
18. `meshtasticd -s` = "Run in Simulated radio mode", `-p` TCP port (default 4403), `--check` validates config. Docs: no Bluetooth on meshtasticd; serial is a client method, not a radio. https://github.com/meshtastic/firmware/blob/develop/src/platform/portduino/PortduinoGlue.cpp , https://meshtastic.org/docs/software/linux/usage/ . No prebuilt Linux binary sits in the GitHub release (19 assets); use OBS/PPA/Docker or `pio run -e native` in CI (unverified on this box).
19. Automated senders: no official Meshtastic policy found. Community guidance (reply by DM, avoid the default public channel, never on MQTT-uplinked channels; Android app queues emergency > DM > channel and warns of throttling) is third-party. https://areyoumeshingwith.us/docs/general/bots-and-automation/ , https://meshtastic.org/docs/software/android/user/messages-and-channels/ . The bridge should be per-channel opt-in, DM-preferred, and say so in its consent copy.
20. L5's presence reader pins `meshtastic==2.7.11` (`50-messaging/sidecars/meshtastic-presence/requirements.in`); python `main` merged protobufs v2.8.1 on 2026-10-02 but no release followed. Unknown-field tolerance probably keeps it reading, but 2.8 node numbering and signed packets make "probably" a bench item.

### 4.2 Forks

**Fork A: sequencing**
- A1. Transport-first (devices.md §8 order: devices core, interfaces.toml, agent tools, phone relay, then bridge). Trade-off: follows the brief; delays the headline; the largest hardware-gated items come first.
- A2. **Bridge-first on a minimal spine (pick).** Spine = `interfaces.toml` with posture (`share_instance = yes`, optional Backbone listener) + renderer v2 + live-attach applier + `transport.read`; then bridge core (categories in Messages, fan-out, relay, loop guard) with the Meshtastic and LXMF adapters; then phone relay v1; then device core (uevent, probes, RNode upsert); kiss-modem last. Reason: the LXMF adapter is blocked on rnsd posture (`config.tmpl` has `share_instance = no`, finding in devices.md §0.4), and every bridge test runs in netns today; the device core and kiss-modem need boards to prove anything.
- A3. Two parallel tracks (bridge, device core). Trade-off: more total throughput, but they meet in `interfaces.toml` and the Messages UI, and D23 limits agents while Layer 5 closes.

**Fork B: first signed Layer 6 release**
- R-A. Bridge + spine + phone relay v1. Gates: one Meshtastic node, one laptop, one Reticulum peer. Smallest; users still add RNode stanzas by hand or by agent proposal.
- R-B. **R-A + device core (identify RNode/Meshtastic/MeshCore, RNode stanza proposals, uevent) (pick).** Matches the D17 agentic principle; gates G1-G3, G5; by signing time the owner's test setup exists. Fall back to R-A if it slips.
- R-C. R-B + kiss-modem Link and the 111 modem image. Adds the two-board bench, CI image pinning and the MeshCore ID PR; lowest value per risk for the bridge goal. Make it the second release.

**Fork C: how to identify a board.** Own byte probes (RNode 13-byte DETECT, MeshCore `GetVersion`; Meshtastic via meshmud) vs shelling to `rnodeconf --info`. Pick own probes for *family detection* (stable bytes, no Python startup, no human-text parsing) and keep rnodeconf for provisioning, EEPROM, pairing and flashing (adopted). Hardware gate G1 decides whether a probe order is safe.

**Fork D: phone side.** D1 **Termux + TCP-to-hub only (pick for the release)**; D2 add Columba as a recommended app (KB candidate, `-no-sentry` APK, license question in finding 13), smoke test G5; D3 build a helper APK (MulticastLock, USB→TCP, hotspot). Adopt vs build, one line each: Termux adopt; MulticastLock build later (no app to adopt); USB→TCP build later on usb-serial-for-android, ~one small Kotlin service, nothing to adopt; LocalOnlyHotspot build later, unverified API facts; Columba adopt as an optional user choice.

**Fork E: Reticulum implementation.** Python rnsd as-is (pick, D17 #12); lnsd as a later swap-in if the owner wants a Rust path and accepts "wire-compatible reimplementation" as within the rule.

**Plan corrections to record:** (1) D20 hand-off "register data type before lock" becomes "use `FF00–FFFF` until the bench, then PR"; (2) devices.md "`--exampleconfig` parse" becomes "scratch-dir rnsd + rnstatus"; (3) L1 `rns` pin resolves from PyPI at release time; (4) L5 presence-reader pin needs a 2.8 bench item; (5) KB: add `rnode-firmware` with the cache-seeding recipe, MeshCore `number_allocations` rule, Meshtastic 2.8 region table, ble-reticulum, leviculum (reference).
