# Layer 6 research 01 — the Meshtastic bridge (send and receive readable text)

Date 2026-10-19 · scout lens 1 · firmware facts read from source at tag `v2.7.26.54e0d8d` (latest non-prerelease listed, 2026-06-24) unless marked `develop`.
No hardware on the lead box: on-air claims are source-derived; hardware gates are listed in section 5.

## 1. Summary

- **Pick: in-binary Rust.** A thin Meshtastic client inside `111d` (prost types generated from a pinned snapshot of the GPL-3.0 `meshtastic/protobufs`), attached to meshmud's existing TCP downlink `127.0.0.1:11230` as one more downlink. Cost measured here: +152 KiB (x86_64 musl) / +132 KiB (aarch64 musl) of binary. It is the only option that also serves the Layer 5 `meshtastic-client` Link seam (sealed `PRIVATE_APP` frames) from the same connection, send queue and keep-alive.
- **meshmud stays as-is and is the wrong place for the bridge.** It forwards every downlink's `ToRadio` verbatim into one uplink and fans every `FromRadio` out to every downlink, rewriting nothing. Two commits, one release (v1.0.0, 2026-03-20).
- **Three firmware facts reshape the design.** (a) The board's API session lapses after 15 minutes without any `ToRadio` (serial and TCP), and the presence reader deliberately sends no heartbeat, so a latent Layer 5 defect exists today. (b) Heartbeat nonce 1 makes the node broadcast NodeInfo on the mesh, so it is a transmit and must never be sent. (c) The firmware rate-limits phone-originated text to one per 2 s per API instance, shared by every meshmud downlink.
- **DMs are PKI-only and need the recipient's public key in the board's NodeDB.** Without it the firmware returns `PKI_SEND_FAIL_PUBLIC_KEY`. Channel text is the easy path; DMs need a "key unknown, ask the node" state.
- **Names:** the bridge speaks as the board's own node. `User.long_name` is now limited to 24 bytes (protobufs commit of 2026-10-18), short name 4 characters in practice. The bridge should read, show and never write them (keeps "111 never changes node configuration").
- **Licensing is no longer the blocker.** D22 plus `LICENSING.md` section 7 allow it. Two follow-ups: the combined `111d` binary is effectively GPL-3.0-only once GPL-3.0-only generated code links in, and two L0 entries still call this path a blocker and need updating.

## 3. Findings that change the plan

1. **Client API.** `ToRadio` fields: packet=1, want_config_id=3, disconnect=4, xmodemPacket=5, mqttClientProxyMessage=6, heartbeat=7. `FromRadio`: id=1, packet=2, my_info=3, node_info=4, config=5, config_complete_id=7, rebooted=8, moduleConfig=9, channel=10, queueStatus=11. Framing `0x94 0xC3 <len hi> <len lo>`, payload over 512 B is treated as corruption. https://raw.githubusercontent.com/meshtastic/protobufs/master/meshtastic/mesh.proto, https://meshtastic.org/docs/development/device/client-api/. Our shim already deframes this: `1-bootstrap/crates/node111/src/daemon/meshtastic/shim.rs:1-25,52-63`.

2. **MeshPacket for text.** `to` (fixed32; 0xFFFFFFFF = channel broadcast), `channel` (index, local), `decoded{portnum=TEXT_MESSAGE_APP(1), payload, reply_id, emoji}`, `id`, `want_ack`, `hop_limit` (default 3, max 7, https://meshtastic.org/docs/configuration/radio/lora/). On receive also `rx_snr`, `rx_rssi`, `hop_start`, `via_mqtt`, `pki_encrypted`, `public_key`, `transport_mechanism`. `rx_time` is node-clock: display hint only. Text with `emoji != 0` and `reply_id` is a tapback, not a message.

3. **The firmware rewrites `from`.** `MeshService.cpp:188-193`: `p.from = 0` ("We don't let clients assign nodenums"), `next_hop`/`relay_node` cleared, `id` generated only when 0; `Router.cpp` `send()` then sets `from` to our node. So the bridge is a normal Meshtastic node whose name is whatever the board owner configured. `User.long_name`: "Limited to 24 bytes of UTF-8 … Clients should enforce 24 bytes" (`mesh.proto`, commit `9370b7a` of 2026-10-18); `short_name` nanopb max 5 incl. NUL (`mesh.options:13`). Our presence reader truncates at 40 B for display; a bridge-name check must use 24.

4. **Sizes.** `Data.payload max_size:233` (`mesh.options:24`). The firmware actually checks the encoded `Data` against `MAX_LORA_PAYLOAD_LEN 255 - header 16`, minus `MESHTASTIC_PKC_OVERHEAD 12` for PKI (`RadioInterface.h:20-22`, `Router.cpp:658`) and answers `TOO_LARGE`. By my arithmetic (portnum 2 B, payload tag+2-byte length, bitfield 2 B) usable text is about 232 B plain and 220 B PKI. The official composer cap is 200 bytes (https://meshtastic.org/docs/software/android/user/messages-and-channels/); advertise 200 B as the adapter's physical ceiling, not a policy. The firmware decompresses compressed text for the client (`Router.cpp:521-535`). On 2.8, signed broadcasts add 66 B and fall back to unsigned when full (L0 `projects/meshtastic.md`). meshtastic-python refuses over 233 (`mesh_interface.py:560`).

5. **Channels and keys.** Indexes 0-7, 0 = PRIMARY, active channels consecutive; names and PSKs must match to talk. The default key `AQ==` is published: "Anything sent on a channel with the default key can be read by anyone." Keys are 0, 16 or 32 B. Both `uplink_enabled` and `downlink_enabled` default false. https://meshtastic.org/docs/configuration/radio/channels/, https://meshtastic.org/docs/overview/encryption/. The client API hands the host every channel's PSK in the clear (`Channel.settings.psk`), so the bridge parses and drops PSKs and never persists them. It does not need them: the firmware decrypts and delivers `decoded`.

6. **PKI direct messages.** A DM is PKI-encrypted automatically when the sender is not `is_licensed`, a 32-byte private key exists, `to` is not broadcast, the port is not traceroute/nodeinfo/routing/position, and the destination's public key is in the NodeDB; otherwise `PKI_SEND_FAIL_PUBLIC_KEY` (`Router.cpp:648-695`). A non-PKI text DM addressed to us is dropped as "Rejecting legacy DM" (`Router.cpp:499`). A DM to the bridge arrives in `FromRadio.packet` with `to == my_node_num`, `pki_encrypted = true`, `public_key` set, decoded. DM payload ceiling is the 220 B figure above. "Who receives it on our side" is an owner decision (question 1).

7. **Acks and our sent / delivered / failed.** `sent` = `ToRadio` written and no `QueueStatus.res != 0` for that `mesh_packet_id`. A `ROUTING_APP` packet with `decoded.request_id == id` and `error_reason NONE` is an ack: if its `from` equals our own node number it is an implicit ack (a neighbour rebroadcast was overheard), meaning "relayed", else it is a real ack from the destination, meaning `delivered` (meshtastic-python's own test, `node.py:1062-1068`; the app shows "Relayed, not confirmed" vs "Delivered to recipient"). For a channel broadcast the firmware forces `want_ack = false` on the air (`Router.cpp:333-336`) yet keeps a local retransmission record that ends in an implicit ack or a `MAX_RETRANSMIT` NAK after `NUM_RELIABLE_RETX = 3` (`ReliableRouter.cpp:17-35,40-62`, `NextHopRouter.h:93`, `NextHopRouter.cpp:284`): channel text can only reach "relayed". NAK reasons to map to `failed` with the reason shown: `NO_ROUTE 1, GOT_NAK 2, TIMEOUT 3, MAX_RETRANSMIT 5, NO_CHANNEL 6, TOO_LARGE 7, NO_RESPONSE 8, DUTY_CYCLE_LIMIT 9, NOT_AUTHORIZED 33, PKI_FAILED 34, PKI_UNKNOWN_PUBKEY 35, RATE_LIMIT_EXCEEDED 38, PKI_SEND_FAIL_PUBLIC_KEY 39` (`mesh.proto` Routing.Error). `DUTY_CYCLE_LIMIT` and `RATE_LIMIT_EXCEEDED` mean "retry later", not "undeliverable".

8. **Firmware throttling a sender sees.** `PhoneAPI.cpp:795-867`: ids already seen among the last 20 are dropped silently (`wasSeenRecently`); text within 2 s of the previous text gets a `QueueStatus` plus `RATE_LIMIT_EXCEEDED`; traceroute 30 s, position/waypoint/alert/telemetry 10 s. The state (`lastPortNumToRadio`, the id window) is per `PhoneAPI` instance, and the board has one, held by meshmud, so the web-client user and the bridge share the 2 s window and the id window. So the bridge keeps one send queue, spaces its text at least 2.1 s (monotonic clock), treats `RATE_LIMIT_EXCEEDED` as busy-retry, and never reuses a packet id. Duty cycle (EU_868 10%, EU_866 2.5%, rolling hour) yields a client warning notification plus a `DUTY_CYCLE_LIMIT` NAK (`Router.cpp:296-324`; https://meshtastic.org/docs/configuration/radio/lora/). A region left `UNSET` means the node transmits nothing; the bridge must read `Config.lora.region` and say so.

9. **The API session lapses after 15 minutes of silence (latent Layer 5 defect).** `SerialConsole.cpp:27,119-121` and `ServerAPI.cpp:6,34`: no `ToRadio` for `15 * 60 * 1000` ms → `close()` → state `NOTHING`, `FromRadio` stops until a new `want_config_id` (TCP: the socket is dropped). The Rust crate's own comment cites this and heartbeats every 5 min (`rust/src/connections/handlers.rs:17-19`); the web SDK every 30 s (`web/packages/sdk/src/core/client/handshake.ts:44`). `meshtastic-presence` strips the library's heartbeat on purpose (`sidecars/meshtastic-presence/README.md`, "No send path"), so with no panel open Nearby silently freezes after 15 minutes on serial. The bridge must heartbeat with nonce 0 or 2+ (`PhoneAPI.cpp` heartbeat case, ~216-232). Nonce 1 means "broadcast our NodeInfo" and is a transmission; the web SDK reserves it for that reason (`handshake.ts:47-52`).

10. **meshmud multiplexing.** From source (clone at `fabe043`, 2026-03-20): each downlink goroutine pushes frames to the uplink's single channel (cap 64, `uplink.go:62,227-248`), written in order; nothing is rewritten, and only `MyNodeInfo` and mesh packets are parsed (`uplink.go:130-143`). Every `FromRadio` goes to every downlink, with a per-client buffer of `mesh_packet_buffer + 256` and drop-with-warning when full (`uplink.go:145-153,193`). If the uplink drops, all downlinks are closed (`dtcp/listener.go:123-139`) and reconnection is the client's job; uplink retry is 10 s (`common/config.go:22-23`). `mesh_packet_dedupe = true` rejects a second connection (`dtcp/listener.go:78-82`): keep it false. There is no DTR/RTS handling (grep: none). Consequences: any client's `want_config_id` restarts the board's config stream for everyone, so each client must ingest replays idempotently and send its own `want_config_id` only once per connection. The web client uses two special nonces, 69420 (config only) and 69421 (nodes only), and notes that re-sending `want_config` inside a session "can wedge firmware" (`handshake.ts:1-21`). A client that drains slowly loses inbound text.

11. **Inbound text can be lost while no client reads.** The firmware's `toPhoneQueue` holds 8 (ESP32 non-S3/C3) or 32 packets; a full queue discards the oldest text (`MeshService.cpp:319-335`, `mesh-pb-constants.h:16-21`). The bridge must stay connected and drain promptly; the UI should say that texts received while it was offline may be missing.

12. **MQTT: what leaks where.** Uplink is per channel. A packet we originate is uplinked whenever its channel has `uplink_enabled`; `ok_to_mqtt` gates only other nodes' packets (`MQTT.cpp:782-786`; `Router.cpp:589` stamps the bit from `config_ok_to_mqtt`). PKI DMs are uplinked as opaque blobs as soon as any channel has uplink enabled (`MQTT.cpp:772-775,796-798`). Packets arriving through MQTT carry `via_mqtt`; `ignore_mqtt` drops them (`Router.cpp:868`). The public server delivers zero-hop, prioritises only NodeInfo/Text/Position/Telemetry/MapReport/Routing, and clamps position precision (https://meshtastic.org/docs/software/integrations/mqtt/); the MQTT module page lists no numeric rate limits. The bridge reads each channel's `uplink_enabled` from `FromRadio.channel`, warns "this channel is published to the internet" before the first send, and tags received `via_mqtt` packets "via internet". Loop guard for cross-network relays cannot rely on Meshtastic: it uses the attested bridge node numbers of our own nodes (A10) plus message ids.

13. **HAM mode.** `is_licensed` → no PKI on DMs (`Router.cpp:648`); the docs say the call sign goes in `long_name` and the channel PSK "Should be Empty, removing encryption"; ITU regions are selectable only in licensed mode (https://meshtastic.org/docs/configuration/radio/user/, https://meshtastic.org/docs/configuration/radio/lora/). The bridge reads `User.is_licensed` from our own NodeInfo, refuses all sealed `PRIVATE_APP` frames, and keeps readable bridging off until a human confirms (US rule at `plan/cross-layer/devices.md` section 0.6).

14. **Community rules for automated senders.** No official Meshtastic policy on bots was found (searches 2026-10-19). The default LongFast key is public and the Android page says the mesh applies airtime fairness. The only automation guide found is regional, dated 2026-08-16 (https://areyoumeshingwith.us/docs/general/bots-and-automation/): "bot" in the node name, reply by DM, avoid the default channel, keep replies short, never answer other bots. A third-party mirror says 2.8.0 adds a rate-limiting Traffic Management Module (unverified; 2.8.0 builds are revoked). Proposed defaults follow these norms: bridging off per channel; never the default channel unless the user picks it; DM replies preferred.

15. **meshmud on Termux.** Release assets are darwin/linux/windows only (https://api.github.com/repos/Rikonardo/meshmud/releases). Our `meshmud-build.sh:145-148` builds `CGO_ENABLED=0 GOOS=linux`; the static arm64 binary should run in Termux (unverified; Go is absent on the lead box). Go's pure resolver misbehaves without `/etc/resolv.conf` on Android (https://golang.org/issue/8877, forum reports), so a Wi-Fi-board uplink should be an IP literal.

16. **Rust numbers (measured here, scratch crates under the session scratchpad).** Release profile as the workspace (`lto=thin`, `codegen-units=1`, `strip=symbols`, `panic=abort`); generated code from `protobufs@9370b7a`: 14,841 lines, 585 KB, full `FromRadio`/`ToRadio` encode+decode.

17. **Licence consequences of A.** GPL-3.0-only generated code in `111d` makes the combined binary effectively GPL-3.0-only (our files stay `-or-later`); `LICENSING.md` section 7 should say so, with sign-off rows for prost, bytes, prost-derive, and the vendored `.proto` snapshot (commit hash plus checksum, shipped beside the notices). Two L0 entries contradict D22 and need a fresher-source edit: `0-knowledge/projects/meshtastic-python.md:36` ("protobufs would be imported into the Rust binary" under Do NOT use) and `:60` ("would make our binary GPL-derived"); also `meshmud.md`'s "no GPL in our binary" sentence and Layer 5 section 14's "no Meshtastic protobuf code enters our Rust binary".

18. **A10 cannot be satisfied as written for a stock board.** The attestation needs a `transport_sig` from the transport key (`2-identity/README.md:223-234,366-370`). A Meshtastic key is X25519; direct messages are unsigned ("Direct messages aren't signed", encryption page); XEdDSA signing exists only for broadcasts on 2.8, which is still prerelease. On 2.7.x the host cannot make the board sign anything. The Meshtastic bridge identity is therefore the node number plus public key, bound by `node_sig` alone, or by a signed 2.8 broadcast later (question 7).

19. **Coexistence facts for the hosted panel.** The web client's HTTP transport `disconnect()` only stops polling and emits a status (`web/packages/transport-http/src/transport.ts:196-215`), so the shim never relays a `ToRadio.disconnect`. A raw `disconnect` frame would call `close()` on the firmware session for all clients (`PhoneAPI.cpp` disconnect case), so the shim should drop `ToRadio` field 4 as a one-byte tag check (0x20), still without decoding protobuf. The firmware does not echo phone-sent text back to other clients (`MeshService.cpp:208,247,263`: `ccToPhone` defaults false), so the web panel will not list bridge-sent texts and our Messages view is the record of them (unverified on hardware). Termux residual (any app can write to the downlink) stays on the service page.

## 4. Recommendation

**Fork: where the bridge lives.**

- **A. In-binary Rust (pick).** `daemon/meshtastic/client.rs` next to `shim.rs` and `meshmud.rs`: connects to `DOWNLINK`, runs the handshake once, a keep-alive (nonce 0), a single send queue, receives `FromRadio`, serves both the text bridge and the `meshtastic-client` Link (`mesh111/src/link/mod.rs:228-264`). Trade-offs: +~150 KiB, GPL-3.0-only effective, schema pin to maintain; best restart behavior (a task, not a respawned process) and one place for the 2 s spacing, id uniqueness and allowlist.
  - **A1 own thin client on prost (pick).** About 300 lines; reuses the shim's deframer; send allowlist enforced at the lowest layer like the presence reader: `ToRadio.packet` only for `TEXT_MESSAGE_APP` (later `PRIVATE_APP`), `want_config_id` once per connection, heartbeat nonce never 1, nothing else (no admin, no config).
  - **A2 adopt the `meshtastic` crate.** Less code, +372/+332 KiB, 0.1.x, a one-author crate, brings tokio-serial and MPL-2.0 `serialport` for features we do not use. Keep as the fallback if A1's stream layer proves fiddly.
- **B. Extend the Python presence sidecar into a two-way bridge.** Proven library, `onAckNak`, venv exists. Against: sealed `PRIVATE_APP` frames would cross a Rust-Python JSON-lines line for the Link seam (two paths or a second protocol); Python on every Termux node for the critical path; the library needs the reader's `_sendToRadio` guard (disconnect, heartbeat, admin); a respawn means a fresh `want_config`. Choose it only for zero GPL code in `111d`.
- **C. A feature in meshmud (Go).** Reject: unmodified-upstream rule, a two-commit project, Go absent locally, and linking Meshtastic Go protobufs would flip meshmud's closure to GPL (its own verdict step, `meshmud.md`).

**Rules for coexisting with the hosted panel (section 5 of the lens):**
1. The bridge is just another downlink; the panel keeps one per session via the shim.
2. The bridge sends `want_config_id` once per connection, ingests everyone's replays idempotently, and uses a random nonce, never 69420/69421.
3. Fold Nearby into this client (it already receives every NodeInfo) and retire the Python reader after parity: one handshake instead of two, and the heartbeat defect (finding 9) goes away. Until then the reader needs a nonce-0 heartbeat (question 4).
4. All outbound goes through the single queue; panel sends are outside it, so `RATE_LIMIT_EXCEEDED` is retry-with-backoff, not failure.
5. The shim drops `ToRadio.disconnect` (finding 19).
6. The Layer 5 section 14 sentence "111 does not see or store" what the user does in the panel stays true for panel sends only; received texts are now stored in the Meshtastic category.

**Proposed service-page copy (replaces "111 never transmits", D23):** "111 transmits on Meshtastic only what you send or choose to bridge, as a normal text from your board's own node `<long name>` (`!<id>`). Anyone on that channel can read it: Meshtastic protects channel messages with the channel's key, and the default channel's key is public. If your board uploads to an MQTT server, messages on channels with uplink enabled are published there. Messages from Meshtastic that appear in 111 are not 111-sealed and are labelled with their Meshtastic sender. Meshtastic is a registered mark, used nominatively."

## 5. Open questions for the owner

1. A DM addressed to the board's node: who sees it, the node's single operator, or every member of a home hub (each with their own inbox)?
2. Foreign text longer than about 200 bytes going into Meshtastic: split into numbered parts, or refuse? (Physics, not policy, but it changes what "send the same message everywhere" means.)
3. Default reach: do all configured Meshtastic channels appear read-only in Messages from first run, and is relaying the default public channel into other networks allowed at all (amplification)?
4. May Layer 6 retire the Python presence sidecar once the in-binary client reaches Nearby parity?
5. Bridge node name: never touch node config (keep L5's promise, name set in the hosted panel), or may the agent propose a `long_name` (24 B) as a typed action?
6. Licensed/HAM boards: bridge fully off, or plain-text bridging after an explicit human confirmation?
7. A10 for Meshtastic: accept a `node_sig`-only attestation on 2.7.x boards?
8. Accept that the shipped `111d` is effectively GPL-3.0-only (our own files remain "or later")?

Hardware gates for the runbook: serial reset behavior under meshmud, the 15-minute idle lapse on serial and TCP, panel plus bridge concurrent sends, implicit vs real ack on two boards, DM with and without a known key, Termux run of linux/arm64 meshmud.
